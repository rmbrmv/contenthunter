# WP#44 — TikTok: честное и надёжное заполнение описания

**Дата:** 2026-05-29
**Ветка:** `wp44-tt-caption-honest-fill`
**OpenProject:** WP#44 «Выкладка (добавить теги в описание)» → статус «В разработке», assignee Данил
**Автор задачи / репортёр симптома:** Анастасия

## Что было не так

Автовыкладка в TikTok публикует ролики **без описания** (и, как следствие, без хэштегов, которые в TT вшиты в текст описания). Симптом массовый и «упорный», репортится Анастасией с 26.05 по многим клиентам/телефонам (эзотерика оракул 162/163/165, Кликпей, Юлия Сваровски 74/75, Lexis Voice 16/17, PANDAFiT 73, Комильфо 37/39, аквабрайт 81/82), свежак 29.05 — «все сегодняшние выкладки в ТикТок без описаний».

### Диагностика (по проду, 23–29.05)

1. **Текст собран правильно.** В `publish_tasks.caption` за 29.05 у TikTok 59/59 непустых описаний (254–368 симв.), описание+хэштеги внутри одного поля, `hashtags=[]` (для TT теги намеренно вшиты в caption на сервере). То есть серверная сборка текста и фича добивки тегов (`hashtag_enrich.js`, WP#44 iter1) работают. **Проблема не на сервере, а на устройстве.**

2. **Поле описания TikTok невидимо для UIAutomator.** Дампы TT-экрана не содержат ни одного узла `EditText`, ни `focused="true"`, ни читаемого текста — поле рендерится через Canvas / обфусцированные классы (`X.12py`, `X.10UB`). Прочитать введённый текст из дампа **невозможно**.

3. **Device-side баг — печать вслепую без честного провала.** В `publisher_tiktok.py` (блок «Шаг 4: описание», ~стр. 1876–1928):
   - `tap_element` ищет поле по тексту-маркеру — на Canvas-поле часто не находит;
   - срабатывает fallback по **фиксированным координатам** `(540, 250/290/350/400)`;
   - есть проверка «открылась ли клавиатура» (`_is_keyboard_shown` XML + `dumpsys input_method … mInputShown`), **но она ни на что не влияет** — после перебора координат код **всё равно** выполняет `adb_text(caption)` и логирует «✅ caption введён», даже если поле не сфокусировано;
   - текст уходит «в никуда» → пост без описания, а телеметрия рапортует успех. Поэтому проблема невидима в кодах ошибок и держится «упорно».

4. **Масштаб растёт.** Доля TT-задач, ушедших в слепой fallback (поле не найдено `tap_element`): 25.05 — 49%, 26.05 — 34%, 27.05 — 45%, **28.05 — 69%, 29.05 — 64%**. Из ~41 «caption введён» за 29.05 — 38 шли уже после полного перебора координат. Деградация связана с layout/навигацией самого приложения TikTok (наш код блока не менялся — пришёл с рефактором `b97f09a`).

5. **Эталон рядом — Instagram.** В `publisher_instagram.py` заполнение надёжно: `_extract_caption_input_state` читает узел `caption_input_text_view` (флаг `focused` + фактический текст), после ввода идёт **верификация** с честным событием `caption_verify_failed`. Поэтому в IG описания не теряются. В TT этого нет вовсе. (IG-приём чтения текста для TT неприменим — поле Canvas; честный сигнал для TT — только состояние IME.)

## Что делаем

Фикс **только по TikTok**. IG уже надёжен, YT (отдельное поле описания) — вне scope (симптом только по TT).

### 1. Гейт по фокусу (ядро честности)
Переписать блок «Шаг 4: описание» так, чтобы `adb_text(caption)` выполнялся **только после подтверждённого фокуса** поля. Честный сигнал — IME показан: `_is_keyboard_shown(ui)` (XML) **ИЛИ** `dumpsys input_method | grep mInputShown` (Canvas-независимо, уже считается как `_kbd_adb`). Никакой печати вслепую.

### 2. Точнее наводимся на поле
Перед фиксированными координатами — найти узел поля по тексту-маркеру (`Добавьте описание`/`Caption`/`Описание`) и тапнуть по **центру его bounds** (а не по самому label-узлу). Фиксированные координаты `(540, 250..400)` оставить только как последний резерв. Цель — поднять долю авто-успеха (сейчас 64–69% уходят в слепой fallback) и сократить нагрузку на ручную очередь.

### 3. Честный фейл → в ручную
Если после всех попыток (node-tap + перебор координат) фокус **не подтверждён** — НЕ печатать. Отдать новый честный код `tt_caption_field_not_focused`:
- завести в каталог `publish_error_codes` (класс — как «ui_changed» / сразу в ручную, по таксономии WP#140);
- **завалить задачу** этим кодом → она маршрутизируется в ручную очередь, оператор выкладывает с описанием.

Решение пользователя (29.05): никаких постов без описания; честный фейл предпочтительнее «постить и пометить на дозалив».

### 4. Правда в телеметрии
Убрать безусловный лог «✅ caption введён». Логировать раздельно:
- успех: «TikTok: caption введён (фокус подтверждён, N симв.)»;
- провал: честное событие + код `tt_caption_field_not_focused`.
Чтобы на дашборде и у Анастасии была видна реальная картина (а не ложный 100% успех).

### 5. Kill-switch
`TT_CAPTION_FOCUS_GATE_ENABLED` (по умолчанию **ON** — включаем честный гейт сразу в проде). При `OFF` — старое поведение (слепая печать + «успех»), мгновенный откат без редеплоя. По принятому в проекте стилю (рубильник на каждый поведенческий фикс).

### 6. Тесты + codex
Юнит-тесты на решение гейта по образцу выделенных IG-тестов:
- фокус подтверждён → `adb_text(caption)` вызывается, лог честного успеха;
- фокус НЕ подтверждён → `adb_text` **не** вызывается, выставляется `tt_caption_field_not_focused`, задача падает;
- `OFF` kill-switch → legacy-поведение (регресс-страховка).
Затем `codex review` раундами до 0 P1, потом — на ревью Данилу.

### 7. Деплой
Прод-autowarm через **PM2** (не systemd), по принятому стилю. Деплой ≠ push (прод делает pull). Verify на утренней пачке выкладок: доля `tt_caption_field_not_focused` и отсутствие постов без описания.

## Архитектура / границы

- **Затрагиваемый модуль:** `publisher_tiktok.py` — блок заполнения описания (Шаг 4). Изоляция: вынести решение «фокус подтверждён?» и «что делать при отсутствии фокуса» в небольшой чистый helper (тестируемый без устройства), по образцу IG-хелперов (`_extract_caption_input_state` / `_build_caption_verify_failed_meta`).
- **Каталог кодов:** `publish_error_codes` — добавить `tt_caption_field_not_focused` с корректным классом.
- **Конфиг:** env-флаг `TT_CAPTION_FOCUS_GATE_ENABLED` (default ON), читается на спавн (`load_dotenv`), без рестарта.
- **Без изменений схемы БД.** Используем существующие `publish_tasks.events` (JSONB) и механику завала задачи → ручная очередь.

## Критерии готовности

1. При неподтверждённом фокусе TikTok НЕ печатает вслепую и НЕ рапортует ложный успех.
2. Такая задача падает с честным `tt_caption_field_not_focused` и уходит в ручную очередь.
3. При подтверждённом фокусе описание вводится и логируется честно.
4. Kill-switch `OFF` возвращает прежнее поведение.
5. Юнит-тесты зелёные; `codex review` 0 P1.
6. На утренней пачке: нет TT-постов без описания (по выборочной проверке Анастасии), коды ошибок отражают реальность.
