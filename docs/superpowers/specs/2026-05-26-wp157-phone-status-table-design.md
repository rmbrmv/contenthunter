# WP #157 — Таблица статусов телефонов в реальном времени

**Дата:** 2026-05-26
**Задача:** OpenProject #157 «Сделать таблицу для отслеживания статуса телефона»
**Статус:** дизайн на ревью

## Проблема

Операторы не понимают, можно ли сейчас что-то делать на телефоне (малинке) — не только в момент выкладок, но и при создании аккаунтов, прогревах, проверке выложенного. Если оператор полезет на телефон, который в этот момент ведёт автоматика, — коллизия и порча работы. Нужна таблица: по каждому телефону текущий статус + подробная строка из лога, обновляемая близко к реальному времени.

## Цель и не-цели

**Цель.** Операторский экран-таблица: одна строка на телефон, колонки «телефон / статус / подробно / обновлено», поллинг ~5–10 c. Статус честно отражает, занят ли телефон автоматикой/оператором прямо сейчас.

**Не-цели (вне охвата v1).**
- Управление телефоном из таблицы (старт/стоп задач) — только просмотр.
- Изменения схемы БД, lock'и, heartbeat'ы, правки `publisher.py`/фабрики/прогрева. Чисто read-only агрегатор.
- Push-realtime (SSE/WebSocket) — используем поллинг, как остальной дашборд.
- Историческая аналитика занятости — только текущее состояние.

## Подход

Read-only агрегатор поверх существующих таблиц задач. Все подсистемы, которые ведут телефон, уже пишут строки с прямой привязкой `device_serial` (= `factory_device_numbers.device_id`) и статусом. Новый GET-эндпоинт в `server.js` собирает «активные» строки из источников, сводит их по телефону через изолированную чистую функцию разрешения статуса и отдаёт массив. Новый под-таб во фронте раз в ~7 c опрашивает эндпоинт и рисует таблицу.

Никаких миграций и правок воркеров: проверено, что у создания аккаунтов есть `factory_reg_tasks`, у проверки выложенного — `archive_tasks`, у ручной выкладки — `validator_manual_publish_queue` с привязкой к устройству. Изначально предполагавшейся «дыры» (подсистема без таблицы задач) нет.

## Источники данных (без миграций)

**Реестр телефонов (строки таблицы):**
- `factory_device_numbers` — `device_id` (серийник, ключ join), `device_number` (отображаемый «#»), `raspberry`, `active`.
- `raspberry_port` — `host` (по `raspberry_number`).
- `device_state` — последняя строка по `device_id`: `online`, `battery_percent`, `checked_at` (источник правды для онлайна).

**Активность по `device_serial` (6 источников):**

| Статус | Таблица | Предикат «активно» | Подробно (detail) |
|---|---|---|---|
| автовыкладка | `publish_tasks` | `status IN ('running','processing')` | последний `events[].msg` (с ts), иначе хвост `log` |
| ручная выкладка | `validator_manual_publish_queue` | `operator_status='in_progress' AND cancelled_at IS NULL` | `pack_name`/`account_username`/`platform` + кто взял (`taken_by_id`→`autowarm_users`), `taken_at` |
| создание аккаунтов | `factory_reg_tasks` | `status='running'` | `current_step`, иначе последний `events[].msg`/`log` |
| прогрев (аккаунт) | `autowarm_tasks` | `status='running'` | `events`/`log`, `current_day` |
| прогрев (телефон) | `phone_warm_tasks` | `status='running'` | `events`/`log`, `day`/`session` |
| проверка выложенного | `archive_tasks` | `status='running'` | `account`/`platform`, `videos_checked` |

Каждый источник также отдаёт «время свежести»: `updated_at` (для `archive_tasks`, где нет `updated_at`, — `started_at`; для ручной — `updated_at`/`taken_at`).

## Классификация состояний задачи

Не каждая незавершённая строка = «телефон занят». Делим состояния на три класса:

- **ACTIVE** — автоматика/оператор ведёт телефон прямо сейчас (предикаты из таблицы выше: `running`/`processing`/`in_progress`). Только это даёт «занят».
- **RESERVED** — телефон зарезервирован, скоро возобновится: `autowarm_tasks`/`phone_warm_tasks` `status='paused'` (есть `resume_at`). Не «свободен», но и не «активно занят» — отдельный класс.
- **NOT-BUSY** — `pending`/`scheduled`/`queued`/`done`/`failed`/`cancelled`/`skipped` и т.п. Телефон с точки зрения этой подсистемы свободен. В частности `validator_manual_publish_queue.operator_status='queued'` (их сотни) — это очередь на ручную, НЕ занятость; показывается отдельным мелким бейджем-счётчиком, не статусом.

## Разрешение статуса (изолированная чистая функция)

`resolvePhoneStatus(device, activities, now) -> { status, kind, detail, stale, updatedAt, queuedManual }`

Алгоритм:
1. Собрать ACTIVE и RESERVED строки телефона из 6 источников.
2. Разбить ACTIVE на **свежие** (`now - updatedAt <= STALE_THRESHOLD`) и **залипшие** (`>`).
3. Если есть свежие ACTIVE → `status` = старший по приоритету тип среди свежих, `detail` из этой задачи, `kind='busy'`.
4. Иначе если есть залипшие ACTIVE → `status='возможно завис (<тип>)'`, `detail` = последняя строка + «нет обновлений N мин», `kind='stale'`. (Намеренно НЕ «свободен» — оператор разберётся.)
5. Иначе если есть RESERVED → `status='<тип> на паузе'`, `kind='reserved'`.
6. Иначе если `device_state.online=false` (или нет свежей строки `device_state`) → `status='offline'`, `kind='offline'`.
7. Иначе → `status='свободен'`, `kind='free'`.

**Fail-closed при недоступном источнике (критично для безопасности).** `resolvePhoneStatus` принимает набор успешно прочитанных источников. Если хотя бы один из 6 источников не прочитан (ошибка запроса/схема-дрифт), то любой вердикт **кроме подтверждённого ACTIVE/RESERVED из успешного источника** понижается до `status='неизвестно (нет данных)'`, `kind='unknown'`. То есть телефон, который мы НЕ можем уверенно подтвердить как занятый, при деградации показывается «неизвестно», а НЕ «свободен»/«offline» — мы не отправляем оператора на телефон, который, возможно, ведёт автоматика в упавшем источнике. Подтверждённый «занят» из живого источника остаётся «занят» (это правда и безопасно).

Свежая ACTIVE-задача намеренно бьёт устаревшее offline-показание `device_state` (телефон явно работает).

**Приоритет типов (при нескольких свежих ACTIVE, старший выигрывает):**
`ручная выкладка → автовыкладка → создание аккаунтов → прогрев (аккаунт/телефон) → проверка выложенного`.
(Порядок подтверждён пользователем; offline/свободен/завис вычисляются логикой выше, а не входят в этот список.)

**Анти-дубль.** `publish_queue` транзитно бывает `running`/`dispatched` синхронно с `publish_tasks` — её НЕ читаем как отдельный источник автовыкладки, чтобы не задваивать (источник автовыкладки только `publish_tasks`).

## Конфигурация

- `PHONE_STATUS_STALE_MINUTES` (env, дефолт **10**) — порог зависания ACTIVE-задачи. 10 мин выбрано с запасом: шаги создания аккаунтов/прогрева длинные.
- Интервал поллинга фронта — **7 c** (в коридоре 5–10).

## Бэкенд

Новый `GET /api/devices/status` (`requireAuth`), стиль проекта (`try/catch` + `pool.query`, `res.json`/`res.status(500).json({error})`).

Стратегия запросов: по каждому источнику — один маленький запрос «только ACTIVE/RESERVED строки» (наборы малы — единицы/десятки), плюс запрос реестра телефонов + последний `device_state` на телефон. Сведение в Node через `resolvePhoneStatus`.

**Деградация — fail-closed.** Каждый источник в своём `try/catch`; список упавших источников собирается и передаётся в `resolvePhoneStatus`. Упавший источник НЕ молча отбрасывается: телефоны, которые без него резолвятся в «свободен»/«offline»/«на паузе», понижаются до `неизвестно` (см. правило выше). Эндпоинт всегда отдаёт `200` с полями `degraded`/`failedSources`, чтобы фронт показал предупреждение, но при этом сохранил подтверждённые «занят». (Полный отказ эндпоинта `500` — запасной вариант, если упал сам реестр телефонов или `device_state`.)

Ответ:
```
{ degraded: <bool>, failedSources: [<string>...],
  devices: [{ deviceSerial, deviceNumber, raspberry, host, online, battery,
              status, kind, detail, updatedAt, stale, queuedManual }, ...] }
```

## Фронтенд

Новый под-таб **«Статусы телефонов»** в разделе «Выкладка». Колонки:
- **Телефон** — `#<device_number>`, рядом малинка (`raspberry`).
- **Статус** — бейдж с цветом по `kind`: `free`=зелёный, `busy`=синий/янтарь, `reserved`=серо-янтарный, `stale`=красный, `offline`=серый, `unknown`=красно-серый (предупреждение). Текст — `status`.
- При `degraded=true` — заметный баннер над таблицей: «Часть данных недоступна (источники: …) — статусы «неизвестно» могут скрывать занятость».
- **Подробно** — `detail` (последняя строка лога/шаг).
- **Обновлено** — относительное время от `updatedAt` (+ батарея/онлайн опционально).
- Мелкий индикатор «N в очереди на ручную» при `queuedManual>0`.

Поллинг `setInterval(loadPhoneStatus, 7000)` (как очередь выкладки сейчас 5 c). Сортировка по умолчанию: занятые/завис сверху, свободные снизу.

## Тестирование

- Юнит-тесты `resolvePhoneStatus` (`node --test`, как `test_*.test.js` в проекте): приоритет при нескольких свежих ACTIVE; stale-guard (залипшая running → «завис», не «свободен»); RESERVED (paused) → «на паузе»; offline-vs-свежая-задача; полностью свободен; `queued` мануал не делает «занят»; **fail-closed: при упавшем источнике телефон без подтверждённого ACTIVE → «неизвестно», а подтверждённый «занят» из живого источника остаётся «занят».**
- Лёгкий интеграционный тест `fetchPhoneStatuses` на сидах в 6 таблицах + `device_state` (через live-DB фикстуру проекта, `engine.dispose` паттерн неактуален — это Node/pg).

## Краевые случаи и решения-по-умолчанию (на ревью)

1. **paused-прогрев** → класс RESERVED («на паузе»), не «занят» и не «свободен». _Дефолт; можно слить с «свободен», если операторам так удобнее._
2. **queued-манул** (сотни строк) → НЕ занятость, только счётчик. _Дефолт._
3. **Порог зависания** = 10 мин (env). _Дефолт._
4. **`scheduled`/`pending`** прогревы/задачи → NOT-BUSY (свободен). _Дефолт._
5. **Свежая ACTIVE бьёт offline** из `device_state`. _Дефолт._
6. **Размещение** — под-таб в «Выкладке». _Дефолт; альтернатива — отдельная страница._

## Вне охвата / зафиксировано отдельно

- У `factory_reg_tasks`/прочих task-таблиц нет heartbeat → залипшая `running` лечится stale-guard'ом в самой таблице. Отдельная заметка/задача по решению пользователя НЕ заводится.
