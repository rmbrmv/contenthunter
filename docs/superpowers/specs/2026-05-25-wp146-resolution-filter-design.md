# WP #146 — Фильтр максимального разрешения видео при загрузке в планировщик

- **Дата:** 2026-05-25
- **Задача:** OpenProject #146 «добавить фильтр на макс размер разрешения на уровне загрузки контента в планировщик»
- **Автор задачи:** Анастасия · **Исполнитель:** Данил
- **Репозиторий изменений:** `validator-contenthunter` (backend + frontend)
- **Ветка планирования (этот документ):** `wp146-resolution-filter` в agent-workspace `contenthunter`

## 1. Проблема

Из описания задачи: «после уникализации видео не грузятся в соц сети из-за высокого разрешения; макс 1080×1920». Предложенное решение автора: «не пропускать для загрузки в планировщик контента видео с разрешением более чем 1080×1920».

## 2. Что показала разведка (проверенные факты)

Разбор примера из задачи (unic_task `3683`, файл `f27ff671`):

| Видео | ffprobe | Статус по задаче |
|---|---|---|
| s6 (для 43 телефонов) | **2260×3940** | «не загрузилось» |
| s5 (Art Estate_40) | **2390×4070** | «загрузилось норм» |
| s8 (Art Estate_63) | **2270×3950** | «загрузилось норм» |

**Вывод 1.** Все три ролика негабаритные, причём «хорошие» (s5, s8) **больше** «плохого» (s6). Значит само разрешение — НЕ то, что отличает успех от провала в этом кейсе. Провал именно s6 на 43 телефонах, вероятно, вызван не разрешением, а состоянием аккаунтов/устройств. Этот фикс системно убирает негабарит, но не претендует на объяснение того единичного провала.

**Вывод 2 (корень).** Исходник task 3683 — **2160×3840** (4K-вертикаль, `validator_content.id=2317`). Уникализация лишь добавляет к нему `scale_add` поверх:
- Схема 6: `scale_add=100` → 2160+100 = 2260 ✓
- Схема 5: `scale_add=240` → 2160+240 = 2400 (с учётом pad/crop = 2390) ✓
- Схема 8: `scale_add=110` → 2270 ✓

То есть негабарит на выходе — следствие **негабаритного исходника**, загруженного в планировщик.

**Вывод 3 (рост уникализации).** Чистое изменение размера = `scale_add + pad_add − crop_reduce`. У всех 30 активных схем оно **положительное**, +70…+260 px. Значит даже идеальный исходник 1080×1920 после уникализации станет ~1150–1340 px по ширине — формально за лимитом, но соцсети это принимают (большинство публикаций проходит). Реальные провалы дают именно негабаритные исходники (2K/4K → 2260–2650 на выходе).

**Вывод 4 (масштаб).** В `validator_content` 2014 видео: **65 превышают 1080×1920** (топ: 2160×3840 ×31, 1440×2560 ×30, плюс 1210×2050, 2112×3840, 1080×2046), 226 ровно 1080×1920, 1452 без метаданных (старые).

**Вывод 5 (текущее состояние валидации).** Картинки уже блокируются по размеру (`image_metadata.check_image_blockers`, 1080×1920 / 768×1376 / 1080×1080 ±5%). Видео же проверяется только по аспекту (`width/height ≤ 0.6`), минимальной высоте (≥720, лишь warning) и кодеку — **верхнего предела разрешения нет**. 1080×1920, 1440×2560, 2160×3840 все проходят, т.к. у всех аспект ≈ 0.5625.

## 3. Решение (согласовано с пользователем)

Зеркалим работающий механизм проверки размеров **картинок** на **видео**: при загрузке в планировщик отклонять видео с разрешением выше 1080×1920 (поведение — **жёсткий reject с предупреждением**, как у картинок). Уникализацию (`unic-worker`) НЕ трогаем.

**Параметры (согласованы):**
- `MAX_WIDTH = 1080`, `MAX_HEIGHT = 1920`
- `RESOLUTION_TOLERANCE = 0.05` (±5%, как у картинок) — гасит h264-паддинг (энкодеры выравнивают 1080 до 1088 — кратность 16). Блокер срабатывает при `width > 1080×1.05` **или** `height > 1920×1.05` (т.е. > ~1134×2016).

### 3.1 Backend — `backend/src/services/video_metadata.py`

Добавить константы рядом с существующими (`MIN_HEIGHT` и пр.):
```python
MAX_WIDTH  = 1080
MAX_HEIGHT = 1920
RESOLUTION_TOLERANCE = 0.05   # ±5%; гасит h264-паддинг 1080→1088
```

В `check_technical_blockers()` добавить блокер (после проверки аспекта, чтобы порядок сообщений был логичным):
```python
if meta.width and meta.height:
    if (meta.width  > MAX_WIDTH  * (1 + RESOLUTION_TOLERANCE) or
        meta.height > MAX_HEIGHT * (1 + RESOLUTION_TOLERANCE)):
        blockers.append({
            "code": "resolution_too_high",
            "message": (
                f"Разрешение {meta.width}×{meta.height} превышает максимум "
                f"{MAX_WIDTH}×{MAX_HEIGHT}. Уменьшите разрешение видео до {MAX_WIDTH}×{MAX_HEIGHT}."
            ),
        })
```

Этого достаточно для обоих путей загрузки — `POST /presign→/complete` (`upload.py:98`) и `POST /file` (`upload.py:346`) уже вызывают `check_technical_blockers` и кидают `422 {"blockers": [...]}`. Серверный лог `[complete] technical blockers hit: ...` подхватит новый код автоматически.

### 3.2 Frontend — `frontend/src/components/UploadModal.vue`

В `analyzeVideo()` добавить пункт `max_resolution` в объект `checks` (рядом с `orientation`/`resolution`):
```ts
if (videoLoaded && width > 0 && height > 0) {
  const tol = 1.05
  checks.max_resolution = {
    ok: width <= 1080 * tol && height <= 1920 * tol,
    label: 'Разрешение ≤ 1080×1920',
    detail: `${width}×${height}`,
    hint: (width > 1080 * tol || height > 1920 * tol)
      ? `Видео ${width}×${height} слишком большое. Загрузите в 1080×1920.`
      : undefined,
  }
} else {
  checks.max_resolution = { ok: false, label: 'Разрешение ≤ 1080×1920', detail: 'Не определено', hint: 'Не удалось прочитать метаданные видео' }
}
```

`videoChecksPass` (`Object.values(videoChecks).every(c => c.ok)`) подхватит новый пункт автоматически → кнопка «Загрузить» заблокируется с уже существующим текстом «🚫 Устраните ошибки», красный badge покажется до отправки. Существующую `resolution` (≥720p) проверку оставляем как есть — это нижняя граница, наша проверка верхняя.

> Допуск на бэке и фронте держать **одинаковым** (1.05). Вынести 1080/1920/1.05 во фронтовые константы рядом с `VERTICAL_TARGETS`, чтобы не было «магических чисел» в двух местах.

## 4. Граничные случаи и поведение

| Вход (W×H) | Решение | Почему |
|---|---|---|
| 2160×3840 | **reject** | негабарит (кейс задачи) |
| 1440×2560 | **reject** | негабарит (30 шт в базе) |
| 1210×2050 | **reject** | > 1134 по ширине |
| 1080×1920 | pass | ровно лимит |
| 1088×1920 | pass | h264-паддинг, в пределах ±5% |
| 768×1376 | pass | меньше лимита (валидный 9:16) |
| 1080×2400 (9:20) | **reject** | высота > 2016; осознанное поведение — соцсети ждут ~9:16 |
| null/нечитаемый | без блокера resolution_too_high | dims неизвестны; решают остальные проверки (no_video_stream и т.п.) |

## 5. Вне рамок (явно НЕ делаем)

- **Уникализацию не меняем.** Рост +70…+260 px остаётся; корректный 1080×1920 → ~1150–1340 на выходе (соцсети принимают). Фикс убирает только экстремальный негабарит исходников.
- **Ретро-чистку не делаем.** 65 уже загруженных негабаритных исходников и их `unic_results`/`publish_queue` остаются как есть. При необходимости — отдельная задача на ре-кью/чистку.
- **Авто-даунскейл не делаем** (пользователь выбрал reject, не ужимать).
- Картиночную валидацию не трогаем.

## 6. Тестирование

Backend (`backend/tests/`, pytest, конструируем `VideoMetadata` вручную или мок ffprobe):
- `resolution_too_high` присутствует для 2160×3840, 1440×2560, 1210×2050, 1080×2400.
- Отсутствует для 1080×1920, 1088×1920, 768×1376, и при `width/height = None`.
- Не ломает существующие блокеры (аспект, кодек, длительность, аудио) — прогон существующих тестов `check_technical_blockers`.

Frontend: при наличии тестов на `analyzeVideo` — добавить кейс negabarit→`videoChecksPass=false`. Иначе ручная проверка: загрузить 2160×3840 → красный badge + блок кнопки.

Учесть фикстуру `backend/tests/conftest.py` (engine.dispose) при live-DB тестах — но эти тесты чисто на функцию валидации, БД не нужна.

## 7. Риски и наблюдаемость

- **Ложные reject почти-1080×1920.** Снят допуском ±5%.
- **Старые видео без метаданных (1452).** Блокер не сработает (dims=None) — это касается только новых загрузок, что и требуется.
- **Наблюдаемость:** существующий `log.info("[complete] technical blockers hit: %s")` уже логирует коды; новый `resolution_too_high` будет виден в `validator` логах без доработок.
- **Кросс-репо схема:** изменений схемы БД нет, новые таблицы/колонки не добавляются — кросс-репо grep не требуется.
