# WP #153 — Статистика по ручной выкладке + «потеряно» (design)

- **Дата:** 2026-05-26
- **Ветка:** `wp153-manual-publish-funnel-stats`
- **OpenProject:** WP #153 (статус «В разработке», assignee Данил)
- **Автор задачи:** Анастасия; макет — вложение 36 (`dashboard-funnel-mockup-2026-05-26.html`)

## Проблема

Сейчас не видно, **где** теряется контент на пути к выкладке и **сколько** из всего обрабатывается вручную. Есть только авто-метрика `done/(done+errors)` в TG-отчёте и на дашборде. Ручная выкладка и «потеряшки» нигде не сведены.

## Что делаем (3 части)

1. **Утренний TG-отчёт** — добавить строки: Запланировано / Выложено авто / Выложено вручную / Потеряно (План − всё выложенное) + % ручной выкладки от авто.
2. **Дашборд «Выкладка» (delivery)** — новый блок «Воронка пайплайна» (6 шагов + 2 итоговые колонки + сноски слепых зон) и KPI-плашка «SR итоговый».
3. **Success rate** — собственно плашка «SR итоговый (авто + ручная)» рядом с «SR авто».

Миграции БД **не нужны** — только чтение существующих таблиц.

## Зафиксированные решения (груминг с Данилом, 2026-05-26)

| # | Решение | Выбор |
|---|---------|-------|
| 1 | Якорь даты «План»/«Потеряно» | **Когорта по текущему `slot_date`** в планировщике. Перенос = перепланирование: слот уходит из плана исходного дня (там НЕ «потерян») и попадает в план целевого. |
| 2 | Окно отчёта / in-flight | **Дефолт «Вчера»** (pending/running ≈ 0). Кнопки периодов работают; «Сегодня» честно покажет in-flight (сноска). |
| 3 | Единица счёта воронки | **Уровень публикаций** (строки `publish_queue`), как верхний блок дашборда. |
| 4 | «В ручную» / «% ручной выкладки» | **Только реактивный handoff** (авто упало → оператору, `manual_handoff_at IS NOT NULL`). |
| 5 | «Потеряно» / проактивная ручная | **План = всё запланированное** (вкл. проактивную ручную). «Потеряно» вычитает Авто выложено + **ВСЮ** выложенную вручную (проактив+реактив). |
| 6 | SR авто / «Ошибки» | **Не трогаем** (handoff = провал авто, как сейчас и в TG). «SR итоговый» — отдельная новая метрика. |

Отклонено (YAGNI): хранение исходной плановой даты (когорта по первой дате), разбивка воронки по платформам, source-привязка аккаунтов для «ожидаемых публикаций».

## Архитектура

Единый общий модуль метрик — единственный источник правды, чтобы TG-отчёт и дашборд не разъезжались в числах (известный риск drift в проекте; см. практику mock-proxy/status-agg).

```
pipeline_funnel.js                       (НОВЫЙ модуль autowarm)
  └─ computeFunnel({ pool, fromUtc, toUtc, filters })
       → { plan, uniqualized, autotask, auto_published,
           manual_handoff, manual_handoff_published,
           manual_published_total,
           lost_count, lost_pct, manual_share_pct, sr_total,
           blind_zones: { before_uniq, after_uniq, auto_errors, manual_stuck },
           proactive_manual_published }

server.js  GET /api/publish-queue/dashboard
   → вызывает computeFunnel(slot_date-окно, filters); кладёт в ответ
     блок `funnel` + `overall.sr_total`. Существующие tiles/series — без изменений.

daily_publish_report.js
   → вызывает computeFunnel за «вчера» (slot_date-когорта), добавляет строки в TG.

public/index.html  (section-publishing-dashboard)
   → рендер блока «Воронка пайплайна» + KPI «SR итоговый» (по макету 36).
```

Граница модуля: `computeFunnel` принимает `pool`, UTC-границы окна и объект фильтров (`{ project, platform, account_username, pack_name }`), возвращает чистый объект чисел. Не знает ни про HTTP, ни про Telegram — тестируется изолированно на фикстурах БД.

## Модель воронки (точные определения; проверено на когорте 2026-05-25)

**Когорта** = строки `publish_queue`, у которых текущая дата слота попадает в окно. Якорь = `COALESCE(validator_schedule_slots.slot_date, unic_tasks.slot_date)` — живая дата планировщика (решение «по текущему slot_date»), снапшот `unic_tasks.slot_date` лишь как fallback при удалённом слоте.
Связь: `pq.unic_task_id → unic_tasks.id`, иначе через `pq.unic_result_id → unic_results.task_id → unic_tasks.id`; слот через `unic_tasks.meta->>'slot_id'`. Ручная очередь якорится так же: `COALESCE(s.slot_date, validator_manual_publish_queue.planned_date)` (join по `m.slot_id`), чтобы обе когорты были на одном дне.
Это важно: окно по дате слота (плановый день), **не** по `publish_queue.scheduled_at` (там часто «сейчас+15мин»).

| Шаг / колонка | Определение | 25.05 |
|---|---|---|
| **План** | все строки очереди когорты (вкл. проактивную ручную) | 280 |
| **Уникализировано** | строки с готовым `unic_result` (`status IN ('ready','done')`) | ≈280 |
| **Авто-задача** | строки с `publish_task_id IS NOT NULL` (диспатчнуто на телефон) | 126 |
| **Авто выложено** | `pq.status='done'` | 113 |
| **В ручную (передано)** | реактивный handoff: `pq.manual_handoff_at IS NOT NULL` | 12 |
| **В ручную выложено** (реактив) | из handoff-слотов выложено оператором — по `validator_schedule_slots.matched_post_url` | 9 |
| **Всего выложено вручную** | строки `validator_manual_publish_queue` когорты с `operator_status='published'` (проактив+реактив) | 122 |
| **Потеряно (кол-во)** | `План − Авто выложено − Всего выложено вручную` | 280−113−122 = **45** |
| **Потеряно (%)** | Потеряно / План | 16% |
| **% ручной выкладки** | В ручную (реактив) / Авто-задача = 12/126 | 9.5% |
| **SR итоговый** | (Авто выложено + Всего выложено вручную) / План = 235/280 | 84% |

**Тождество для самопроверки:** `Потеряно% + SR итоговый = 100%`.

### Почему «В ручную выложено» (реактив) считаем по `matched_post_url`

Связь `publish_queue → validator_manual_publish_queue` идёт через `unic_result_id` и является **один-ко-многим** (за 25.05 даёт 21 вместо 12 — задвоение). Поэтому реактивный «выложено вручную» считаем по `validator_schedule_slots.matched_post_url` (1 слот = 1 матч, устойчиво даёт 9). Реактивность определяем по `pq.manual_handoff_at`, **не** по флагу `slot.manual_publish` (флаг грязный: у проактивных слотов встречаются `done` в авто).

### Слепые зоны (сноски под воронкой)

| Зона | Смысл | Источник |
|---|---|---|
| *до постановки в очередь* | слоты в планировщике, не давшие строк очереди (отвал уникализации) | оценочно, уровень слотов (`validator_schedule_slots` без строк `publish_queue`) |
| *после уник., до авто-задачи* | недиспатчнутые строки (переносы / past-slot), кроме проактивной ручной | `Уникализировано − Авто-задача − проактивная_ручная` (от `Уникализировано`, чтобы не досчитывать довуникализационные отвалы — они уже в зоне «до постановки в очередь») |
| *ошибки авто* | `Авто-задача − Авто выложено − реактивный handoff` | — |
| *зависло вручную* | `В ручную передано − В ручную выложено (реактив)` | — |
| *проактивная ручная* | поясняющая сноска: проактивно-ручные успехи (≈113) учтены в «Потеряно» через «Всего выложено вручную», но не показаны в реактивной ветке | — |

## Часть 1 — TG-отчёт (`daily_publish_report.js`)

После существующих per-platform строк SR (якорь `scheduled_at`, **не меняем**) добавляем блок за вчера по `slot_date`-когорте:

```
——— Воронка за {dateLabel} ———
Запланировано: 280
Выложено авто: 113
Выложено вручную: 122
Потеряно: 45 (16%)
Ручная выкладка: 9.5% от авто-задач
```

Сознательная разница якорей (новые строки — `slot_date`, старые SR-строки — `scheduled_at`) фиксируется комментарием в коде и в этом спеке. Kill-switch отчёта (`DAILY_REPORT_ENABLED`) и расписание (09:50 МСК) — без изменений. Деградация: если `computeFunnel` бросил/вернул пусто — блок воронки пропускается, остальной отчёт уходит как раньше (новые строки не должны ронять существующий отчёт).

## Часть 2/3 — Дашборд delivery (`server.js` + `public/index.html`)

- **KPI «SR итоговый»** в блоке «Все задачи авто» — выделенная фиолетовая плашка `(Авто + Ручная) / План`, рядом с «SR авто» (его не трогаем). Бэкенд кладёт `overall.sr_total`.
- **Блок «Воронка пайплайна»** справа от «По платформам» — таблица 6 шагов + 2 итоговые колонки + стрелки слепых зон + строка-сноска, по макету 36. Без разбивки по платформам.
- Фильтры (`project/platform/account_username/pack_name`) и период применяются к воронке через `slot_date`-окно (отдельный `WHERE` от tiles, которые остаются на `scheduled_at`).
- Ответ эндпоинта расширяется обратносовместимо: добавляются ключи `funnel` и `overall.sr_total`; существующие `overall/by_platform/series` не меняются.

## Edge-cases

- **NULL `client_publish_id` / legacy-строки** — попадают в «План», но могут не доходить до поздних шагов → это и есть слепая зона, не замалчиваем.
- **In-flight при «Сегодня»** — pending/running попадут в «Потеряно»; дефолт «Вчера» снимает; для «Сегодня» — сноска.
- **Пустое окно** (нет слотов) — все шаги 0, проценты = `null` (как `computeSuccessRate` сейчас), без деления на ноль.
- **Грязный `manual_publish`** — реактивность только по `manual_handoff_at`.

## Тестирование

- Юнит-тесты `pipeline_funnel.js` на фикстурах БД (паттерн `engine.dispose` из практики validator): каждый шаг, тождество `Потеряно% + SR итоговый = 100%`, реактив vs проактив, пустое окно.
- Регрессионный эталон — реальная когорта 25.05 (План 280 / авто 113 / ручная 122 / Потеряно 45 / SR итоговый 84%).
- Смоук эндпоинта `/api/publish-queue/dashboard` (наличие `funnel`, `overall.sr_total`).
- Визуальная сверка блока дашборда с макетом 36.

## Что НЕ делаем (YAGNI)

- Не храним исходную плановую дату.
- Не трогаем SR авто, «Ошибки», per-platform логику и `scheduled_at`-якорь существующих метрик.
- Не добавляем разбивку воронки по платформам.
- Не строим source-привязку аккаунтов («ожидаемые публикации»).

## Открытые риски

- Точность «слепой зоны до постановки в очередь» — оценочная (слот→публикации фан-аут не хранится). Помечаем в UI как оценку, не как точное число.
- Якорь по `slot_date` для воронки vs `scheduled_at` для SR-строк в одном TG-отчёте — потенциальная путаница; снимаем явными подписями.
