## #119 — Instagram `ig_target_not_in_picker`

### Корневая причина (подтверждена UI-дампами)
На шаге `ig_4_pick_account` Instagram **на переднем плане** (`com.instagram.android`), но открыт **не sheet выбора аккаунта**, а Home Feed / Reels Feed. Доказательства:
- task 9448 — лента Reels (текст «Вы посмотрели все видео Reels…»), распарсенный «список» = `['друзей.']`;
- task 9476 — Home Feed (кнопки «Нравится»/«Комментарий»/«Сохранить», цифры лайков), «список» = `['17','cохраненное','invictus','samal']`.

Гард 21.05 `_ig_guard_picker_foreground` (`account_switcher.py:1710`, вызов `:1872`) проверяет **только foreground-пакет**: если IG → проходит no-op. Поэтому новый честный код `ig_account_switcher_wrong_foreground` (`:1876`) ни разу не появился, а `_find_and_tap_account` (`:4642`) / `read_accounts_list` (`:1288`) слепо скребут ленту → мусор → `ig_target_not_in_picker`.

### Дыра
Между «IG на переднем плане» и «парсим список» нет проверки, что текущий дамп — это **именно sheet переключения аккаунтов**, а не другой экран IG.

### Фикс (выбран: screen-validation + переоткрытие)
Расширить `_ig_guard_picker_foreground`: после подтверждения пакета IG добавить проверку экрана.
- **Позитивный маркер** sheet выбора аккаунта: устойчивый resource-id строк аккаунтов / контейнера sheet (например `com.instagram.android:id/...` — конкретный id выбрать на реальном дампе sheet, см. открытый вопрос).
- **Негативный маркер** (не sheet): наличие engagement-кнопок ленты («Нравится»/«Комментарий»/«Сохранить»/«Поделиться») и/или таб-бара («Дом»/«Reels»/«Профиль»).
- Если **не sheet** → попытаться переоткрыть sheet (повторный tap по header профиля, как при `ig_3_open_list`), N ограниченных попыток.
- При устойчивом неуспехе → fail честным `ig_account_switcher_wrong_foreground` (НЕ `ig_target_not_in_picker`).

Под существующим kill-switch `IG_PICKER_FG_GUARD_ENABLED` (default on). Логировать факт wrong-screen с распарсенным «списком» для дальнейшего триажа.

**Единица:** новый хелпер `_ig_on_account_switcher_sheet(ui_dump) -> bool` (чистая функция над дампом, тестируемая отдельно) + ветка переоткрытия в гарде.

**Отклонённая альтернатива:** только честный код без переоткрытия — проще, но ничего не восстанавливает.

### Тесты
- RU/EN дампы реального sheet → True; дампы Home Feed (9476) и Reels Feed (9448) → False; пустой/битый дамп → безопасный путь (как сейчас при `None`).
- Регресс: happy-path (валидный sheet) проходит без переоткрытия.

### Приёмка
`ig_target_not_in_picker` падает к ~0; остаток (если IG не вернуть на sheet) проявляется честным `ig_account_switcher_wrong_foreground` → корректный триаж.

### Открытый вопрос (для плана)
Снять реальный дамп sheet выбора аккаунта IG (на тестовом телефоне или из артефактов) и зафиксировать **стабильный** позитивный resource-id. До этого опираться на негативные маркеры + отсутствие username-подобного результата.

## #118 — TikTok `tt_upload_confirmation_timeout`

### Корневая причина (подтверждена скринкастом, самопроверено по кадрам)
Публикация **реально проходит**, но детектор подтверждения её не распознаёт — **ложно-негатив** (прямой аналог IG #73). На task 9357:
- события: AI не нашёл кнопку → FALLBACK `(816,2130)` → через 6с XML нашёл реальную кнопку `text='Опубликовать' pos=(798,2103)` и нажал → подтверждение не пришло → watchdog 90с → таймаут;
- кадры скринкаста (≈460с, 700с): на экране пост **«ContentHunter_0 · 1 c. назад»** в ленте (таб «Друзья», нижняя навигация «Главная/Друзья/+/Входящие/Профиль»), поверх — модал **«Пусть вас заметят»** («Мы выбрали ваш аккаунт для участия в программе TikTok Amplify…») с кнопками «Откройте для себя TikTok Amplify» / **«Не сейчас»**.

Плашка Amplify перекрывает экран, цикл ожидания (`UPLOAD_OK`-маркеры ~`publisher_tiktok.py:2127`) её не знает и не видит успех. В событиях плашка **не залогирована** (слепая зона).

Вторичный/неточный режим: 2 из 7 задач (9175, 9606) шли по fallback-координатам и могли быть промахом мимо кнопки — оставляем под наблюдением, не главный режим. (Замечание: ранее озвученное «fallback Y>2100 за экраном» неверно — это разрешение видео 720×1560, устройство 1080×2340, y=2130 валиден.)

### Дыра
Цикл подтверждения ждёт устаревший набор in-editor маркеров и не считает успехом факт выхода в ленту/профиль; post-publish плашка Amplify не гасится; post-publish экран не логируется.

### Фикс (выбран: confirm-by-transition + гашение Amplify + логирование)
В цикле ожидания подтверждения:
1. **Confirm-by-transition:** признать публикацию успешной по факту выхода из композера в ленту/профиль — маркеры нижней навигации («Главная»/«Друзья»/«Входящие»/«Профиль») и/или Activity-переход из композера в Feed/Profile. Паттерн уже валидирован на IG #73.
2. **Гашение плашки:** при обнаружении промо-модала (Amplify «Пусть вас заметят» и т.п.) нажимать «Не сейчас» — чтобы не залипало устройство для следующих задач. Generic-подход (по тексту/кнопке), как SAFE_DISMISS в WP #67 Layer 3.
3. **Логирование:** дампить post-publish экран (категория события вроде `tt_post_publish_screen`) — закрыть слепую зону для будущего триажа.

Под новым kill-switch `TT_PUBLISH_CONFIRM_BY_FEED_ENABLED` (default on) — он покрывает и confirm-by-transition, и гашение промо-модала (один флаг, чтобы откат был атомарным). При успехе по transition — статус `inferred_success` (как в WP #82), а не fail.

**Единица:** хелпер `_tt_on_feed_or_profile(ui_dump) -> bool` + хелпер распознавания/гашения промо-модала; обе — чистые функции над дампом + тонкая обвязка в цикле.

**Отклонённая альтернатива:** только гасить Amplify и ждать старый маркер — хрупко к следующей неизвестной плашке.

### Тесты
- Кадр/дамп post-publish ленты с пост-маркером → confirm success; дамп с плашкой Amplify → распознан + «Не сейчас» нажата; дамп редактора (публикация не стартовала) → НЕ false-positive success (продолжаем ждать/таймаут честно).
- Регресс: обычный happy-path подтверждения не ломается.

### Приёмка
`tt_upload_confirmation_timeout` падает; появляются события `inferred_success` / `tt_post_publish_screen`; устройства не залипают за плашкой Amplify.

### Открытый вопрос (для плана)
Снять точную дамп-сигнатуру (текст/resource-id) плашки Amplify и feed-маркеров — первой задачей плана включить логирование и/или взять дамп, прежде чем хардкодить матч. Перепроверить 9175/9606 (промах vs тот же ложно-негатив).

## #117 — YouTube `yt_editor_upload_timeout`

### Корневая причина (подтверждена событиями task 9628)
Desc-trap-гард 21.05 (`_yt_on_bare_description_screen`, `publisher_youtube.py:239`; срабатывание ~`:1469-1482`) корректно детектит экран «Добавьте описание» и делает `KEYCODE_BACK`, но **BACK с этого экрана не возвращает на форму с «Загрузить»**:
- шаг 11: BACK → профиль канала (не форма);
- шаг 15: повторный BACK → **выход из YouTube в лаунчер**;
- дальше дрейф в камеру/диалоги, AI Unstuck бесполезен → `yt_editor_upload_timeout`.

Гард делает `continue` **без проверки `topResumedActivity`** — в отличие от соседнего stuck-counter'а (`~:1484-1530`), который проверяет, остался ли процесс в YouTube, и при выходе перезапускает `Shell_UploadActivity` (`:1283`). Инфраструктура парсинга `topResumedActivity` уже есть (`:29`).

### Дыра
После BACK гард не верифицирует, что (а) мы всё ещё в YouTube и (б) попали на metadata-форму с «Загрузить». Повторный BACK эскалирует проблему (выход из app).

### Фикс (выбран: post-BACK verify + restart upload activity + cap)
После BACK в desc-trap-гарде:
1. Проверить `topResumedActivity`; если ушли из YouTube → перезапустить `Shell_UploadActivity` (переиспользовать существующий путь из stuck-counter, не дублировать).
2. Ограничить число BACK из ловушки (1–2); дальше — recovery, а не повторный BACK.
3. Сбрасывать `_yt_prev_texts` после escape (сейчас `continue` минует сброс).

Под существующим kill-switch `YT_DESC_TRAP_GUARD_ENABLED` (default on).

**Единица:** правка ветки гарда (≈несколько строк) + переиспользование restart-хелпера stuck-counter'а.

**Отклонённая альтернатива:** только cap BACK=1 и честный fail — не восстанавливает, но проще; берём полный вариант, т.к. restart-путь уже существует рядом.

### Тесты
- После BACK `topResumedActivity` не YouTube → ветка restart вызвана; внутри YouTube → нормальное продолжение; cap BACK соблюдается.
- Регресс: исходный happy desc-trap escape (BACK возвращает на форму) не ломается.

### Приёмка
Слабый сигнал (1 рецидив), поэтому приёмка = **механика починена** (нет ухода в лаунчер по этому пути) + отсутствие рецидива `yt_editor_upload_timeout` с сигнатурой desc-trap на последующих пачках.

## Сквозные правила и риски

- **Kill-switch** на каждое изменение (два существующих + один новый для #118).
- **Тесты** RU/EN + негативные кейсы на реальных дампах/кадрах упавших задач; весь набор платформы зелёный перед PR.
- **Codex-review** спеки и плана до отдачи пользователю; раундами до 0 P1 (практика проекта).
- **Деплой** без рестарта PM2 (per-task spawn); каждый PR независим, порядок выкатки не критичен.
- **Line numbers** в этом доке — снимок 2026-05-25; перед правкой verify через `grep -n` (publisher.py/account_switcher.py быстро растут).
- **Риск ложно-позитива** только у #118 (confirm-by-transition): дамп редактора (публикация не стартовала) НЕ должен распознаваться как success — это негативный тест-кейс.
- **Зависимость:** для #119 и #118 нужно снять реальные дамп-сигнатуры (sheet IG / плашка Amplify) — это первые задачи в плане соответствующего PR.
