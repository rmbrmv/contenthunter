## Проблема

Анастасия сверила воронку за 26.05 с ручными расчётами и по 6 пунктам нашла расхождения. Разбор скриншота (вложение 48) + кода (`pipeline_funnel.js`, `daily_publish_report.js`, `public/index.html`) показал: **расчёты #153 верны и взаимно согласованы — это НЕ ошибки арифметики.** Корень почти всех расхождений один:

> **Воронка ПОКАЗЫВАЕТ только реактивную ветку ручной** (бокс «В ручную» = `manual_handoff` = 29, «В ручную выложено» = `manual_handoff_published` = 25), **а итоговые метрики (Потеряно, SR итоговый) и слепые-зоны СЧИТАЮТ по полной картине** (вся ручная `manual_published_total` = 64, включая 39 невидимых проактивных + диверсии). Поэтому наивная арифметика по видимым боксам не сходится.

### Данные 26.05 (из скриншота, сверено с модулем)

```
ПЛАН 307 · УНИКАЛИЗ. 307 · АВТО-ЗАДАЧА 277 · АВТО ВЫЛОЖЕНО 228
В РУЧНУЮ 29 (хэндофф) · В РУЧНУЮ ВЫЛОЖЕНО 25 (реактив) · ПОТЕРЯНО 15 / 5% · % РУЧНОЙ 11%
Слепые зоны: до постановки 2 · после уник.→авто 20 · ошибки авто 20 · зависло вручную 4
```

Производные модуля: вся ручная = `307 − 228 − 15` = **64**; из них проактив = `64 − 25` = **39**; `proactive_nd` (проактив, не дошедший до авто-задачи) = `uniqualized − autotask − after_uniq` = `307 − 277 − 20` = **10**.

### Разбор всех 6 пунктов

| П. | Жалоба Анастасии | Что считает модуль | Причина | Категория |
|----|------------------|--------------------|---------|-----------|
| 1 | Потеряно = `307−228−25` = 54 (у нас 15) | `307 − 228 − вся ручная 64` = 15 | вычитает видимый реактив (25); 39 проактивных невидимы | подача |
| 2 | после уник. `307−277` = 30 (у нас 20) | `uniq − autotask − proactive_nd(10)` = 20 | 10 ушли в проактив-ручную (не «потеряны до авто») | подача |
| 3 | после автовыкладки `277−228` = 49 (у нас 20) | `autotask − auto − handoff(29)` = 20 | 29 отданы в реактив-ручную (не «ошибки авто») | подача |
| 4 | сноска «не понимаю что значит» | — | формулировка «учтена в «Потеряно»» двусмысленна | текст |
| 5 | Телега ≠ дашборд (52/27/9% vs 25/15/11%) | см. ниже | (а) разные поля под ярлыком; (б) дрейф снимка | подача + пояснение |
| 6 | итоговый SR `(228+25)/307` = 82% vs «на платформе» 95% | `sr_total = (228+64)/307` = **95%** (наша плашка) | те же 39 невидимы; «82%» — её ручной пересчёт | подача |

**Загадка «82 vs 95» разрешена:** 95% — это наши собственные числа (и плашка `SR итоговый`, и старая авто-метрика `done/(done+errors)` ≈ 95% на 26.05 — совпадение знаменателей в этот день). 82% — ручной пересчёт Анастасии по реактивному боксу. Версия брифа («95 = старый авто-SR, 82 = новый») по сути неверна: оба наших числа = 95.

### Детализация п.5 (Телега ≠ дашборд)

- **«выложено вручную» 52 vs 25 = разные поля под одним ярлыком.** TG (`daily_publish_report.js:224`) показывает `manual_published_total` (вся ручная). Дашборд-бокс (`index.html:11943`) — `manual_handoff_published` (только реактив). Это реальная нестыковка ярлыков между поверхностями.
- **Потеряно 27 vs 15, ручная 9% vs 11% = дрейф снимка.** Окна обеих поверхностей считаются одной функцией `slotDateBoundsFromRange` с тем же MSK-сдвигом → для 26.05 границы `slot_date` идентичны (не баг окна/таймзоны). Разница — поздние ручные публикации, докатившиеся между прогоном Телеги (09:50 МСК) и просмотром дашборда (позже). Воронка прошедшего дня **не заморожена**: поздняя ручная докапывается, `manual_published_total` растёт (52→64), `lost` падает (27→15).

## Зафиксированные решения (груминг с Данилом, 2026-05-27)

| # | Вопрос | Решение |
|---|--------|---------|
| A | Пп. 1/2/3/6 — чинить расчёт или менять определения? | **Чинить ПОДАЧУ.** Определения #153 (Потеряно = План − Авто − ВСЯ ручная; SR итоговый по плану; стадии — slot-оценка) оставляем. Делаем проактивную ручную и диверсии видимыми, чтобы видимая воронка сходилась. Расчёт не меняем. |
| B | Какой «итоговый SR» показывать (82 vs 95)? | **Оставить обе метрики, явно подписать.** Заголовочная — `SR итоговый = (авто+ручная)/план`; рядом «Авто success-rate = `done/(done+errors)`» с тултипом «как считается». Разные знаменатели → разойдутся в другие дни. |
| C | Вёрстка ручной на дашборде | **Вариант A:** один бокс «Ручная выложено» = вся ручная (64) с подписью «реактив 25 + проактив 39». Компактно и сразу совпадает с Телегой. |

**Почему не «менять определения» (отклонено):** считать Потеряно/SR только по реактивной выложенной (25) означало бы записать 39 реально опубликованных вручную видео в «Потеряно» — семантически неверно и противоречит согласованной модели #153.

## Архитектура

Все изменения — **слой подачи**. Расчётные формулы `pipeline_funnel.js` не меняются; модуль остаётся единым источником правды для трёх поверхностей (дашборд / TG / фронт). Миграции БД не нужны. Kill-switch `PIPELINE_FUNNEL_ENABLED` уже гейтит всю воронку — нового рубильника не вводим (изменения display-only).

```
pipeline_funnel.js   (autowarm)  — аддитивно вернуть производные для подачи; формулы те же
server.js  GET /api/publish-queue/dashboard — без изменений логики (funnel прокидывается as-is)
daily_publish_report.js — выровнять ярлык ручной + добавить строку SR итоговый + штамп снимка
public/index.html — вариант A боксов, строка-сверка, обогащённые слепые-зоны, 2 подписанные SR, новая сноска, штамп снимка
```

## Изменения по поверхностям

### 1. Модуль `pipeline_funnel.js` (аддитивно, формулы неизменны)

`assembleFunnel` дополнительно возвращает (всё уже вычисляется внутри — просто выносим наружу для подачи):

```js
manual_reactive_published:  manual_handoff_published,            // 25
manual_proactive_published: proactive_manual_published,          // 39 (уже есть, переименование-алиас для ясности подачи — оставить и старое поле)
diversions: {
  before_autotask: proactive_manual_notdispatched,               // 10 — проактив, ушедший мимо авто-задачи
  after_autotask:  manual_handoff,                               // 29 — реактивный хэндофф из авто-задач
},
stage_gaps: {
  after_uniq:     clamp0(uniqualized - autotask),                // 30 — «сырой» разрыв (для подписи «из 30…»)
  after_autotask: clamp0(autotask - auto_published),             // 49 — «сырой» разрыв (для подписи «из 49…»)
},
```

Существующие поля (`manual_published_total`, `lost_count`, `sr_total`, `blind_zones`, `proactive_manual_published`) — без изменений. Обратносовместимо: только добавляем ключи.

**Инвариант-тест (новый):** `auto_published + manual_published_total + lost_count === plan` (при неотрицательном `lost`). Это формальная гарантия «воронка сходится».

### 2. Дашборд `public/index.html` (вариант A)

- **Бокс ручной (вариант A):** заменить «В ручную выложено» (`manual_handoff_published`, 25) на **«Ручная выложено»** = `manual_published_total` (64) с подписью-разбивкой «реактив `manual_reactive_published` + проактив `manual_proactive_published`». Бокс «В ручную» (`manual_handoff`, 29, хэндофф) остаётся как стадия. Это же выравнивает дашборд с Телегой (обе показывают total) — закрывает ярлык-часть п.5.
- **Строка-сверка** под воронкой: `Авто {auto_published} + Ручная {manual_published_total} + Потеряно {lost_count} = План {plan}` с галочкой ✓ при равенстве. Делает п.1/6 самоочевидными.
- **Слепые-зоны с диверсиями** (обогащаем подписи, числа из `stage_gaps`/`diversions`):
  - «после уник. → авто-задача — {after_uniq} *(из {stage_gaps.after_uniq}: {diversions.before_autotask} → проактив-ручная)*» → «20 (из 30: 10 → проактив-ручная)» (п.2)
  - «ошибки авто — {auto_errors} *(из {stage_gaps.after_autotask}: {diversions.after_autotask} → хэндофф в ручную)*» → «20 (из 49: 29 → хэндофф)» (п.3)
- **Две SR явно подписать (решение B):** оставить плашку **«SR итоговый»** = `sr_total` (заголовочная, фиолетовая) + рядом **«Авто success-rate»** = `overall.success_rate` (`done/(done+errors)`). Тултип на каждой: формула простыми словами. Снимает п.6 как «почему два числа».
- **Сноска (п.4)** — переписать (см. ниже).
- **Штамп снимка:** «на момент HH:MM МСК {дата}» под блоком — объясняет дрейф п.5 (число живёт, пока докатывается поздняя ручная).

### 3. TG-отчёт `daily_publish_report.js`

- **Ярлык «Выложено вручную»** = total (как сейчас) + разбивка «(реактив N + проактив M)» — чтобы дословно совпадало с дашбордом (ярлык-часть п.5).
- **Добавить строку «SR итоговый: {sr_total}»** — сейчас её в TG нет (есть только Потеряно и % ручной); паритет с дашбордом.
- **Штамп снимка** «(на 09:50 МСК)» в шапке блока воронки.

### Новая формулировка сноски (п.4)

Текущая (двусмысленная): _«Проактивная ручная (≈39) учтена в «Потеряно», но не в реактивной ветке.»_

Новая:
> «Проактивная ручная ({manual_proactive_published}) — слоты, опубликованные оператором без авто-задачи; засчитаны как **выполненные** (вошли в «Ручная выложено» и **вычтены** из «Потеряно»), но проходят мимо реактивной ветки воронки. «Потеряно» за сегодня может включать ещё не завершённые публикации; число прошедшего дня уточняется по мере докатывания поздней ручной.»

## Edge-cases

- **Пустое окно** — все производные 0/`null`, как сейчас; деления на ноль нет.
- **Клампы** — `clamp0` на `stage_gaps`/`diversions`: при экзотических данных (вычитаемое > уменьшаемого) подпись «из X: Y → …» не даёт отрицательных; если `Y > X` после клампа — подпись скрывается (защита от бессмыслицы).
- **Kill-switch** `PIPELINE_FUNNEL_ENABLED=0` — весь блок (включая новые поля/подписи) гаснет как раньше; TG/дашборд деградируют штатно.
- **Совпадение знаменателей** SR-итоговый ≈ Авто-SR на 26.05 — не зашивать как факт; обе считаются независимо и подписаны раздельно.

## Тестирование

- Юнит `pipeline_funnel.js`: новые поля (`manual_reactive/proactive_published`, `diversions`, `stage_gaps`) на фикстуре 26.05 (307/277/228/29/25/64/39/10); **инвариант** `auto + manual_total + lost == plan`; регрессия эталона 25.05 из #153 (280/113/122/45/84%) — не сломать.
- Смоук `/api/publish-queue/dashboard`: новые ключи присутствуют, `overall.sr_total` и `overall.success_rate` оба не `null`.
- Сверка TG (dry-run): строка SR итоговый + разбивка ручной + штамп.
- Визуальная сверка дашборда: вариант A, строка-сверка сходится, две подписанные SR, новая сноска.

## Что НЕ делаем (YAGNI)

- Не меняем расчётные формулы #153 (Потеряно/SR/стадии/якорь slot_date).
- Не трогаем `scheduled_at`-якорь старых per-platform SR-строк.
- Не вводим новый kill-switch (изменения display-only под существующим `PIPELINE_FUNNEL_ENABLED`).
- Не «замораживаем» воронку прошедшего дня (дрейф — ожидаемое поведение, объясняем штампом, а не убираем).
- Не делаем разбивку воронки по платформам / source-привязку.
