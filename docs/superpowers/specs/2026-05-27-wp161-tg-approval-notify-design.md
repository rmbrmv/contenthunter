# WP#161 — Telegram-уведомления: ролики на одобрении / отсутствие контента

**Дата:** 2026-05-27
**OpenProject:** #161 (статус «В разработке», исполнитель Данил)
**Ветка кода:** autowarm-репо (`workspace-genri/autowarm`), реализация отдельной веткой
**Ветка документации:** `wp161-tg-approval-notify` (репо contenthunter)

## 1. Проблема

Аня пропускает ролики, ожидающие ручного одобрения, и клиентов без загруженного контента. Из-за этого выкладка стартует с опозданием на день. Нужна регулярная Telegram-сводка, которая делает оба пробела видимыми.

## 2. Цель

Раз в час (в рабочее окно) присылать в Telegram-тред сводку из двух блоков:
1. **На одобрении сейчас** — сколько роликов ждут ручного одобрения и у каких клиентов, с плановыми датами выкладки.
2. **Контент не загружен** — у каких клиентов на завтра и послезавтра есть пустые слоты в расписании.

## 3. Зафиксированные продуктовые решения

Развилки ТЗ закрыты автором (Данил) на брейншторме 2026-05-27:

| Развилка | Решение |
|---|---|
| **Адресат** | Тред группы «Модерация и уникал»: `t.me/c/3262248975/10477` → `chat_id = -1003262248975`, `message_thread_id = 10477` |
| **Бот** | Переиспользуем `@gengo_tech_notify_1_bot` (он уже шлёт ежедневный отчёт WP#114 и умеет постить в тред) |
| **Каденция** | Раз в час |
| **Окно отправки** | 09:00–18:00 МСК (макс. 10 сообщений/день) |
| **Пустые часы** | Если оба списка пусты — в этот час **не шлём** ничего |
| **«На одобрении»** | Только `validator_content.status = 'needs_review'` (контент, который авто-модерация отправила на ручной свайп) |
| **«Контент не загружен»** | Пустые слоты в расписании: `validator_schedule_slots` с `content_id IS NULL` или `status = 'empty'` на завтра+послезавтра, по активным проектам |

## 4. Архитектура

Подход — **отдельный модуль по образцу `daily_publish_report.js`** (WP#114). Это проверенный в проде паттерн: `setInterval`-тик, env-конфиг, идемпотентность через таблицу-claim, ретраи, kill-switch. Альтернативы отклонены: расширять `daily_publish_report.js` — смешение разных сущностей и риск для рабочего модуля; cron/systemd — вразрез с тем, как в проекте устроены расписания (self-managed `setInterval` внутри autowarm-процесса) и с деплой-ограничениями (PM2, не systemd).

### Компоненты (autowarm-репо)

- **`approval_notify.js`** — новый модуль:
  - `startApprovalNotifyCron(pool)` — `setInterval` 60 сек; раз в начале каждого часа в окне 09–18 МСК пытается заклеймить час и отправить.
  - `buildApprovalSummary(pool)` — выполняет SQL (см. §5), возвращает `{ pendingApproval: [...], emptySlots: [...] }`.
  - `formatMessage(summary)` — **чистая функция**, собирает HTML-текст (см. §6).
- **`telegram_send.js`** — небольшой общий хелпер: escape HTML + `POST sendMessage` (с `message_thread_id`) + 3 ретрая с экспоненциальным бэкоффом. Новый модуль использует его.
- Регистрация в **`server.js`** при старте — вызов `startApprovalNotifyCron(pool)` рядом с существующим `startDailyReportCron(pool)`.

Существующий `daily_publish_report.js` **не изменяем** (YAGNI на рефакторинг рабочего кода; общий хелпер используется только новым модулем).

### Данные

Одна БД `openclaw` (Docker-контейнер) содержит и `validator_*`, и `publish_queue` → нотификатор обходится **одним SQL** на блок, без кросс-БД.

## 5. Запросы (имена колонок верифицированы по схеме валидатора)

**Блок 1 — «На одобрении» (`needs_review`):**

Один ролик может быть привязан к нескольким слотам (на `content_id` нет уникального ограничения — `uq_slot` стоит на `project_id, slot_date, slot_position`). Поэтому даты агрегируем **на уровне ролика** через `GROUP BY vc.id`, чтобы `LEFT JOIN` не размножал строки и не задваивал счётчик:

```sql
SELECT vp.project AS client,
       vc.id AS content_id,
       array_agg(to_char(s.slot_date, 'YYYY-MM-DD') ORDER BY s.slot_date)
         FILTER (WHERE s.slot_date IS NOT NULL) AS slot_dates
FROM validator_content vc
JOIN validator_projects vp ON vp.id = vc.project_id
LEFT JOIN validator_schedule_slots s ON s.content_id = vc.id
WHERE vc.status = 'needs_review'
GROUP BY vp.project, vc.id
ORDER BY vp.project, vc.id;
```

Даты форматируются в SQL текстом `YYYY-MM-DD` (сортируемо лексикографически = хронологически; обходит tz-парсинг `DATE` в node-pg). `FILTER (WHERE … IS NOT NULL)` даёт `NULL` (→ пустой массив в JS), если у ролика нет слота.

Обработка в коде: ровно **одна строка на ролик** (`N` = число строк = число различных роликов `needs_review`). Для вывода группируем по `client`: объединяем `slot_dates` всех роликов клиента → дедуп (`Set`) → сортировка (лексикографическая по ISO) → формат `DD.MM` → склейка через запятую. Если у клиента нет ни одной даты — пометка «дата не назначена».

**Блок 2 — «Контент не загружен» (завтра + послезавтра):**

```sql
SELECT DISTINCT vp.project AS client
FROM validator_schedule_slots s
JOIN validator_projects vp ON vp.id = s.project_id
WHERE s.slot_date IN (:tomorrow, :day_after)
  AND (s.content_id IS NULL OR s.status = 'empty')
  AND vp.active = true
ORDER BY vp.project;
```

`:tomorrow` и `:day_after` вычисляются как `current_date + 1` и `current_date + 2` в зоне `Europe/Moscow` (как в ежедневном отчёте). `M` = число клиентов.

**Верифицированные факты схемы:**
- `validator_content.project_id` (Integer, NOT NULL); `ContentStatus.needs_review = 'needs_review'`.
- `validator_schedule_slots`: `project_id`, `slot_date` (Date), `content_id` (nullable FK → `validator_content.id`), `status` (enum `SlotStatus`, дефолт `empty`).
- `validator_projects`: `project` (имя клиента), `active` (bool).

## 6. Формат сообщения (HTML в тред)

```
🎬 На одобрении: 3 ролика
• Клиент A — 28.05, 29.05
• Клиент B — 28.05
• Клиент C — дата не назначена

📭 Контент не загружен на завтра/послезавтра (2):
Клиент 1, Клиент 2
```

Правила формата:
- Блок показывается только если в нём есть строки; если пусты оба блока — сообщение не отправляется (см. §7).
- Числительное «ролик/ролика/роликов» и «клиент/клиента/клиентов» согласуются по числу.
- Имена клиентов HTML-escape'ятся (`<`, `>`, `&`) перед вставкой.
- Даты в формате `DD.MM` (МСК).

## 7. Расписание, идемпотентность, надёжность

- **Тик:** `setInterval` каждые 60 сек. На каждом тике: если текущий час в окне `[09, 18]` МСК (включительно) — пробуем отправку для текущего часового бакета. Один сенд в час гарантирует не минутная проверка, а per-hour claim (ниже), что заодно даёт catch-up, если процесс стартовал посреди часа.
- **Пустые часы:** сводку строим **до** claim. Если `pendingApproval` и `emptySlots` оба пусты и `APPROVAL_NOTIFY_SUPPRESS_EMPTY != '0'` — выходим без claim и без отправки (строка в журнале не создаётся; следующий тик в этом часе дёшево перепроверит). In-process `_running`-guard не даёт перекрытия тиков внутри процесса.
- **Идемпотентность:** таблица **`approval_notify_runs`** с уникальным ключом `report_hour TIMESTAMPTZ` (начало текущего UTC-часа; границы UTC-часа совпадают с МСК, т.к. МСК=UTC+3 без DST). Claim делаем только для непустых часов: `INSERT ... ON CONFLICT (report_hour)` с `status` (`sending`/`sent`/`failed`), `attempts`, `claimed_at`. Апсёрт защищает от двойной отправки при рестарте/двойном тике/нескольких процессах; staleness-recovery 10 мин (как у `daily_report_runs`).
- **Ретраи:** до 3 попыток `sendMessage` с бэкоффом `2^n * 1000 мс`.
- **Зона/окно:** все часовые расчёты в `Europe/Moscow`.

## 8. Миграция

Таблица `approval_notify_runs` создаётся миграцией в `<autowarm-репо>/migrations/` (правило проекта: код, читающий/пишущий таблицу, сопровождается миграцией). Миграция идемпотентна (`CREATE TABLE IF NOT EXISTS`).

## 9. Конфигурация (env)

| Переменная | Назначение | Дефолт |
|---|---|---|
| `APPROVAL_NOTIFY_ENABLED` | Kill-switch; `'0'` отключает крон целиком | вкл |
| `APPROVAL_NOTIFY_BOT_TOKEN` | Токен бота `@gengo_tech_notify_1_bot` | — (обяз.) |
| `APPROVAL_NOTIFY_CHAT_ID` | Целевой чат | `-1003262248975` |
| `APPROVAL_NOTIFY_THREAD_ID` | `message_thread_id` топика | `10477` |

## 10. Тестирование (TDD)

- **`formatMessage` (чистая функция):** unit-тесты на форматирование — оба блока непусты; только один блок; «дата не назначена»; склонение числительных; HTML-escape имён. Без БД.
- **`buildApprovalSummary`:** тест с фейковым `pool` (мок-результаты двух запросов) или seeded-набором → проверка группировки и сбора дат. Изоляция БД по правилам проекта (не мутировать прод-таблицы).
- **Окно/идемпотентность:** unit на логику «час в окне», «первый тик часа», «пустой час → skip».
- Стиль и раннер — как у существующих autowarm-тестов (`node --test`).

## 11. Предусловия и риски

- **Предусловие:** бот `@gengo_tech_notify_1_bot` должен состоять в группе `-1003262248975` и иметь доступ к топику `10477`. Проверить на этапе деплоя пробной отправкой.
- **Риск шума:** даже с окном 09–18 и подавлением пустых часов почасовая каденция может оказаться шумной. Митигация: kill-switch и легко изменяемое окно через env; при необходимости перейти на 3×/день — точечное изменение `APPROVAL_NOTIFY_WINDOW`/логики без переписывания.
- **Риск дублей при рестартах:** покрыт claim-таблицей.
- **`needs_review` без слота:** ролик на одобрении может быть не привязан к слоту → показываем «дата не назначена», не теряем его из счётчика.

## 12. Деплой и kill-switch

- Деплой в рамках PM2 (не systemd); код в autowarm-репо, прод подтягивает изменения (см. правила деплоя проекта).
- Мгновенный откат: `APPROVAL_NOTIFY_ENABLED='0'` в прод-`.env` (крон не запускает отправку).

## 13. Вне scope (YAGNI)

- Гибридная каденция / внеплановые пинги по новому контенту.
- Включение в сводку не-`needs_review` статусов (pending-модерация, uploading).
- Кнопки/диплинки на одобрение в сообщении.
- Рефакторинг `daily_publish_report.js` под общий хелпер (хелпер используется только новым модулем).
