# WP #44 — Добивка тегов в описание публикаций (design spec)

- **Дата:** 2026-05-25
- **Задача:** OpenProject #44 «Выкладка (добавить теги в описание)» (проект Content Hunter)
- **Статус:** дизайн согласован с заказчиком (Данил), готов к написанию плана
- **Ветка:** `wp44-publish-tags-in-description`

---

## 1. Контекст и проблема

Задача из трёх пунктов (автор — Анастасия):

1. Теги из планировщика добавлять к описанию публикаций.
2. Если клиент указал меньше 5 тегов — добирать «парочку» из «распаковки», желательно рандомайзером (одни и те же теги изо дня в день IG/TT не любят).
3. Проверить формирование текста описания в автовыкладке: у клиента «Еноты по полкам» в опубликованном тексте видны литеральные подписи «Теги:» / «описание» (телефон 66, TikTok).

## 2. Что выяснили (текущее поведение)

Источник тегов и описания — таблица `validator_content` (общая БД `openclaw`):
- `description` (text, ≤2200) — описание;
- `hashtags` (jsonb, ≤5) — структурные теги из планировщика (вкладка «Хэштеги» в карточке контента).

Сборка текста публикации происходит в autowarm (`server.js`) **ровно в двух местах**:
- `assignUnicResultsToQueue` (~6452/6456) — авто-очередь;
- ручной endpoint постановки в очередь (~2380/2383).

Поведение по платформам:
- **IG / TikTok:** `caption = описание + "\n\n" + "#тег1 #тег2 …"`; в `publish_queue.hashtags` массив тоже пишется, но диспетчер при создании `publish_tasks` ставит `hashtags=[]` (теги уже внутри caption).
- **YouTube:** `caption = заголовок (title)`; описание идёт в `publish_queue.content_description`, теги — в `publish_queue.hashtags`. Диспетчер пробрасывает их в `publish_tasks`, а `publisher_youtube.py` (≈1597-1600) дописывает `#теги` в **поле описания** видео: `описание + "\n\n" + "#теги"`.

Проверка реальных данных подтвердила:
- свежий контент Енотов (2026-05-22) публикуется чисто: `#школапокера #shorts #ютубшортс …` добавляются корректно;
- литерал «Теги:» из пункта 3 лежит **в самом поле `description`** (контент id 2256, 2026-05-20) — его вписал клиент вручную. Код autowarm подпись «Теги:» нигде не добавляет.

«Распаковка» = бренд-профиль `validator_brand_profiles` (по `project_id`), поле `keywords` (jsonb-массив). Логики добивки тегов сейчас нет вообще.

**Важно по формату keywords:** в распаковке это в основном многословные фразы («уход за кожей», «купить квартиру спб», «longevity movement Dubai»), а не готовые хэштеги.

## 3. Решения заказчика

| Вопрос | Решение |
|---|---|
| Пункт 3 (ugly-блок «Теги:») | Случайная ошибка клиента — **код не трогаем**, из задачи снято. |
| Источник добивки | `validator_brand_profiles.keywords` (распаковка), случайно добирать **до 5**. |
| Где разместить логику | В **autowarm**, при сборке caption (исходный контент в валидаторе не трогаем). |
| Платформы | Все три (IG / TikTok / YouTube). Для YT теги пишутся в поле описания. |
| Нормализация фраз | Склейка слов без пробелов, lowercase, без пунктуации (как уже сделаны теги клиента: `школапокера`, `енотыпополкам`). |
| Рандомизация | На каждую публикацию (per строка очереди) — набор отличается день ото дня. |

## 4. Scope

**Входит:**
- Обогащение массива тегов перед сборкой caption: клиентские теги + случайная добивка из keywords бренда до 5, когда у контента < 5 тегов.
- Нормализация keyword → валидный хэштег.
- Единое поведение для IG / TikTok / YouTube.

**Не входит:**
- Любая обработка/чистка ugly-блока «Теги:» в описании (пункт 3 снят).
- Изменения в валидаторе и его UI.
- Изменение данных `validator_content`.

## 5. Дизайн

### 5.1. Ключевой принцип — одна точка

Вся фича сводится к **обогащению массива `hashtags` ДО сборки caption**. Существующий код дальше раскладывает теги правильно сам:
- IG/TT — обогащённый массив идёт в строку `#теги` внутри caption;
- YT — обогащённый массив идёт в `publish_queue.hashtags` → публикатор дописывает в поле описания.

Значит правка точечная: там, где сейчас `contentHashtags` превращается в финальный набор, подставляем результат `enrichHashtags(...)`.

### 5.2. Помощник `enrichHashtags(clientTags, brandKeywords, opts)`

Чистая функция (без обращения к БД), легко тестируется.

Сигнатура (JS):
```
enrichHashtags(clientTags: string[], brandKeywords: string[], {
  target = 5,
  maxLen = 30,
  shuffle = defaultShuffle,   // инъекция для детерминированных тестов
}) -> string[]
```

Алгоритм:
1. **Нормализуем клиентские теги:** убрать ведущий `#`, `trim`, отбросить пустые, дедуп (без учёта регистра). Клиентские теги сохраняем как ввёл клиент (не калечим), только без `#`.
2. Если получилось `>= target` — вернуть как есть (за keywords в БД **не ходим**).
3. Иначе строим **пул кандидатов** из `brandKeywords`:
   - для каждого keyword: `trim` → убрать ведущий `#` → `lowercase` → удалить всё кроме букв/цифр/`_` (regex `/[^\p{L}\p{N}_]/gu`, флаг `u`);
   - отбросить пустые после нормализации и длиннее `maxLen` (30);
   - отбросить дубли (без учёта регистра) уже выбранных тегов и других кандидатов.
4. `shuffle(пул)`, взять первые `target - clientCount`, добавить к результату.
5. Вернуть итог (≤ target, но если keywords не хватило — может остаться < target).

### 5.3. Получение keywords и рандомизация

- Хелпер `getBrandKeywords(pool, projectId) -> string[]` — один лёгкий запрос `SELECT keywords FROM validator_brand_profiles WHERE project_id=$1`; пусто/нет профиля → `[]`.
- В `assignUnicResultsToQueue` keywords тянем **один раз на проект** (мемоизация `Map<projectId, string[]>` в рамках вызова), чтобы не делать запрос на каждую строку.
- `enrichHashtags(...)` вызывается **на каждую строку очереди** (per аккаунт) → рандом отрабатывает заново → разные наборы у разных публикаций/дней.

### 5.4. Точки внедрения (`server.js`)

- `assignUnicResultsToQueue` (~6452/6456): `const finalHashtags = enrichHashtags(contentHashtags, brandKeywords); ` затем `finalHashtags` используется и для строки caption (IG/TT), и как `hashtags` (YT).
- Ручной endpoint (~2380/2383): то же для одиночной постановки.
- План реализации обязан **проверить всех producer'ов `publish_queue`** (включая slot/backfill/carousel-пути, где есть SELECT `content_hashtags` на строках ~2171/2215, ~5367, ~6208) и убедиться, что ни один не обходит обогащение либо осознанно исключён.

### 5.5. Поведение по платформам (после правки)

- **IG / TikTok:** `caption = описание + "\n\n" + #(finalHashtags)`.
- **YouTube:** `title = заголовок`; поле описания = `описание + "\n\n" + #(finalHashtags)` (через существующий публикатор).

## 6. Граничные случаи

- Нет бренд-профиля / `keywords` пустой → возвращаем клиентские теги как есть (тихо, без падения).
- keywords меньше, чем нужно для добивки → добираем сколько есть (может остаться < 5).
- keyword после нормализации дублирует клиентский тег → пропускаем.
- У контента уже ≥ 5 тегов → ничего не добавляем, в БД за keywords не ходим.
- keyword нормализуется в пустую строку (только пунктуация) или > 30 символов → пропускаем.

## 7. Kill-switch и конфигурация (домашняя практика)

- `PUBLISH_TAG_FILL_ENABLED` (по умолчанию `1`/вкл) — глобальный выключатель добивки. Выкл → поведение как сейчас (только клиентские теги).
- `PUBLISH_TAG_FILL_TARGET` (по умолчанию `5`) — целевое число тегов.
- `PUBLISH_TAG_FILL_MAXLEN` (по умолчанию `30`) — максимальная длина добираемого тега.

## 8. Тестирование

Юнит-тесты `node --test` на `enrichHashtags` (детерминированно через инъекцию `shuffle`):
- < 5 клиентских тегов → добивка до 5 из keywords;
- ровно/больше 5 тегов → без изменений, keywords не запрашиваются;
- многословный keyword → корректный склеенный тег;
- дедуп: keyword, совпадающий с клиентским тегом (разный регистр) → пропуск;
- пустой/отсутствующий пул keywords → клиентские теги как есть;
- keywords меньше потребности → частичная добивка;
- слишком длинный / пустой-после-нормализации keyword → пропуск;
- kill-switch выключен → поведение без добивки.

Лёгкий интеграционный smoke на `getBrandKeywords` (реальный проект с keywords) — по живой БД, аккуратно (см. практику чистки zombie node --test процессов).

## 9. Риски и заметки

- Несколько producer'ов `publish_queue` — главный риск пропустить путь; закрывается аудитом в плане (см. 5.4).
- Качество добранных тегов зависит от качества keywords в распаковке; для «бедных» профилей добивка частичная — это ожидаемо.
- Рандом на каждую строку = у разных аккаунтов одного ролика могут быть разные добранные теги; это приемлемо и даже полезно для разнообразия.
