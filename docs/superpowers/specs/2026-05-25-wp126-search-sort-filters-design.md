# WP #126 — Поиск, единая сортировка и мультивыбор в фильтрах (delivery + client)

- **OpenProject:** [WP #126](https://openproject.contenthunter.ru/work_packages/126) «Добавить поиск к фильтру по клиенту/проекту/телефону»
- **Дата:** 2026-05-25
- **Ветка:** `wp126-search-sort-filters`
- **Приоритет:** Низкий
- **Статус:** В разработке

## 1. Проблема и цель

Фильтры по клиенту/проекту/телефону в обоих фронтах — это голые нативные `<select>`. Из них вытекают три боли пользователя (из описания WP):

1. **Нет поиска.** Чтобы найти нужный проект/телефон в длинном списке, приходится глазами вычитывать весь список (нативный type-ahead неудобен и непредсказуем).
2. **Сортировка не единая.** Где-то опции в порядке прихода из API, где-то по алфавиту; на клиентском дашборде латиница (`Boris Kostin Real Estate`) и мусор (`--status`) перемешаны с кириллицей (см. скриншот img19).
3. **Нет мультивыбора.** Нельзя отфильтровать сразу по нескольким проектам/телефонам.

**Цель:** во всех перечисленных фильтрах — поиск по подстроке, единая алфавитная сортировка и мультивыбор там, где это осмысленно.

**Исключения из мультивыбора** (явно от пользователя): страницы «Уникализация» (`/client/schemes`) и «Мой пакет» (`/client/contract`) — там остаётся одиночный выбор.

## 2. Затронутые системы

Задача охватывает **два независимых фронта в разных репозиториях**:

| Фронт | URL | Репозиторий / чекаут | Стек |
|---|---|---|---|
| **delivery** (менеджерский) | delivery.contenthunter.ru | `GenGo2/delivery-contenthunter`; dev-чекаут `/home/claude-user/autowarm-testbench/`, прод `/root/.openclaw/workspace-genri/autowarm/` | vanilla JS, единый `public/index.html` (~14.4k строк), без сборки |
| **client** (кабинет клиента) | client.contenthunter.ru | `/home/claude-user/validator-contenthunter/` | Vue 3.4 + Tailwind 3.4 + Pinia, **без UI-библиотеки**, Vite-сборка |

Готового searchable / multi-select компонента нет ни там, ни там.

## 3. Решение по фазам

Реализация **последовательная, один общий spec**. Сначала delivery (Фаза 1, приоритет), потом client (Фаза 2). Разведка кода показала, что в delivery серверно фильтруют все 4 не-ручные страницы → мультивыбор тянет правку 4 эндпоинтов. Поэтому Фаза 1 делится на два независимо отгружаемых среза:

- **Фаза 1a — delivery: поиск + единая сортировка (одиночный выбор), только фронт.** Виджет `makeSearchSelect()` + сортировка на всех 5 страницах; каждый виджет вызывает существующий одиночный обработчик. Бэкенд не трогаем — низкий риск, закрывает 2 из 3 требований. **Это первый план/PR.**
- **Фаза 1b — delivery: мультивыбор.** Виджет переключается в `multi:true` + обратно-совместимая правка 4 серверных эндпоинтов (список значений) + клиентский мульти на Ручной выкладке. Отдельный план/PR после 1a.
- **Фаза 2 — client.** Компонент `SearchableSelect.vue` + замена 7 селекторов проекта + правки validator-бэкенда под список `project_id` для 5 страниц с мультивыбором (2 — одиночные). Отдельный PR.

Текущий шаг — implementation plan для **Фазы 1a**.

Каждая фаза имеет свой implementation plan (следующий шаг — `writing-plans` для Фазы 1).

## 4. Архитектура: переиспользуемый searchable-dropdown

**Выбранный подход:** свой мини-виджет в каждом фронте (без новых зависимостей и без библиотек). Альтернативы (минимальный апгрейд нативного `<select>`; готовая либа типа Tom Select) отклонены: первая не даёт поиска (главное требование), вторая тянет зависимость в single-file vanilla и в «Vue без UI-либы».

### 4.1 Единое поведение (контракт виджета, общий для обоих фронтов)

- **Триггер** показывает состояние: `все` / имя выбранного / `выбрано: N`.
- **Всплывашка:** поле поиска (фильтр по подстроке, регистронезависимо) → прокручиваемый список опций.
  - **Single:** клик по опции выбирает и закрывает.
  - **Multi:** чекбоксы; строки-действия «Все» / «Сбросить»; **применение фильтра при закрытии всплывашки** (а не по каждому клику) — критично для серверных фильтров, чтобы не слать запрос на каждый чек.
- **Пин `все`/`Все проекты`** всегда первой строкой, не участвует в алфавитной сортировке.
- Закрытие по клику вне виджета и по Esc; доступность с клавиатуры — best-effort (стрелки/Enter), не блокер.

### 4.2 Правило сортировки (единое везде)

Чистая функция сравнения по отображаемому имени:

```
localeCompare(b, 'ru', { sensitivity: 'base', numeric: true })
```

- регистронезависимо; кириллица/латиница — естественный RU-порядок;
- `numeric: true` → телефоны и нумерованные паки сортируются «по-человечески» (№2 раньше №10);
- **без хостинга выбранного наверх** — чистый алфавит, предсказуемо (чинит мешанину из img19);
- сентинел `все` пинится первым отдельно от сортировки.

Эта функция выносится в тестируемый модуль в каждом фронте.

### 4.3 Семантика мультивыбора

Мультивыбор фильтра = **OR**: «показать строки по любому из выбранных значений». Пустой выбор = `все` (без фильтра). По месту фильтрации:

- **Клиентская фильтрация (без бэкенда):** строки уже на клиенте — фильтруем массив по `value ∈ selectedSet`. В delivery это **только Ручная выкладка** (`mpqApply`).
- **Серверная фильтрация (нужен API под массив):** эндпоинт учится принимать список значений. Обратная совместимость: одиночный параметр продолжает работать (старые вызовы не ломаются). В delivery так фильтруют **Запланировано, Опубликовано, Планировщик и Дашборд** (все через серверный запрос; разведка кода 2026-05-25 это подтвердила — Tabulator-предположение оказалось неверным).

На клиентском кабинете мультивыбор означает **агрегацию данных по нескольким проектам** (аналитика/публикации/аккаунты суммируются по выбранному набору) — это сознательное изменение бэкенда, согласовано.

### 5.1 Матрица страниц

> **Важно (разведка 2026-05-25):** в delivery серверно фильтруют **все 4** не-ручные страницы (а не только Планировщик). Планировщик фильтрует по числовому `project_id` (список из `/api/validator/projects` = `{project_id, project_name}`), остальные — по строковому **имени** проекта (`/api/publish/queue/projects`). Виджет принимает опции как `{value, label}` и обе схемы переваривает.

### 5.2 Точки интеграции (по факту кода 2026-05-25)

- **Ручная выкладка:** `MPQ_COLS` (12095), `mpqFilterCell()` (12165, ветка `select` на 12187), `mpqMatch()` (12149), `mpqApply()` (12157), `mpqRenderHead()` (12258), состояние в `mpqFilters` (12083). Заменяем `select`-ветку на host-плейсхолдер, монтируем виджет после `mpqRenderHead`; в `mpqMatch` фильтр select становится «значение ∈ множество».
- **Запланировано:** `<select id="up-project-select">` (index.html:2430), наполнение `loadQueueProjects()` (11404), фильтр `upColFilter()` (11391) → `_upqTable.setFilter` → серверный параметр через `upqMapFiltersToServer` (11064); сброс `upClearFilters()` (11395). Сервер: `buildPublishQueueFilters` (server.js:1900/1918) — `project = $?`.
- **Опубликовано:** `<select id="upt-project-select">` (index.html:2502), `loadTasksProjects()` (11273), `uptColFilter()` (11268) → `_uptTable.setFilter` → `uptMapFiltersToServer` (11084). Сервер: tasks-фильтр (server.js:935) — `t.project = $?`.
- **Планировщик:** `<select id="planner-project-select">` (index.html:2468), `plannerInit()` (10889), `plannerLoad()` (10920, шлёт `project_id`). Список из `/api/validator/projects`. Сервер: `/api/publish/planner` фильтрует по `project_id`.
- **Дашборд выкладки:** `<select id="dash-filter-project">` (index.html:2312), `_dashApplyFilters()` (11986) → `loadPublishingDashboard()`. Список из `/api/publish/queue/projects`.

### 5.3 Бэкенд delivery (autowarm, server.js)

Под мультивыбор учим принимать список значений (обратно совместимо: одиночный параметр работает как раньше) **четыре** точки:

- `buildPublishQueueFilters` (1900/1918): `project` → `IN (...)`;
- tasks-фильтр (935): `t.project` → `IN (...)`;
- `/api/publish/planner`: `project_id` → `IN (...)`;
- dashboard-запрос (`loadPublishingDashboard` серверная часть): `project` → `IN (...)`.

Формат передачи списка (повторяемый параметр или CSV) фиксируется в плане Фазы 1b. Ручная выкладка — клиентская, бэкенд не трогаем.

## 7. Вне скоупа

- Кнопочные тумблеры (платформы/дни/режим) — это не выпадашки, их не трогаем.
- Существующие мультичекбоксы «Платформы»/«Статус» на Ручной выкладке — оставляем как есть.
- Добавление новых фильтров (напр. фильтр по телефону на страницах, где его нет) — кроме явно перечисленных. Вопрос «по телефону в ручной» — там фильтр уже есть, доп. работы нет.
- Чистка мусорных проектов в данных (`--status` и т.п.) — не наша задача; сортировка просто разместит их по алфавиту.

## 8. Риски и заметки

- **Размер `index.html`.** Файл огромный и редактируется параллельными сессиями — атомарные коммиты, `git fetch` перед стартом, не оставлять half-broken state.
- **Сосуществование виджетов.** Новый виджет не должен конфликтовать с уже существующими мультичекбоксами на Ручной выкладке (общий popup-менеджер / закрытие по клику-вне).
- **Агрегация на клиентском кабинете.** Семантика суммирования метрик по нескольким проектам в аналитике требует аккуратности — детали в плане Фазы 2.
- **Cross-repo.** Две фазы = два репозитория и два PR; не смешивать.
- **Кодекс-ревью.** Spec и каждый план прогоняются через `codex review` до отдачи пользователю.
