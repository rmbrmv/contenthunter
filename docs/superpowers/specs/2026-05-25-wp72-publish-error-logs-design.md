# WP #72 — Изучить логи ошибок в выкладке (Эль-косметик + Онлайн-школа)

- **Дата:** 2026-05-25
- **WP:** #72 (тип «Задача», автор Анастасия, приоритет Высокий, assignee Данил, статус «В разработке»)
- **Ветка:** `wp72-publish-error-logs`
- **Тип задачи:** исследование/триаж (не сборка фичи)

## 1. Цель

Понять, почему у двух клиентов высокий процент фейлов выкладки, и разложить причины
по трём корзинам с понятным резюме для нетехнической аудитории (Аня/операторы).

Клиенты (из `validator_projects`):
- **Эль-косметик** — id `82`, api_name `el_kosmetik_content_hunter`. **Активна**, выкладывается до
  сих пор (последняя строка 25.05).
- **Онлайн-школа Anecole** — id `84`, api_name `onlayn_shkola_anecole_content_hunter`. Числится
  active=true, manual_publish=false, но **в очереди публикаций тишина с 06.05** (последняя
  активность 2026-05-06). Все её фейлы — за 15.04→06.05. Поэтому для школы **два вопроса**:
  (1) что ломалось, пока она выкладывалась; (2) **почему выкладка остановилась 06.05** — вероятно
  операционная причина, а не код, и это, возможно, главный сюрприз для Ани.

Предварительная картина (последние ~40 дней, для масштаба — **не** окно анализа):
- Эль-косметик: 108 failed / 61 done / 28 cancelled / 9 pending / 4 skipped / 3 past_slot_dropped
- Онлайн-школа: 67 failed / 44 done / 1 skipped (всё это — до 06.05)

Из failed ~47% — **без `error_code`** (Эль 40, Школа 42): это слепая зона, ради которой и нужен
разбор по событиям.

## 2. Scope

**В scope:** анализ причин, резюме в #72, дочерние WP на незакрытые код-баги, evidence-файл.

**Вне scope (в рамках #72):** правки кода, re-queue публикаций, операционные действия с
аккаунтами/устройствами. Всё это — отдельные задачи/циклы. Фиксы по заведённым дочерним WP
идут своим spec→plan→impl циклом.

## 3. Данные и окно

**Окно — per-client** (выяснено разведкой 25.05: у школы нет активности в окне с 15.05):
- **Эль-косметик (82):** `created_at >= 2026-05-15` (дата постановки задачи) по «сейчас».
- **Онлайн-школа (84):** `created_at` в `[2026-04-15, 2026-05-06]` — её реальное окно активности.
  Плюс **отдельный шаг**: установить причину остановки 06.05 (расписание/слоты, онбординг,
  договор, ручное отключение — не код).

- **Источник:** `publish_queue` (project_id ∈ {82, 84}) `LEFT JOIN publish_tasks pt ON pt.id = pq.publish_task_id`.
  **LEFT**, а не INNER — иначе строки с `publish_task_id IS NULL` (фейл/отмена до создания таска)
  выпадут, что сломает контроль сумм (§7) и противоречит §8. NULL-task строки классифицируем
  по `pq.status` / `pq.skip_reason`.
- Берём не только `failed`, но и `cancelled` / `skipped` / `past_slot_dropped` — чтобы **отделить
  баги системы от ручных отмен / просроченных слотов**. У Эль 28 cancelled — почти наверняка не баг;
  если этого не показать, «64% фейлов» вводит в заблуждение.

## 4. Метод (события + точечный vision)

### 4.1 Определение реальной финальной причины

`error_code` в `publish_tasks` ненадёжен (пишет первую ошибку, часто preflight; у ~47% пуст).
Поэтому **реальная категория = последняя ПРИЧИННАЯ `meta.category` среди error-событий** в
`pt.events`, **исключая шум и пост-фейловый cleanup** (иначе цепляется не-причина — проверено на
task 8433, где последний error = `screencast_stop_failed`):
- `adb_devices_unreachable` (preflight/сетевой шум),
- `process_interrupted` (PM2 deploy-kill, не баг),
- `screencast_stop_failed` (ошибка выгрузки видеозаписи — cleanup ПОСЛЕ фейла, не причина),
- иные artifact/upload-ошибки, всплывшие при разведке (список финализировать в Task,
  где смотрим landscape категорий).

Каскад: последняя причинная `events[].meta.category` → fallback `error_code` → fallback
`preflight_errors`. Если после исключений ничего не осталось → категория `uncategorized`
(кандидат на vision-разбор, §4.5).

### 4.2 Срезы

1. клиент × платформа × финальная_категория × кол-во;
2. по аккаунту (`pt.account`) — ищем концентрацию на 2–3 «плохих» аккаунтах;
3. по устройству (`pt.raspberry` / `pt.device_serial`) — концентрация на «плохих» телефонах;
4. по дням — динамика (с поправкой на трафик, см. 4.4).

### 4.3 Сверка с деплоями (уже починено vs рецидив)

По каждой категории, у которой был релиз 18–22.05, сравниваем дату фейла с датой фикса:
дата фейла **до** деплоя → «уже починено, наблюдаем» (WP не заводим); **после** → рецидив/новое.

**Важно про школу:** все её фейлы — до 06.05, т.е. до релизов 18–22.05. Значит по школе нельзя
подтвердить «починено» (нет трафика после фикса). Формулировка для школы: «категория чинилась
релизом, но на этом клиенте проверить нельзя — выкладок после 06.05 нет». Поэтому для школы код-WP
заводим только если категория НЕ закрыта релизом ни у кого; всё остальное упирается в вопрос
«почему встала 06.05».

### 4.4 Поправка на трафик (защита от ложных выводов)

23–24.05 — выходные с низким трафиком; нули по категориям там — **слабый** сигнал, не «починено».
Ориентир нормального дня 25.05: IG ~66 / TT ~47 / YT ~27 публикаций. Выводы «закрыто/рецидив»
делаем на буднях с нормальным объёмом, а не по выходным.

### 4.5 Vision по спорным

Для категорий, где первопричина может прятаться под вторичной ошибкой (особенно пустой
`error_code` и `switch_failed_unspecified`), берём 1–2 представителя и смотрим
`screen_record_url` / кадры (ffmpeg) + `vision_analysis_url`, если есть. Память: «screencast-first»
(инцидент pt 4523 — primary RC был скрыт под secondary).

## 5. Раскладка причин

| Корзина | Действие |
|---|---|
| Код-баг, незакрыт, **нет существующего WP** | завести дочерний WP (тип Ошибка, assignee Данил id 5, родитель #72, приоритет по частоте) |
| Код-баг, по которому **WP уже есть** (открыт/переоткрыт, напр. #117/#118/#119) | **не дублировать** — добавить наблюдение по этим клиентам в существующий WP / упомянуть в отчёте |
| Уже закрыто релизом, рецидивов нет | строка «закрыто, наблюдаем» — без WP |
| Аккаунт/устройство (слетел логин, аккаунта нет на телефоне, бан, OTA-экран) | раздел «операторам» — без кода |
| Не баг (ручная отмена, past_slot) | исключаем из «проблем» |

**Дедуп обязателен:** перед заведением дочернего WP — поиск по открытым WP проекта content-hunter
на ту же сигнатуру (cross-session: соседние сессии могли уже завести). Линкуем, а не плодим дубли.

## 7. Проверка корректности

- **Контроль сумм:** Σ по категориям == общему числу failed в окне (для каждого клиента).
- Каждый «уже починено» подтверждён датой фейла < дата деплоя и отсутствием будних рецидивов после.
- Спека и план прогоняются через `codex review` (раундами до 0 P1) перед отдачей Данилу
  (standing practice проекта).

## 8. Открытые допущения

- `pt.events` — JSON-массив с `meta.category` на error-событиях (схема `type='error'`, не `level`).
  Проверить форму первой же выборкой перед массовым разбором.
- Связь `publish_queue.publish_task_id → publish_tasks.id` может быть NULL у части строк
  (фейл до создания таска) — такие классифицируем по `pq.skip_reason` / `pq.status` отдельно.
