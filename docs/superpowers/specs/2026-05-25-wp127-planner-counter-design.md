# WP #127 — Планировщик в деливери: счётчик выложенного — Design Spec

- **Дата:** 2026-05-25
- **OpenProject:** WP #127 «правки по планировщику в деливери» (тип «Задача», автор Анастасия, assignee Данил)
- **Ветка (docs):** `docs/wp127-planner-counter-2026-05-25`
- **Базируется на:** WP #109 (планировщик — `publish_planner.js` + под-таб `up:planner`), WP #108 (`client_publish_id`, леджер попыток), WP #86 (`published_no_url`)

## 1. Постановка задачи

Из описания (Анастасия, со скриншотами): в планировщике деливери **некорректно работает счётчик** — карточка показывает «опубликовано 0/12» (на скрине бейдж «⚠️ Частично 0/12» + «12 ожидают»), хотя по факту за этот день ролики **успешно опубликованы**.

**Объём задачи** (подтверждён с Данилом 2026-05-25): только счётчик выложенного в карточках планировщика. Других правок по планировщику в #127 нет.

## 2. Корень (подтверждён на живой БД, project_id=65 «Forsal», 22.05.2026)

- `publish_queue` за 22.05 у Forsal: 12 строк — `youtube done=6`, `tiktok done=4`, `tiktok failed=2`. По статусу очереди выложено **10/12**; у всех строк `client_publish_id` проставлен.
- Планировщик (full-путь `getPlannerCards` в `publish_planner.js`) считает успехи **не по статусу очереди, а по связке `publish_tasks.client_publish_id`**. Из 10 «done»-строк очереди только **1** находит парную задачу в `publish_tasks` по `client_publish_id`; у **9** совпадения нет.
- Причина разрыва: `publish_tasks.client_publish_id` заполняется **нестабильно** — на 22.05 пустой у 212 из 291 записи (~73%), при этом на 20/23/24/25 мая — 0% пустых. Интермиттирующая проблема пайплайна публикации.
- Итог: реконструкция находит 0 успехов → `done_count=0` → бейдж «Частично 0/12», а остаток `N − 0 = 12` рисуется фронтом как «12 ожидают».

**Вывод:** `publish_queue.status` (`done`/`published`) — надёжный сигнал факта публикации, а планировщик его игнорирует в пользу хрупкой связки через `publish_tasks`.

## 3. Решения, согласованные с заказчиком (Данил, 2026-05-25)

| Вопрос | Решение |
|---|---|
| Объём #127 | Только счётчик выложенного в карточках планировщика |
| Подход к корню | **Доверять статусу очереди.** `publish_queue.status` авторитетен для факта «выложено/нет»; `publish_tasks` — только для уточнения дня-переноса, когда связка есть |
| Первопричина (NULL `client_publish_id` в `publish_tasks`) | Вне scope #127 — отдельная находка (см. §10), возможно отдельная задача |

## 4. Решение — Подход A (гибрид)

`publish_queue.status` авторитетен для факта «выложено». Точная атрибуция дня-переноса сохраняется там, где связка `publish_tasks` есть:

1. **Если у намерения есть привязанный успех в `publish_tasks`** (status ∈ `{done, published, published_no_url}`, кроме `process_interrupted`) — берём день первого такого успеха (поведение как сейчас; переносы/echo/final точны).
2. **Если привязанного успеха нет, но `publish_queue.status` ∈ `{done, published, published_no_url}`** — синтезируем успех на лучшей доступной дате:
   - последний реальный (не `process_interrupted`) день попытки из `publish_tasks`, если такие дни есть;
   - иначе — плановый день слота (`scheduled_date`, МСК).
   - `via_manual` синтезированного успеха = есть ли у строки `manual_handoff_at` (→ режим `👋 вручную`).
3. **Если ни привязанного успеха, ни успешного статуса очереди нет** (`failed`/`pending`/`running`/...) — намерение не выложено, в `done_count` не входит (как сейчас).

`done_count` карточки = число намерений цепочки, признанных выложенными к концу дня (нарастающим). Остаток (`carried_out_count = N − done_count`) и состояние (`partial`/`echo`/`final`/`published`) считаются существующей логикой `buildPlannerCards` поверх исправленных успехов.

### Проверка на Forsal 22.05 (ожидаемо после фикса)
10 done + 2 failed → `done_count=10`, `state=partial`, остаток 2 → «⚠️ Частично 10/12», «↗ 2 …». Вместо текущего «0/12» + «12 ожидают».

## 5. Что меняется (только бэкенд `publish_planner.js`)

1. **SQL `qrows`** (full-путь, ~125–141): добавить в SELECT `pq.status AS queue_status`. `manual_handoff_date` уже селектится — пробросить в намерение.
2. **Маппинг `intents`** (~174–186): пробросить в объект намерения `queue_status` и `manual_handoff_date`.
3. **`buildPlannerCards`** (~32–40): при сборке успехов на намерение, если в `attempts` успеха нет, но `queue_status ∈ SUCCESS_STATUSES` — синтезировать успех по правилу §4.2. Дата синтеза добавляется в `activitySet`.
4. **Деградационный путь** (нет колонок #108, ~188–214): уже считает `COUNT(*) FILTER (WHERE pq.status IN ('done','published'))` — **не трогаем**.

Сигнатура `buildPlannerCards` остаётся чистой функцией: новое поле `queue_status` (и `manual_handoff_date`/`via_manual`) приходит внутри объектов `intents` — тестируется без БД.

## 6. Что НЕ меняется

- **Фронт** (`public/index.html`, `plannerCardHtml` ~10960) — рендерит `done_count`/`total_accounts` как есть; правка не нужна.
- **Плановые карточки** (`approved`/`pending`) из расписания.
- **Колонки очереди** «попытка»/«перенесено» (`deriveTransferColumns`, `attachQueueTransferColumns`).
- **Логика переносов между днями** (echo/final, `carried_in/out`, `closed_transfer_from`) — работает поверх исправленного множества успехов.
- **Схема БД** — ничего не добавляем (Подход 1 #109: переносы выводим, не храним).

## 7. Kill-switch / флаги

| Флаг | Дефолт | Назначение |
|---|---|---|
| `PLANNER_TRUST_QUEUE_STATUS` | `true` (новое поведение) | Синтез успеха из `publish_queue.status` в full-пути. `false` → старое поведение (только связка `publish_tasks`). Мгновенный откат без редеплоя |

Передаётся в `getPlannerCards`/`buildPlannerCards` как опция (читается из env в `server.js` при вызове роута), чтобы чистая функция оставалась тестируемой.

## 8. Тестирование

**`node --test` (`buildPlannerCards` — чистая функция, mock-данные):**
- намерение `queue_status='done'` без привязанного успеха → учтено в `done_count` (дата = `scheduled_date`);
- намерение `queue_status='done'` с реальными попытками, но без success-статуса в `publish_tasks` → синтез на последний день попытки;
- намерение `queue_status='done'` И привязанным успехом на более поздний день → день берётся из задачи (перенос сохранён, синтез не срабатывает);
- `failed`/`pending` без успеха → не учтено;
- сценарий Forsal: 12 намерений (10 done + 2 failed), связки нет → `done_count=10`, `state=partial`, остаток 2;
- регресс: цепочка с полной привязкой задач считается как раньше (новый код не меняет результат);
- `PLANNER_TRUST_QUEUE_STATUS=false` → синтез отключён, старое поведение.

**Live-DB smoke (testbench/прод read-only):** прогон `getPlannerCards` на реальном окне Forsal 22.05 → карточка показывает 10/12.

## 9. Зависимости и деплой

- **Read-only фича.** Изменение чисто в чтении/агрегации, схему не трогает.
- **Cross-repo grep перед деплоем** (общая БД `openclaw`): имя флага `PLANNER_TRUST_QUEUE_STATUS` — нет коллизий.
- **Деплой:** бэкенд-только — `publish_planner.js` (+ чтение флага в `server.js`) в autowarm → PR в `GenGo2/delivery-contenthunter` → prod `git pull` main → `sudo -n pm2 restart autowarm`. Прод-деплой — с одобрения Данила; **без force-push**; учитываем auto-push hook прод-autowarm (любой коммит в прод-чекаут улетает в `GenGo2/delivery-contenthunter`).
- **Где код:** фикс в репо autowarm (`GenGo2/delivery-contenthunter`), не в `contenthunter` (здесь только docs). Реализация — на отдельной ветке autowarm-воркдерева.

## 10. Non-goals / YAGNI

- **Первопричина NULL `client_publish_id` в `publish_tasks`** — вне scope #127. Находка для отдельной задачи: пайплайн публикации (#108) нестабильно проставляет `client_publish_id` на задачах (на 22.05 ~73% NULL). Стоит завести отдельный WP, т.к. это бьёт и по точности дня-переноса, и по колонке «попытка» в очереди.
- **Бэкфилл `client_publish_id`** на исторических задачах.
- **Изменение фронта**, плановых карточек, колонок очереди.
- **Изменение схемы БД.**
