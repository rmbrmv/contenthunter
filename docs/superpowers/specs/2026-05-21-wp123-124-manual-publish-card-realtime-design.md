## Контекст и текущее состояние

Очередь ручной выкладки — operator-facing раздел delivery-дашборда (`delivery.contenthunter.ru` → autowarm `server.js`, порт 3848), модуль «📤 Выкладка» (`#sidebar-publishing`, секция `section-publishing-manual`). Бэкенд: `manual_publish_queue.js` + endpoints `/api/publishing/manual-queue*`. Таблица `validator_manual_publish_queue` (openclaw). Наполнитель `manual_queue_assign.js` (`assignManualPublishQueue`).

**Грейн строки сейчас:** 1 строка на `(unic_result_id × account_username × platform)`. Уникальный индекс `(unic_result_id, account_username, platform) WHERE cancelled_at IS NULL`.

**Что сейчас на фронте** (`public/index.html`): таблица `MPQ_COLS`, группировка строк **по телефону** (`📱 Тел. № N`), per-row кнопка «Взять в работу», карточка `mpqOpenCard` (title/описание/хэштеги/гео — копирование по клику; плеер уник-видео; скачивание исходника/уника; форма публикации). **Реалтайма нет** — только ручное «🔄 Обновить» + перезагрузка после действия (`mpqLoad` в `index.html` ~11890). **Имя оператора, занявшего запись, не хранится** (есть только `taken_at`).

**Авторизация дашборда:** индивидуальные операторы — таблица `autowarm_users`, в сессии `req.session.user = {id, username, role}` (server.js ~78). → имя занявшего оператора доступно.

> Номера строк индикативны (разведка на testbench-чекпоинте); реализатор сверяет с актуальным кодом.

## Доменная модель (уточнена с заказчиком)

- **Пак** = набор аккаунтов, **по одному на платформу** (в паке не может быть двух активных аккаунтов одной платформы). Размер пака: 1–3 аккаунта (IG/TT/YT — может быть меньше).
- Юзернеймы аккаунтов пака **по платформам могут различаться** (в Feminista совпадают, но это не правило: при бане аккаунт заменяется другим с другим юзернеймом). → в карточке показываем **per-platform handle**, не «один юзернейм пака».
- **Одно уник-видео делается под один пак.** Одно исходное видео уникализируется отдельно под каждый пак (content 2240 → 4 уник-видео → 4 пака).
- В очереди три платформенные строки одного пака связаны общим **`unic_result_id`**.

## #123 — Группировка по исходному видео

### Ключ карточки = `unic_result_id` (= одно уник-видео × один пак)

Строки очереди группируются по `unic_result_id` (эквивалентно `(unic_result_id, pack_id)` — они 1:1). Одна карточка = один пак с его уник-видео.

### Карточка (раскрывается на весь экран)

Содержимое:
- **Исходник:** плеер/скачивание (как сейчас).
- **Уник-видео:** плеер/скачивание (как сейчас) + **НОВОЕ поле «Ссылка на уник-видео» — клик копирует URL в буфер обмена** (паттерн copy-on-click, как для title/описания/хэштегов).
- **Шапка:** название пака + проект + **общая дата выкладки**.
- **Мета контента:** title / описание / хэштеги / гео (копирование по клику — как сейчас).
- **Мини-таблица по платформам пака** (1–3 строки):

  | Платформа | Аккаунт (per-platform handle) | Статус | Ссылка на публикацию | Действие |
  |---|---|---|---|---|
  | Instagram | feminista.beauty | в работе / выложено | [поле ввода/копирования] | отметить выложенным |
  | TikTok | … | … | … | … |
  | YouTube | … | … | … | … |

  Поле ссылки на публикацию — на каждую платформу (req: «отдельные поля под платформы для копирования ссылки на выложенный пост»); по клику на заполненную ссылку — копирование в буфер.

### Список очереди

Рендерим одну строку-карточку на `unic_result_id` (вместо N платформенных строк). Внутри сохраняем существующую группировку по телефону (`📱 Тел. № N`) — карточки группируются по телефону пака. В строке-карточке: пак/аккаунт, исходник, уник, дата, агрегатный статус, кнопка действия.

## #124 — Реалтайм + защита «уже в работе»

### «Взять в работу» — на всю карточку, атомарно

- Кнопка «Взять в работу» берёт **весь пак сразу** (все платформы карточки) — req #123.1 («кнопка общая на все платформы исходя из исходного ролика»).
- Атомарный claim всех queued-строк `unic_result_id`:
  `UPDATE … SET operator_status='in_progress', taken_by_user_id=$op, taken_at=now() WHERE unic_result_id=$1 AND operator_status='queued' AND taken_by_user_id IS NULL`.
- `taken_by_user_id` берётся из `req.session.user.id`; имя для отображения — join `autowarm_users`.

### Проверка по клику + предупреждение

- Если карточку уже занял другой оператор (claim затронул 0 строк, т.к. `taken_by_user_id` уже стоит) → **409** с телом `{ error, taken_by: '<username>' }`.
- Фронт показывает предупреждение **«Задача взята оператором XXX в работу»**, после чего **подгружает актуальный статус записи** (рефетч карточки/строки).
- Это жёсткая гарантия от двойной работы — не зависит от частоты автообновления.

### Частичная выкладка

- Каждую платформу отмечаем независимо: оператор вставляет ссылку по платформе → `publish` по строке (per-platform), пишет `post_url` + `published_at`, `operator_status='published'` для этой строки.
- **Агрегатный статус карточки** (вычисляется из строк пака):
  - `queued` — все строки queued;
  - `in_progress` — взято, ни одна не published;
  - `partial` (**частично выложено**) — часть строк published, часть нет;
  - `published` — все строки published.
- «Вернуть в очередь» (`return`) — по `unic_result_id`: освобождает оставшиеся `in_progress` строки (published не трогает), сбрасывает `taken_by`.
- `rework` — по строке (вернуть платформу на доработку), как сейчас.

### Близко к реалтайму

- Лёгкий **поллинг** вкладки раз в **~5 c** (интервал — ENV/конфиг). Аккуратный ре-рендер: обновляем таблицу/статусы, **не дёргая открытую карточку** (если карточка пака открыта — обновляем её статусы in-place, не закрывая/не сбрасывая ввод).
- Поллинг — для свежести UI; защита от коллизий обеспечена атомарным claim + клик-проверкой. Поэтому 5 c достаточно и дёшево.
- *Альтернатива (если потребуется мгновенный push): SSE на `server.js`. Не выбрана — поллинг проще и покрывает требование.*

## Схема / миграция

`validator_manual_publish_queue`:
- **Колонки `taken_by_id`/`published_by_id` УЖЕ существуют** (от WP#107) — новых колонок не добавляем. `takeItem` их не писал; начинаем писать `taken_by_id`.
- **НО нужна миграция-FK-fix:** исходная WP#107-схема указывала FK обеих колонок на `validator_users` (клиентская таблица), а оператор delivery-дашборда — это `autowarm_users`. Без перенаправления FK `takeGroup` упадёт на FK-violation при записи `autowarm_users.id`. Миграция `migrations/20260521_manual_queue_taken_by_fk_fix.sql` (+rollback): `DROP CONSTRAINT … ; ADD … REFERENCES autowarm_users(id)`. Безопасна: на момент правки 0/119 строк имели non-NULL `taken_by_id`/`published_by_id`, текущий prod-код их не пишет → нулевой риск, идемпотентна (`IF EXISTS`).
- Частичная выкладка ложится на текущий per-`(unic_result×account×platform)` грейн (статус/`post_url`/`published_at` уже per-row).

## API (изменения `/api/publishing/manual-queue*`)

| Метод | Путь | Грейн | Поведение |
|---|---|---|---|
| GET | `/api/publishing/manual-queue` | список | Возвращает строки + признак группы (`unic_result_id`) + `taken_by` (username) + агрегатный статус карточки. Фронт группирует по `unic_result_id`. |
| GET | `/api/publishing/manual-queue/group/:unicResultId` | карточка | Все платформенные строки пака + мета + ссылки. |
| POST | `/api/publishing/manual-queue/group/:unicResultId/take` | группа | Атомарный claim всех queued-строк; 409 + `taken_by` если занято. |
| POST | `/api/publishing/manual-queue/group/:unicResultId/return` | группа | Освободить in_progress-строки, сбросить `taken_by`. |
| POST | `/api/publishing/manual-queue/:id/publish` | строка | Per-platform: `post_url` + `published_at` обязательны (422 иначе), `operator_status='published'`. Сохраняем существующую логику штампа `matched_post_url` слота (WP #107). |
| POST | `/api/publishing/manual-queue/:id/rework` | строка | Вернуть платформу на доработку (как сейчас). |

Существующие per-id `take`/`return` (server.js ~5700–5733) эволюционируют в групповые (по `unic_result_id`); per-id `publish`/`rework` сохраняются для частичной выкладки.

## Обработка ошибок / edge cases

- **Claim-гонка:** два оператора жмут «Взять» одновременно → выигрывает атомарный UPDATE, второй получает 409 + имя первого.
- **Пак из 1–2 платформ:** мини-таблица показывает только существующие платформы; группировка/claim работают по любому числу строк.
- **Разные юзернеймы по платформам:** мини-таблица берёт `account_username` каждой строки.
- **Открытая карточка во время поллинга:** ре-рендер обновляет статусы, не сбрасывая незакоммиченный ввод ссылок.
- **Отменённая строка (`cancelled_at`)** не попадает в группу/карточку (как сейчас).

## Kill-switches

- ENV-интервал поллинга (вкл. возможность фактически отключить, выставив большое значение/0).
- При необходимости — ENV-флаг на групповой claim (фолбэк на старый per-row), решается в плане.
