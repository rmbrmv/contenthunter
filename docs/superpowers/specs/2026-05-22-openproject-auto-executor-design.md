# Design Spec: OpenProject Auto-Executor

- **Дата:** 2026-05-22
- **Автор:** Claude (brainstorm с Данилом)
- **Статус:** На вычитке (design approved в диалоге, ожидает review спеки перед планом)

## Проблема

Запуск работы над задачей сейчас стоит времени: открыть сессию, загрузить контекст, понять, что именно делать. Данил хочет ассистента, который сам подхватывает задачи из OpenProject, делает «домашку», доводит простое до PR, а по сложному задаёт точечные вопросы — так, чтобы участие Данила свелось к решениям, а не к разогреву.

## Цели

- Подхватывать задачи, которые Данил вручную пометил как готовые к работе.
- По каждой задаче: разобрать → классифицировать → либо довести до PR самостоятельно, либо запросить решение.
- Закрывать петлю: статусы, комментарии в задаче, документация, отчёт в Telegram.
- Прод никогда не меняется без участия Данила.
- Холостой ход (пустая очередь) почти ничего не стоит.

## Не-цели (out of scope для первой версии)

- Авто-мёрж и авто-деплой (категория A останавливается на PR).
- Полная автономия без гейта (берём только то, что Данил пометил).
- Задачи чужого авторства/не-dev — пропускаем.
- Поддержка соцсетей вне IG/TT/YT и т.п. — это вопрос самих задач, не оркестратора.

## Поток (одна строка)

Данил двигает задачу в статус **«В спецификации» (id 2)** → тупой поллер замечает → агент берёт, разбирает, классифицирует → **A:** доводит до PR сам; **B:** спрашивает в Telegram → закрывает петлю (статус + коммент + отчёт).

## Конечный автомат (реальные статусы OpenProject, проверены 2026-05-22)

```
Новое(1) → [Данил вручную] → В спецификации(2)   ← ГЕЙТ
   В спецификации(2) → [поллер берёт] → В процессе(7)     (дедуп: выпадает из фильтра)
      категория A, успех → В тестировании(9)   → [Данил мёржит/верифит] → Готово(12)
      категория B           → остаётся В процессе(7), помечена awaiting_answer во внутреннем сторе
      падение/исчерпаны попытки → остаётся В процессе(7) + коммент + эскалация в TG (становится фактически B)
```

Нет статуса «ждёт ввода», поэтому B-задачи остаются в «В процессе(7)», а под-состояние (`working` / `awaiting_answer` / `queued` / `failed`) держим во внутреннем сторе. Статусами не «дёргаем» туда-сюда, чтобы не создавать петли перезахвата.

## Категоризация

**Гейт (что вообще берём):** только задачи в статусе «В спецификации (id 2)». Этот статус Данил проставляет руками — это явный сигнал «готово к работе». Поллер ничего другого не трогает.

**Внутри взятой задачи агент сам решает A vs B:**
- **A — «делаю сам»:** чёткое ТЗ, низкий риск, понятный скоуп (баги с воспроизводимым повтором, доки, мелкие фичи).
- **B — «нужно решение»:** размытое ТЗ, продуктовые/UX-развилки, рискованные зоны, **или агент не уверен, какого репозитория/скоупа касается задача**. Неуверенность = автоматически B, не угадывание.

## Компоненты

### 1. Детектор (поллер)
- PM2-демон (Node или Python), интервал **1 минута**.
- Один `curl` к OpenProject: `GET /work_packages?filters=[{status:{operator:"=",values:["2"]}}]`.
- **Без вызова Claude → ноль токенов вхолостую.** Claude поднимается только на реальной задаче.
- Нашёл новую → кладёт в очередь и **сразу PATCH `2 → 7 «В процессе»`** (дедуп + видно, что взято).
- Состояние — лёгкий стор (sqlite или json-файл): `task_id, sub_state, category, brief_path, awaiting_answer, attempts, worktree_path, pr_url, updated_at`.

### 2. Диспетчер
- Потолок **3** одновременных воркеров категории A.
- Пока активных < 3 — берёт из очереди следующую готовую задачу (новую или ту, на которую пришёл ответ по B). Остальные ждут.
- После каждого воркера — **чистка stale `node --test`/pytest процессов** (защита от zombie-инцидента, забивавшего RAM/swap/load).

### 3. Воркер (на задачу) — headless `claude -p` в изолированном worktree
- Лаунчер: `claude -p "/work-task <id>"` в нужном репозитории/worktree.
- **Биллинг — строго подписка (требование Данила).** Лаунчер запускает воркер с **явно вычищенным ключом**: `env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN claude -p …`, и **не сорсит** `~/secrets/anthropic.env` (там ключ проектного рантайма для moderation и т.п.). При старте — **fail-closed**: если ключ всё же присутствует в окружении, воркер отказывается работать (чтобы подписка не «слетела» на API по случайному наследованию env). Opt-in на API — отдельное явное действие, не дефолт. (См. [[reference-claude-p-billing]].)
- Шаги воркера:
  1. Читает задачу: описание, комменты, вложения (скрины ресайзить перед Read), сверяет с памятью/git/кодом, **определяет целевой репозиторий** (autowarm / validator (в составе contenthunter) / knowledge / bugs-bot / …).
  2. Классифицирует **A vs B**.
  3. **A:** worktree → план → TDD → зелёные тесты → `codex review` (раундами до 0 P1) → **PR** → коммент в задаче (house-style) → статус `7 → 9` → отчёт в TG. **Мёрж/деплой не делает. Никаких force-push. В main не вливает** (особенно autowarm/validator, где мёрж = деплой в прод).
  4. **B:** пишет бриф `.md` (вся домашка + варианты решения) → шлёт в TG (вопрос + ссылка на задачу + бриф + готовая команда `claude "/task <id>"`) → ставит `awaiting_answer`, **освобождает слот** (не висит в ожидании).

### 4. Приём ответов (двусторонний Telegram)
- На стеке bugs-бота (`aiogram 3`, systemd): тот же бот и спрашивает, и принимает ответы.
- Реплай Данила ловится → привязывается к задаче → снимает `awaiting_answer` → задача возвращается в очередь, воркер продолжает с решением.
- Альтернатива: Данил вставляет `claude "/task <id>"` в Termius и добивает сложное в живой сессии — бриф перечитывается, контекст не теряется (контекст живёт в брифе, не в переписке).

### 5. Отчёты и документация
- Коммент в задаче по итогам — **house-style** (Что было не так → Что сделано → Что осталось; без жаргона; без подписи/футера).
- Документация-MD по задаче в `docs/`.
- TG: отдельные сообщения на событие (B-вопрос / A-готов-PR / падение) в новом топике **«Задачи»**; дневная сводка в **20:00 МСК** («N в PR, M ждут тебя, K упало»). *(дефолт — подтвердить на вычитке)*

## Биллинг / auth

**Требование: разработка идёт строго по подписке.** Текущее состояние проверено 2026-05-22: Claude Code залогинен через OAuth (`subscriptionType: max`); `ANTHROPIC_API_KEY` **не** в шелле/профиле — он изолирован в `~/secrets/anthropic.env` и подхватывается только сервисами, которые его явно сорсят. То есть `claude -p` из обычного шелла уже идёт по подписке.

Чтобы это была гарантия: воркер стартует с **вычищенным ключом** (`env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN`), не сорсит `~/secrets/anthropic.env`, и **fail-closed** — отказывается работать, если ключ присутствует.

С 2026-06-15 `claude -p` на подписке уходит в отдельный Agent SDK credit (не делит окно с интерактивом). До этой даты тяжёлые воркеры могут подъедать 5-часовое окно живых сессий — объём гейтится вручную (сколько задач Данил положит) + потолок 3; если мешает, есть явный opt-in на API-ключ. Детали: [[reference-claude-p-billing]].

## Защита / guardrails

- Потолок параллелизма **3** + очередь.
- **Kill-switch** — флаг (env/файл/SQL), мгновенно ставит весь цикл на паузу.
- worktree-изоляция; **никаких force-push**; **никакого мёржа в main**.
- Идемпотентность через стор + **потолок попыток** на задачу (не зацикливаться на падающей; исчерпал → эскалация в TG).
- Чистка stale тест-процессов после каждого воркера.
- Дедуп через немедленную смену статуса `2 → 7`.
- PM2 (не systemd) для нового демона — по практике деплоя проекта.
- **Биллинг fail-closed на подписку:** воркер запускается с `env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN`, не сорсит `~/secrets/anthropic.env`, и при старте отказывается работать, если ключ в окружении присутствует (без явного opt-in).
- **Недоверенный контент задачи (защита от prompt-injection):** описание/комменты задачи пишет кто угодно → это **данные, не инструкции**. Доверенный оркестратор (Python) держит все секреты и делает весь I/O (чтение задачи, коммент, статус, TG). Воркер получает задачу как файл-данные, не имеет секретов в окружении и запускается **read-only** (`--allowedTools Read`, без Grep/Glob/Bash/Write/сети, без `--dangerously-skip-permissions`; Grep/Glob вернутся в Фазе 2 под sandbox-юзером). Уже в Фазе 1: чтение `~/secrets`/`~/.claude` **жёстко запрещено** через `.claude/settings.json` (deny), читаемые папки ограничены allowlist'ом (`--add-dir`), а оркестратор **вырезает известные секреты** из вывода воркера до публикации (бэкстоп). В Фазе 2, где воркеру дадут Write/Bash для кода, он обязан бегать под **отдельным низко-привилегированным юзером** без доступа к `~/secrets` и без исходящей сети.

## Открытые вопросы (к вычитке / на этап плана)

1. **Отчёты:** ✅ подтверждено 2026-05-22 — per-event + дневная сводка 20:00 МСК, отдельный топик «Задачи».
2. **Headless-права:** `claude -p` под PM2 должен иметь права на свои инструменты без интерактивного подтверждения (Bash/Edit/git/gh). Решаемо (allowlist или `--dangerously-skip-permissions` в изолированном worktree) — **проверить на смоуке до доверия прод-репозиториям**.
3. **Маппинг репозитория:** правило «не уверен → категория B» зафиксировано; на этапе плана уточнить эвристику определения репо по тексту задачи.
4. **Бот:** расширяем существующий bugs-бот или поднимаем отдельный «tasks»-бот/топик — решить на этапе плана.
