## 1. Контекст и постановка

Тикет WP#213 состоит из 6 пунктов. По решению владельца (Данил) задача разбита на два независимых под-проекта:

- **A (этот документ): «Правдивость лога»** — пункты 1, 4, 6. Баги в read-model «Лога событий» (`lifecycle.js`), из-за которых статусы врут. Чистый display/read-model, без изменения поведения публикации.
- **B (отдельно): «Коды и фильтры»** — пункты 2, 3, 5. Фронт-фичи (код ролика в ручной выкладке и планировщике, фильтры статусов и периода).

Принцип владельца: «лучше один раз уточнить». Решения по развилкам зафиксированы (см. §2).

### Что такое «Лог событий»
Раздел Аналитики (delivery.contenthunter.ru → Аналитика → 📜 Лог событий), построен в WP#174. Агрегирует жизненный цикл каждого ролика (по `content_id`) в 8 стадий и выводит «худший» статус-бейдж + ленту стадий. Модалка «Лог аккаунта» показывает таймлайн попыток по конкретному аккаунту.

Ядро — `lifecycle.js`:
- `rollupSql()` — агрегат по `content_id`: считает строки `publish_queue` по стадиям 1–8.
- `accountsSql()` — построчная стадия по аккаунтам (разворот ролика).
- `deriveWorstState(row, N)` — «худший» бейдж (N = `lifecycle_stuck_days`, дефолт 2).
- `buildTimeline({pq, attempts, mq})` — точки таймлайна для модалки «Лог аккаунта».
- `applyClientSideFilters()` — фильтры/сортировка на стороне сервера.

## 2. Диагностика (подтверждено на проде, read-only)

БД: `openclaw` @ localhost:5432 (все таблицы — `publish_queue`, `publish_tasks`, `validator_manual_publish_queue`, `validator_content`, `validator_projects` — в ней же).

### Баг п.4 — «застрял в ручной» ложный на 99.3 %
Стадия «В ручной очереди» (stage 5) ставится по `pq.manual_handoff_at IS NOT NULL` (`lifecycle.js:57`) **без проверки живой строки** в `validator_manual_publish_queue`.

| stage-5 «в ручной» всего | реально в ручной (живая строка) | ЛОЖНЫХ | затронуто роликов |
|---|---|---|---|
| 2157 | **16** | **2141** | **226** |

Все 2141 ложных = `pq.status='failed'`, `manual_handoff_at` установлен, живой mq-строки нет (отменена/вычищена — напр. гейтом WP#216 или оператором). По факту задачи нигде, а лог рисует «застрял в ручной».

### Баг п.1 — LEX-012 реально застрял в АВТО
content_id 2445. Аккаунты `@LexisVoice_Sales` (ig/tt/yt): `pq.status='failed'`, `error_code=process_interrupted`, `manual_handoff_at` **пуст**, mq-строки нет, висят ~4.8 дня. **Прямой ответ Данилу:** реально застряли, в ручную НЕ передавались, лог отображает корректно (это другой случай, чем п.4). Сейчас бейдж показывает мягко «В РАБОТЕ (в авто)» — это скрывает застревание.

### Баг п.6 — WAN-021 «не выложен», а в логе «запланирован»
content_id 2431. `buildTimeline` (`lifecycle.js:145`) не рисует терминальные негативные состояния. Для отменённого аккаунта без попыток модалка показывает только «📅 Запланирован … сейчас», хотя бейдж/лента справедливо считают его «Не выложен» (stage 8). Отсюда противоречие. Также «в свёрнутом виде в запланирован ни одного нет» — `s_planned=0` верно, конфликт только в модалке.

### Бонус-баг — `published_auto` ложно «не выложен»
stage 7 проверяет только `mq.operator_status='published'`, но не `published_auto` (WP#187). 9 живых строк `published_auto`; те из них, где `pq.status='cancelled'`, ложно классифицируются как «Не выложен». Чиним в той же правке.

### Решения по развилкам (от владельца)
1. **Декомпозиция:** сначала «Правдивость» (A) отдельным PR, затем фичи (B).
2. **П.4 классификация:** ложные «застрял в ручной» → **«Не выложен» (слетел из ручной)**.
3. **П.1 поведение:** только честное отображение; механизм handoff/ретраев не трогаем (отдельный тикет, если потребуется авто-handoff после N фейлов).
4. **П.1 индикация:** ввести честный бейдж «ЗАСТРЯЛ В АВТО» (утверждено в дизайн-ревью).

## 3. Подход

**Правка только read-model + отрисовка таймлайна, за kill-switch, без миграции данных.**

Все три бага — в способе *вычисления* статуса, а не в данных. Меняем SQL-классификацию и `buildTimeline` — 2141 строки «переедут» из «застрял в ручной» в «не выложен» автоматически при следующем рендере. Радиус — только раздел «Лог событий».

Отклонённые альтернативы:
- **Миграция-чистка** (NULL-ить `manual_handoff_at` у 2141): мутирует `publish_queue`, риск задеть ретраи/диспетчер, противоречит «поведение не менять».
- **Новый отдельный статус «Потерян»**: владелец выбрал «Не выложен».

## 4. Детальный дизайн

### 4.1. Stage-логика — `rollupSql()` и `accountsSql()` (баги 4 + published_auto)

Новый порядок CASE (идентично в обоих SQL):

```
stage 7 «Выложен»:        pq.status='done'
                          OR mq.operator_status IN ('published','published_auto')
                          OR s.matched_post_url IS NOT NULL
stage 6 «На ручной»:      mq.operator_status='in_progress'
stage 5 «В ручной очереди»: mq.id IS NOT NULL AND mq.operator_status='queued'   ← требуем ЖИВУЮ строку
stage 8 «Не выложен»:     pq.status IN ('cancelled','skipped','past_slot_dropped')
                          OR (pq.manual_handoff_at IS NOT NULL AND mq.id IS NULL)  ← «слетел из ручной» (2141)
stage 4 «Авто-публикация»: pq.status IN ('running','failed')
stage 3 «Авто-очередь»:    pq.publish_task_id IS NOT NULL
stage 2 «Уникализация»:    ur.status IS NULL OR ur.status NOT IN ('ready','done')
stage 1 «Запланирован»:    иначе
```

Ключевые отличия от текущего:
- stage 5 теперь требует `mq.id IS NOT NULL` (живую строку) **и** `operator_status='queued'`.
- «передан, но живой строки нет» → stage 8 (поднят выше stage 4).
- stage 7 включает `published_auto`.

`stage_since` для stage-8-через-handoff = `pq.manual_handoff_at` (честный возраст «слетело из ручной»). Для прочих stage 8 — `pq.updated_at` (как сейчас).

### 4.2. `deriveWorstState()` — «ЗАСТРЯЛ В АВТО» (баг 1)

В `rollupSql` rollup добавить агрегат:
```
max_auto_days = MAX(дней с stage_since) FILTER (WHERE stage IN (3,4))
```
В `deriveWorstState` добавить ветку (после `stuck_uniq`, до `working`):
```js
if (maxAuto != null && maxAuto > N) return { code: 'stuck_auto', label: 'ЗАСТРЯЛ В АВТО' };
```
Тогда LEX-012 (failed ~5 дней) честно покажет «ЗАСТРЯЛ В АВТО» вместо «В РАБОТЕ (в авто)».

### 4.3. `buildTimeline()` — терминальные точки (баг 6)

Принимает уже всё нужное (`pq.status`, `attempts` с `error_code`, `mq.operator_status`/`taken_at`/`published_at`) — эндпоинт `server.js:1612` менять не нужно.

После существующих точек, **если не была добавлена точка «Выложен»**, добавить терминальную точку:
- `mq.operator_status='published_auto'` → «✅ Выложен (авто, отмечен оператором)»
- иначе `pq.status IN ('cancelled','skipped','past_slot_dropped')` → «⛔ Не выложен»
- иначе `pq.manual_handoff_at` есть, но живого mq нет → «⛔ Не выложен (слетел из ручной)»

Маркер `current:true` (бейдж «сейчас») встаёт на реальное последнее состояние и совпадает с бейджем ролика.

### 4.4. Фронт `public/index.html`

- `lcRenderRows`: цвет/лейбл бейджа для `stuck_auto` (по аналогии со `stuck_manual`).
- Выпадающий фильтр статусов: пункт «ЗАСТРЯЛ В АВТО» (`status` фильтруется по `_worst.code`, см. `applyClientSideFilters:173`).

### 4.5. Kill-switch

Env `LIFECYCLE_TRUTHFUL_STAGE_ENABLED` (default **ON**). Включает: новую stage-логику (4.1), `stuck_auto` (4.2), терминальные точки таймлайна (4.3). При OFF — прежнее поведение. Позволяет откат без передеплоя.
