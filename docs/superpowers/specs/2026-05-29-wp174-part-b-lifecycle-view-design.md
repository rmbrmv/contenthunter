# WP#174 Часть B — Lifecycle View «Лог событий»

**Дата:** 2026-05-29
**Задача:** OpenProject #174 «Таблица Лог событий» (ЧАСТЬ B из двух).
**Статус:** дизайн утверждён, готов к плану.
**Зависимость:** Часть A (коды роликов) — предусловие (колонка «Код», фильтр `RLM-*`).

## Контекст и цель

В админке разрозненные таблицы (Запланировано / Ручная / Уникализация / Опубликовано / планировщик). Один ролик одновременно в разных состояниях по разным аккаунтам — не видно «где теряемся, что зависло». Вводим сквозной Lifecycle View с агрегированной визуализацией состояний по аккаунтам внутри одной строки.

## Репозиторий

- **`delivery-contenthunter`** (`server.js` + vanilla `public/index.html`) — основная работа: эндпоинты read-model + UI раздела.
- БД `openclaw` (localhost:5432) — чтение существующих таблиц.

## Решения (из брейншторма)

- Данные таймлайна — **выводим из существующих таблиц** (read-model), без новой writer-таблицы.
- «Мёртвые» аккаунты — **отдельный 8-й бакет «⛔ Не выложен»** (cancelled/skipped/past_slot_dropped/терминальный failed); сумма всех сегментов = «Всего аккаунтов».
- Порог застревания N — **DB-настройка** (default 2 дня) + редактирование в UI раздела; без рестарта.
- Drill-down из воронки — **отложен**; URL-параметры закладываем сейчас.

## Заземление данных (проверено по БД 29.05)

- `publish_queue` **не имеет** прямого `content_id`: связь `pq.unic_result_id → unic_results.task_id → unic_tasks.content_id` (или `pq.unic_task_id`). ~459 контентов с активной очередью из 9149 строк → объём малый, агрегация **на лету**.
- Ретраи: до 49 строк `publish_tasks` на один `client_publish_id` (avg 1.24) — попытки реальны.
- `validator_manual_publish_queue` имеет `content_id` + операторский таймлайн (`taken_at/taken_by_id`, `published_at/published_by_id`, `cancelled_at`, `operator_status`, `post_url`).
- `publish_tasks.events` (JSONB) — лог-строки **со временем без даты** (`ts`=HH:MM:SS); для аннотации ошибок, НЕ для межэтапного таймлайна. Переходы между этапами берём из таймстампов уровня таблиц.

## B0. Архитектура

Новый раздел внутри вкладки «Аналитика» в delivery. Read-only read-model, агрегация на лету.

Эндпоинты (`server.js`):
- `GET /api/lifecycle` — список (1 строка = 1 контент), server-side фильтры/сортировка/пагинация.
- `GET /api/lifecycle/:contentId/accounts` — mini-breakdown для expand.
- `GET /api/lifecycle/account/:pqId/timeline` — таймлайн для модалки «Лог аккаунта».
- `GET/PUT /api/lifecycle/settings` — порог N (DB-настройка).

Доступ: admin (по существующей сессионной модели delivery, `req.session.user.role`).

## B1. Гранулярность

- **1 строка = 1 контент** (`validator_content`, связь через `unic_tasks.content_id`).
- **Аккаунт** внутри = строка `publish_queue` (account_username + platform + device_serial).
- «Всего аккаунтов» = число `publish_queue`-строк контента.

## B2. Derivation 7 этапов + 8-й бакет (по приоритету — текущий этап аккаунта)

Для каждой `publish_queue`-строки определяем РОВНО один этап (сверху вниз, первое совпадение):

| # | Этап | Правило |
|---|------|---------|
| — | ⛔ Не выложен (8-й бакет) | `pq.status IN ('cancelled','skipped','past_slot_dropped')` ИЛИ терминальный `failed` (исчерпаны ретраи, не передан в ручную, нет post_url) |
| 7 | ✅ Выложен | `pq.status='done'` ИЛИ `mq.operator_status='published'` ИЛИ post_url есть |
| 6 | ✋ На ручной выкладке | `mq.operator_status='in_progress'` |
| 5 | 📋 В ручной очереди | `manual_handoff_at IS NOT NULL` и не выложен/не in_progress |
| 4 | 🤖 Авто-публикация | `pq.status='running'` ИЛИ активная (не-терминальная) publish_task-попытка |
| 3 | 🚦 Авто-очередь | `publish_task_id IS NOT NULL`, статус pending (диспатчнут, ждёт) |
| 2 | 🎬 Уникализация | `ur.status NOT IN ('ready','done')` (вариант ещё не готов) |
| 1 | 📅 Запланирован | дефолт (очередь есть, ничего выше) |

**Инвариант:** сумма по 7 этапам + «⛔ Не выложен» = «Всего аккаунтов» (контроль корректности).

Точная классификация «терминального failed» уточняется по `publish_error_codes.retry_strategy` / отсутствию активной попытки — финализируется в плане; при сомнении аккаунт остаётся на этапе 4 (Авто-публикация) с аннотацией ошибки.

## B3. Общий статус ролика — worst-state badge

Приоритет (от худшего к лучшему, по B.4 ТЗ):
1. **ЗАСТРЯЛ В РУЧНОЙ** — хоть один аккаунт на этапе 5/6 > N дней, не выложен (красный).
2. **ЗАСТРЯЛ НА УНИКАЛИЗАЦИИ** — аккаунты на этапе 1/2 > N дней (оранжевый).
3. **В РАБОТЕ** — есть активные, ничего критично не застряло. Под-метка режима:
   - «В работе (в авто)» — все активные на этапах 3-4.
   - «В работе (в ручной)» — все активные на этапах 5-6.
   - «В работе (оба)» — часть на авто, часть на ручных.
4. **ПОЛНОСТЬЮ ВЫЛОЖЕН** — все аккаунты на этапе 7.
5. **ЗАПЛАНИРОВАН** — все на этапе 1, задачи ещё не созданы.

Worst-state считается по живым+выложенным аккаунтам. Если **все** аккаунты в 8-м бакете → бейдж **НЕ ВЫЛОЖЕН**; если часть — отражается ⛔-сегментом в ленте (финальная семантика бейджа валидируется с Аней при ревью).

«Зависание» = `max(дней на текущем этапе)` среди аккаунтов ролика. N — порог из DB-настройки (default 2).

## B4. Таблица (по B.2 ТЗ)

Колонки слева направо: **Код** (кликабелен — копирование) / Клиент / Заголовок видео / Плановая дата / Всего аккаунтов / Общий статус (бейдж) / **Лента этапов**. Колонки «Действия» нет. Все колонки сортируемы (клик на заголовок).

## B5. Лента этапов (по B.3 ТЗ)

В одной ячейке — 7 компактных элементов (+ ⛔ при наличии): иконка + число аккаунтов на этапе.
- 0 на этапе → иконка opacity 0.4, число `0`. >0 → полная интенсивность.
- Hover → tooltip с полным названием этапа.
- Иконки: 📅 Запланирован / 🎬 Уникализация / 🚦 Авто-очередь / 🤖 Авто-публикация / 📋 В ручной очереди / ✋ На ручной выкладке / ✅ Выложен / ⛔ Не выложен.
- Мягкий разделитель между элементами. Пример: `📅0 | 🎬0 | 🚦3 | 🤖0 | 📋2 | ✋0 | ✅5`.

## B6. In-place expand — mini-breakdown (по B.5 ТЗ)

Клик по строке/шеврону → `GET /api/lifecycle/:contentId/accounts` → таблица 6 колонок:
- Аккаунт (`@handle`)
- Телефон `#N` (через `factory_device_numbers.device_number` по `device_serial`)
- Платформа (иконка по бренду: 🎵 TikTok / 📷 Instagram / ▶️ YouTube)
- Дата действия (ДД.ММ ЧЧ:ММ)
- Комментарий по этапу (текущий этап + контекст: оператор/попытка/ошибка, БЕЗ даты)
- Кнопка «📜 Лог аккаунта»

Несколько строк могут быть раскрыты одновременно; повторный клик/клик вне — сворачивает.

## B7. Модалка «Лог аккаунта» — таймлайн (по B.5 ТЗ)

`GET /api/lifecycle/account/:pqId/timeline` — точки таймлайна из таймстампов таблиц:
- 📅 Запланирован — `pq.scheduled_at` / `pq.created_at` (+ слот)
- 🎬 Уникализация → готово — таймстампы `unic_tasks`/`unic_results`
- 🚦 Авто-очередь — диспатч publish_task
- 🤖 Авто-публикация — **каждая** `publish_tasks`-попытка (попытка №, `error_code`; деталь из `events`)
- 📋 Передан в ручную — `pq.manual_handoff_at`
- ✋ На ручной выкладке — `mq.taken_at` + оператор (`taken_by_id`)
- ✅ Выложен — `mq.published_at` / `pq.status='done'` + post_url

Каждая точка: время → этап → опциональный контекст (попытка №, ошибка, оператор, телефон). Текущее состояние — жёлтый маркер + плашка «сейчас».

## B8. Сортировка и фильтры (по B.6/B.7 ТЗ)

- Дефолт-сортировка: «зависшие дольше всего» (max дней на текущем этапе, desc).
- Альт-сортировки кликом: код / клиент / план.дата / общий статус / всего аккаунтов.
- Фильтры под заголовками (единый ряд): Код (точный / `RLM-*`) / Клиент (multi-select) / Заголовок (подстрока) / Плановая дата (диапазон) / Всего (1–5 / 6–10 / 10+) / Общий статус (multi-select). Фильтр «Платформа» — в шапке блока. Отдельного «Застрял >N дней» нет (отражено в статусе/сортировке).

## B9. Порог N (DB-настройка)

Хранилище: строка в таблице настроек (app_settings / lifecycle_settings), редактируется админом в UI раздела (`PUT /api/lifecycle/settings`), применяется без рестарта. Default 2 дня.

## B10. URL-параметры (задел под drill-down, B.10 ТЗ)

Lifecycle View принимает `?stage=...&blind_zone=...&client=...&code=...` → предзаполняет фильтры. Сам drill-down из воронки дашборда — **отдельной задачей** (не в этой итерации).

## B11. Производительность

Агрегация на лету (~459 контентов). SQL: per-content rollup (CTE с derivation по `publish_queue` + LEFT JOIN manual_queue/unic/factory_device_numbers), server-side фильтр/сортировка/пагинация. При росте объёма — кэш-снапшот отдельной задачей (YAGNI сейчас).

## B12. Тестирование

- **Derivation:** каждое из 7 правил + 8-й бакет на синтетических наборах publish_queue; инвариант суммы сегментов.
- **Worst-state:** все 5 бейджей + под-метки режима + «НЕ ВЫЛОЖЕН» + порог N (граница дней).
- **Expand/timeline:** сборка таймлайна из нескольких таймстампов; несколько попыток с ошибками; маркер «сейчас».
- **Телефон #N:** маппинг device_serial → device_number; отсутствие в роутере → честный fallback.
- **Фильтры/сортировка:** код/префикс, multi-select, диапазоны, дефолт-сортировка.
- **Видимость:** раздел только админу.
