# WP#152 — Новые схемы уникализации (пул 34 → ~70)

**OpenProject:** [#152 «Новые схемы уникализации»](https://openproject.contenthunter.ru/work_packages/152) (тип Задача, parent «Уникализация», автор Анастасия).
**Дата:** 2026-06-02. **Дедлайн клиента:** выкладка стартует 10 июня.
**Статус:** дизайн одобрен, спека на ревью.

---

## 1. Проблема и цель

Появился клиент со ~100 аккаунтами на 3 платформах. Одна схема уникализации
закрывает сразу 3 платформы (1 пак = 3 аккаунта), значит у клиента ~**34 пака**.
Текущего пула в **34 схемы** не хватает: клиенту нужен пул с запасом, чтобы он
мог отбраковать часть в тиндере и всё равно остаться выше порога.

**Цель:** довести общий пул схем уникализации с **34 до ~70** (верх комфортного
диапазона 60–70), добавив **+36 новых схем** (id 35–70). Разнообразие наращиваем
по двум осям: новые лица-оверлеи и новый эффект «тряска».

### Как устроена система (контекст)

- `unic_schemes` (openclaw PG, localhost:5432) — глобальный пул схем, 53 колонки
  FFmpeg-параметров. UI/эндпоинта создания нет — только прямой SQL. Сейчас 34
  строки (id 1–34), все `status=true`.
- Каждая схема привязана к одному оверлею («лицу») через `content_video_index`.
  Оверлеи лежат в `validator_unic_content WHERE content_type='video' AND
  project_id=0` (сейчас 14 строк, id 466–501). Индекс = `(content_video_index-1)
  % len(overlays)`. Сейчас 30 исходных схем = 3 рецепта × 10 оверлеев; 31–34
  (WP#111) = по 1 рецепту на оверлеи 11–14.
- Рендер выполняет локальный воркер `autowarm/unic-worker/worker.py` (PM2,
  root): собирает `filter_complex` из параметров схемы (`scheme.get('колонка')`),
  поэтому новая колонка проходит в пайплайн автоматически. `rotate_deg` —
  статичный угол; **динамической «тряски» в наборе параметров нет**.
- Клиент выбирает схемы в тиндере → `validator_scheme_preferences`. Гейт
  `run_auto_unic.js`: число одобренных схем должно быть ≥ числа паков клиента
  (`factory_pack_accounts`). **Пул глобальный** — тиндер показывает клиенту все
  схемы `id>0`; пред-одобрять не нужно, клиент сам выберет.

## 2. Архитектура решения

Четыре независимых компонента + деплой. Существующие 34 схемы и 14 оверлеев
**не меняются** — только добавление.

### Компонент 1 — 10 круглых лиц-оверлеев (данные + S3)

Источник: [Google Drive folder](https://drive.google.com/drive/folders/1vYBVAhHfS9PhS4vfLhCJpEjOMcpl9Wgp)
— 10 квадратных видео «говорящих голов» (768²–1440², H.264/HEVC, 24fps, ~4–8с).

Одноразовый prep-скрипт для каждого файла:
1. Скейл до **720×720** (как существующие оверлеи).
2. Обрезка в круг: круглая альфа-маска (`geq`, радиус ≈ 356px от центра 360,360).
3. Композит на сплошной зелёный `0x00ff00` (фон вне круга).
4. Кодирование H.264 / yuv420p / faststart.
5. Загрузка в S3 (`factory/overlay_video/<uuid>.mp4`, бакет `1cabe906ea6e-gengo`,
   публичный `https://save.gengo.io`).
6. `INSERT` в `validator_unic_content`: `content_type='video'`, `project_id=0`,
   `usage_type='Универсально (любой проект)'`, `label='video_0_15..24'`,
   `file_path`=S3 URL, **`chromakey_color='0x00ff00'`**.

Новые оверлеи получают `content_video_index` 15–24. Воркер на рендере вырежет
зелёный штатным `chromakey` → останется круглый «пузырь» с лицом. Зелёный фон мы
задаём сами → подбор хромакея покадрово (боль WP#111) здесь не нужен.

**Прототип проверен** на реальном файле: круг чистый, лицо в центре. ✓

### Компонент 2 — эффект «тряска» (воркер + БД)

- БД: две новые колонки в `unic_schemes`:
  - `shake_amp` (integer, амплитуда в px; `NULL`/`0` = выкл) — default `NULL`.
  - `shake_freq` (numeric, Гц; default `1.0`).
- Воркер `worker.py`: новая ветка фильтра после `crop`/`rotate`. Принцип —
  лёгкий зум, затем `crop` с синусоидальным смещением окна по x/y, чтобы края
  не уходили в чёрное:
  ```
  scale=iw+2*A:ih+2*A,
  crop=iw-2*A:ih-2*A : A+A*sin(2*PI*F*t) : A+A*cos(2*PI*F*t)
  ```
  где `A=shake_amp`, `F=shake_freq`. Смещение в диапазоне `[0, 2A]`, окно кропа
  гарантированно внутри увеличенного кадра. Выходные размеры = исходным.
- Гейт на включение: ветка добавляется только если `shake_amp` задан и `>0`.
  Существующие 34 схемы имеют `shake_amp IS NULL` → поведение не меняется
  (нулевой риск регрессии). Дополнительный глобальный рубильник не требуется.

### Компонент 3 — +36 схем (гибрид «рецепт × лицо»)

Прямой SQL (паттерн WP#111: TEMP TABLE clone + override полей). 36 новых строк
(id 35–70). Принцип гибрида — каждая новая схема уникальна **и по параметрам, и
по лицу**:
- Набор рецептов параметров: вариации `crop_reduce`/`crop_offset`, `rotate_deg`
  (малые углы), `speed` (0.95–1.05), `scale_add`, `pad_add`, аудио
  (`audio_atempo`/`audio_volume`/`audio_highpass`/`audio_lowpass`) — в пределах,
  уже проверенных на существующих 34 схемах (mobile-safe, без переискажения).
- Часть рецептов — с тряской (`shake_amp` 4–12px, `shake_freq` 0.8–1.6),
  часть — без.
- `content_video_index` распределяется по оверлеям с приоритетом новым 10
  (индексы 15–24), с добором существующих, чтобы каждая комбинация
  «рецепт × лицо» была уникальной.
- `status=true`, `label`/`metadata_title` — осмысленные.

### Компонент 4 — превью и валидация

- **Превью для тиндера** новых схем 35–70: прямой рендер (воркерный
  FFmpeg-пайплайн локально) → загрузка в S3 → upsert в
  `validator_scheme_previews` по `(scheme_id, project_id=0)`.
  **НЕ** через `scheme_preview`-задачу в `unic_tasks` — по WP#111 она ненадёжна
  для точечного ре-рендера (рапортует done, но S3 не перезаписывает).
- **Рендер-тест** каждой новой схемы через полный пайплайн: выход валиден,
  mobile-safe (H.264 Main/4.1/yuv420p), хромакей на новых оверлеях вырезается
  чисто (круг без зелёной каймы).

```

   └─ prep-скрипт: scale 720² → круглая альфа → композит на зелёный → H.264
        └─ S3 (factory/overlay_video/*.mp4)
             └─ INSERT validator_unic_content (project_id=0, chromakey 0x00ff00)  [idx 15–24]

   └─ INSERT 36 схем (id 35–70): рецепт (± тряска) × оверлей

worker.py: + ветка shake (читает shake_amp/shake_freq)

Превью: рендер 35–70 → S3 → upsert validator_scheme_previews

Клиент → тиндер показывает все id>0 (70 схем) → approve/reject → preferences
   └─ run_auto_unic.js: approved ≥ packs → автоподбор схемы на пак
```

## 4. Обработка ошибок и крайние случаи

- **Drive-файл не лицо/битый** — prep-скрипт валидирует ffprobe перед обработкой;
  битый файл логируется и пропускается, не валит весь батч.
- **Зелёный присутствует в самом лице** — мы задаём чистый `0x00ff00`; при
  рендер-тесте проверяем, что внутри круга нет ложного выреза (similarity 0.12).
  Если лицо содержит близкий зелёный — поднять/опустить similarity для этого
  оверлея (колонка `chromakey_color` индивидуальна).
- **Тряска уводит края в чёрное** — диапазон смещения жёстко `[0,2A]` при зуме
  `+2A`, окно кропа всегда внутри. Тест проверяет отсутствие чёрных полос.
- **Регрессия существующих схем** — гарантирована: новые колонки `NULL` у 1–34,
  ветка тряски не активируется; оверлеи 1–14 не трогаются.
- **S3 upsert превью не перезаписался** (гоча WP#111) — используем прямой
  PUT + проверку URL, upsert с возрастающим `last_task_id`.

## 5. Тестирование

- **Юнит (unic-worker/tests)**: при `shake_amp>0` в `filter_complex` появляется
  ожидаемая `scale+crop`-ветка с корректными выражениями; при `NULL/0` — ветки
  нет (защита от регрессии).
- **Смок-рендер**: прогнать 1 схему с тряской и 1 на новом круглом оверлее через
  полный пайплайн; проверить валидность выхода (ffprobe) и отсутствие чёрных
  полос / зелёной каймы (`blackdetect` + визуальный кадр).
- **Рендер-тест всех 36** новых схем перед публикацией пула.
- **Превью в тиндере**: убедиться, что схемы 35–70 показываются с превью.

## 6. Деплой

1. БД: `ALTER TABLE unic_schemes ADD COLUMN shake_amp int, ADD COLUMN shake_freq
   numeric DEFAULT 1.0;` (alembic-миграция в validator-репо для консистентности).
2. Воркер: git pull в `autowarm` + `sudo pm2 restart unic-worker`.
3. Данные: prep-скрипт оверлеев → S3 → INSERT `validator_unic_content`;
   INSERT 36 схем; рендер превью → S3 → upsert `validator_scheme_previews`.
4. Порядок: миграция колонок → деплой воркера → оверлеи → схемы → превью
   (схемы с тряской рендерятся только после деплоя воркера).

**Откат:** удалить новые строки (схемы 35–70, оверлеи 15–24, их превью);
колонки `shake_amp/shake_freq` безвредны (используются только новыми схемами).
