## Контекст и расследование

Автор заметила в разделе «Выкладка» (ручная выкладка, `delivery.contenthunter.ru`), что у паков Feminista #154/#155/#156 и Ambassadori #112/#114 **«Ручная дата» (25.05) оказывается раньше «План даты» (26–29.05)**. Гипотезы автора: (1) за план-дату берётся дата до переноса в планировщике; (2) логика неверна — вся Feminista на ручной выкладке, значит «Ручная дата» должна равняться «План дате».

**Разведка по коду и БД (read-only) показала:**

- «Ручная дата» = `validator_manual_publish_queue.created_at` (день попадания строки в ручную очередь), «План дата» = `planned_date` (снимок `validator_schedule_slots.slot_date` на момент наполнения). Обе колонки добавлены/трактованы намеренно в WP #128.
- **Гипотеза №1 опровергнута данными:** снимок `planned_date` в очереди **точно совпадает** с текущим `slot_date` по всем проверенным строкам — устаревания из-за переносов нет.
- **Симптом — не баг данных.** Он вытекает из двух ожидаемых механик:
  - **① Перевод проекта в ручной режим «задним числом».** `validator_projects.manual_publish_set_at`: Ambassadori (проект 58) переведён 25.05 07:27, Feminista (проект 100) — 21.05 13:51. В момент перевода наполнитель `assignManualPublishQueue` смёл в ручную **весь готовый уникализированный архив проекта**, включая слоты с план-датой 2–3-недельной давности (Feminista — планы с 05-07).
  - **② Уникализация опережает план-дату.** Для ручного проекта контент падает в очередь в момент готовности уникализации; будущие слоты (план 26–29.05) уникализировались 25.05 и сразу попали в ручную → «Ручная дата 25 < План 26–29». Это ровно то, что увидела автор, и это корректно.
- **Остаточной утечки уже-опубликованного нет** (0 `queued`-строк, чей `unic_result+account+platform` уже `done` в авто — зачистка WP #148 отработала).

**Ключевое несоответствие, вскрытое расследованием:** авто-тракт (`assignUnicResultsToQueue` → `clampPastSlot`, `server.js:6209`) **дропает прошедшие слоты** (`slot_date < todayBusiness`, аудит-строка `past_slot_dropped`). Ручной наполнитель (`assignManualPublishQueue`) **такой проверки не имеет** — отсюда и флуд просрочки.

**Масштаб на 2026-05-26:** в ручной очереди **277 `queued`-строк с план-датой в прошлом** (5 проектов, старейшая — 05-07) против 95 актуальных. ~74% очереди — шум просрочки.

## Решение

Внести в ручной наполнитель ту же политику «прошедшего слота», что в авто-тракте, но с маленьким грейс-окном (ручная выкладка — про человеческий догон), под kill-switch; разово зачистить уже накопившуюся просрочку; уточнить ярлык колонки.

### Продуктовые решения (зафиксированы с Данилом 2026-05-26)

- **Порог = грейс 3 дня.** В ручную льются слоты с план-датой не старше 3 дней. Отсекает глубокий флуд (Feminista 05-07, Ambassadori 05-14), оставляет свежую просрочку (ClickPay 05-25, rev_el 05-24), чтобы оператор мог довыложить.
- **Ретро-зачистка — да**, скриптом с dry-run по умолчанию, по тому же порогу.
- **Осознанное расхождение с авто-трактом:** авто = 0 грейса, ручная = 3 дня. Документируется намеренно.

## Изменения

### R1 — Гейт просрочки в наполнителе (`manual_queue_assign.js`)

**Расчёт порога (раз за прогон, в начале `assignManualPublishQueue`):**

```js
const GRACE_DAYS = parseInt(process.env.MANUAL_QUEUE_PAST_SLOT_GRACE_DAYS || '3', 10);
function dropPastEnabled() {
  return process.env.MANUAL_QUEUE_DROP_PAST_SLOTS !== 'false';
}
// таймзона из настроек, ровно как авто-тракт (server.js:6249-6251)
const { computeBusinessDate } = require('./unic_sweep');
const { rows: settings } = await pool.query('SELECT * FROM unic_settings WHERE id=1');
const timezone = settings[0]?.timezone || 'Asia/Dubai';
const cutoff = computeBusinessDate(timezone, Date.now() - GRACE_DAYS * 86400000); // 'YYYY-MM-DD'
```

> Таймзона — колонка `timezone` в `unic_settings` (один ряд `id=1`), читается тем же запросом, что авто-тракт `assignUnicResultsToQueue` (`server.js:6249-6251`). Дефолт `Asia/Dubai`. (Замечание: `autowarm_settings` — это другое, key/value хранилище без ключа `timezone`; не путать.)

**Фильтр в SELECT** (когда `dropPastEnabled()`):

```sql
AND to_char(vss.slot_date, 'YYYY-MM-DD') >= $cutoff
```

- **Почему именно в SQL, а не пропуском в цикле:** текущий SELECT — `ORDER BY ur.created_at ASC LIMIT 100`. Если фильтровать в цикле, батч из 100 забьётся самыми старыми (просроченными) результатами, и актуальные **никогда не дойдут до вставки** — старьё «голодит» очередь. SQL-фильтр чинит это в корне.
- **Строковое сравнение TZ-safe** (как помечено в `clampPastSlot`: `'2026-05-07' < '2026-05-08'`).
- При `MANUAL_QUEUE_DROP_PAST_SLOTS=false` фильтр не добавляется — поведение «тащить всё» (откат без релиза).

**Наблюдаемость:** в начале прогона залогировать `{tag:'manual-queue', gate:'past_slot', enabled, cutoff, grace_days}`. Опционально — одним лёгким `COUNT(*)` посчитать, сколько готовых eligible-результатов отсечено порогом, и залогировать (диагностический сигнал «сколько просрочки придержано»).

### R2 — Флаги (env)

- `MANUAL_QUEUE_DROP_PAST_SLOTS` (default `true`) — kill-switch гейта.
- `MANUAL_QUEUE_PAST_SLOT_GRACE_DAYS` (default `3`) — ширина грейс-окна в днях.

Оба читаются из `process.env` на каждом прогоне (как `isEnabled`/`batchSize` рядом). **Важно:** само значение в `process.env` фиксируется при старте процесса — чтобы новое значение дошло до `setInterval`-прогонов, нужен `sudo pm2 restart autowarm --update-env` (это рестарт процесса с обновлённым окружением, но не релиз кода).

### R3 — Ретро-зачистка (`cleanup_wp155_manual_queue_overdue.js`)

Паттерн `cleanup_wp148_manual_queue_dups.js`:

- **dry-run по умолчанию**; `--apply` для выполнения; `--onlyProject=<name|id>` для тест-изоляции.
- Кандидаты: `validator_manual_publish_queue` где `operator_status='queued'` И `cancelled_at IS NULL` И `to_char(planned_date,'YYYY-MM-DD') < cutoff` (тот же `cutoff` = `today − GRACE_DAYS`).
- Действие: `UPDATE … SET cancelled_at=now()`. Колонки причины отмены в таблице **нет** (есть только `cancelled_at`, проверено по схеме) — причину `wp155_overdue_gate` пишем в лог скрипта, без ALTER.
- **Не трогаем** `published` и `in_progress` (и любой не-`queued`). CHECK-констрейнт `ck_manual_pub_status` подтверждает три статуса: `queued|in_progress|published`.
- Отчёт: сколько подходит под порог, разбивка по проектам; в dry-run только печать, без записи.
- Идемпотентность: повторный прогон не находит уже отменённых (фильтр `cancelled_at IS NULL`).

### R4 — Ярлык колонки (`public/index.html`)

- В `MPQ_COLS`: `label: 'Ручная дата'` → `label: 'Добавлено в очередь'`. Ключ поля (`manual_date`) и бэкенд-алиас **не трогаем**.
- Опционально — `title`/подсказка на `<th>`: «дата, когда пак попал в ручную очередь (не дата публикации)».
- Колонка «План дата» (сортировка/фильтр `daterange`) — без изменений; именно по ней оператор ориентируется на дату выкладки.

## Тестирование

**Бэкенд (node `--test`, рядом с `test_manual_publish_queue.test.js`):**
- Гейт отсекает результат со `slot_date` старше `cutoff` (не попадает в ручную).
- Гейт оставляет результат в пределах грейса (план = `today − GRACE_DAYS`) и будущий.
- `MANUAL_QUEUE_DROP_PAST_SLOTS=false` → гейт выключен, тащит и старое (старое поведение).
- `MANUAL_QUEUE_PAST_SLOT_GRACE_DAYS` меняет границу.
- Антирегресс «голодания»: при большом числе старых результатов + LIMIT актуальные/будущие всё равно попадают в очередь (гейт отсёк старые на уровне SQL).

**Скрипт зачистки (node `--test` или smoke):**
- dry-run ничего не пишет; `--apply` отменяет только `queued` с план-датой < cutoff.
- Не трогает `published`/`in_progress`.
- Повторный прогон идемпотентен.

**Ручная приёмка (тест-копия → прод):**
1. Новый перевод проекта в ручной режим не засыпает очередь слотами 2-недельной давности.
2. Свежая просрочка (≤3 дня) и будущее по-прежнему попадают.
3. После зачистки 277 просроченных queued-строк ушли из очереди; published/in_progress на месте.
4. Колонка называется «Добавлено в очередь».

## Риски

- **Грейс-граница (off-by-one по таймзоне):** использовать строковое сравнение `to_char(...,'YYYY-MM-DD') >= cutoff` и `computeBusinessDate` (как авто-тракт), не ручной date-math, не `CURRENT_DATE` (UTC ≠ бизнес-TZ).
- **Скрипт зачистки трогает живые данные:** dry-run по умолчанию + фильтр строго `queued`/`cancelled_at IS NULL` + `--onlyProject` для проверки на одном проекте до массового `--apply`.
- **Потеря легитимной просрочки:** контент старше 3 дней (напр. уникализация догнала поздно после стопора) в ручную не попадёт. Допустимо по решению; при необходимости — ручной re-queue. Грейс настраивается env без релиза.
- **Расхождение политик авто (0) vs ручная (3 дня)** — намеренное; задокументировано в комментарии у гейта.
