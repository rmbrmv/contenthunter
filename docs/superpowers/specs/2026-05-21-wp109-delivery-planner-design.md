- **Дата:** 2026-05-21

- **Ветка (docs):** `docs/wp109-delivery-planner-2026-05-21`
- **Базируется на / переиспользует:** WP #108 (движок ретраев — источник данных о переносах/попытках/ручной передаче), WP #107 (раздел «Ручная выкладка» — паттерн врезки секции), WP #90 (Chart.js и стиль дашборда), WP #85/#115/#125 (модель ручной/авто выкладки), WP #86 (`post_url`)

## 1. Постановка задачи

Дать **менеджеру** (Аня) видимое представление выкладок: для каждого исходного слота показать подслоты по конкретным аккаунтам с их статусом, попытками и фактом публикации. Главная ценность — **визуализация переносов**: когда часть аккаунтов не выложилась сегодня и уехала на следующий день (авто-ретрай), а на 3-й день — в ручную.

Из описания задачи — **две части**:

1. **Календарь-планировщик** в админ-части деливери (НЕ в клиентской): недельная сетка по дням, карточки «проект × ролик × день», статусы `частично`/`перенос`, счётчик `N/N` (выложено на текущий день), прогресс-бар для частичных, пометки переносов (`↗ N на 21.05` / `↩ с 20.05` / `↩ закрыло перенос с 20.05`), плашка режима `🤖 авто` / `👋 вручную`, hover-подсветка одной цепочки среди всех клиентов.
2. **Две новые колонки** в существующей таблице очереди (`#publishing/publishing?sub=up:queue`): **«перенесено»** (на какую дату уехал слот в автовыкладке) и **«попытка»** (сколько раз пытались перевыложить).

Клиентам переносы **пока не показываем** (в описании явно «пока нет») — клиентская часть вне scope.

## 4. Контракт данных к #108 (тонкий)

Планировщик читает **только** то, что уже есть в spec #108 — новых полей под перенос не запрашиваем:

| Поле / источник | Откуда (#108) | Зачем планировщику |
|---|---|---|
| `publish_queue.client_publish_id` (uuid, стабилен через ре-queue) | #108 §4 | Связать все попытки одного намерения (контент × аккаунт × платформа); ключ для счётчика попыток и таймлайна |
| `publish_tasks.client_publish_id` + `publish_tasks.created_at` + `publish_tasks.status` | #108 §4 (леджер попыток) | **Таймлайн попыток** — основа вывода переносов (кто на какой МСК-день уехал/закрылся) и счётчика «попытка» |
| `publish_tasks.error_class` | #108 §4/§5 | Подпись причины в деталях слота (network/ui_changed/banned/...); не обязательно для карточек |
| `publish_queue.manual_handoff_at` (timestamptz NULL) | #108 §4/§8 | Признак «ушло в ручную» (день 3) → режим `👋 вручную` и дата ручного дня |

**Деградация без #108:** до мёрджа+бэкфилла #108 этих полей нет. Планировщик и колонки очереди **не падают**, а вырождаются: карточки рисуются по `publish_queue`/`unic` без цепочек переносов и без счётчика попыток (колонки показывают `—`). Частичная ценность доступна сразу; полные переносы «загораются», когда #108 в проде и проставил `client_publish_id`/леджер. Все обращения к полям #108 — через защиту существования (`COALESCE`/проверка колонки), либо фича-флаг (см. §13).

## 5. Read-model: эндпоинт планировщика

Новый эндпоинт `GET /api/publish/planner?from=<DATE>&to=<DATE>&project_id=<опц.>` (зеркалит стиль `manual_publish_queue.js`: модуль `publish_planner.js` + роут в `server.js`). Вся агрегация — на бэкенде; фронт только рендерит.

Read-model **объединяет два источника** (UNION на уровне карточек):
- **Выкладка** (`publish_queue` + леджер `publish_tasks`) → карточки `published`/`partial`/`echo`/`final` с `N/N` и переносами.
- **План контента** (расписание + статус модерации) → карточки `approved`/`pending` на будущие дни, где строк выкладки ещё нет. Точные таблицы плана (`validator_schedule_slots` + статус `unic_results`/контента) и их джойн «контент по дню по проекту» — сверяются на этапе плана (см. §17).

Возвращает **карточки**, уже разложенные по дням недели. Карточка = «исходный слот (проект × ролик) в проекции на конкретный день»:

```jsonc
{
  "chain_id": "slot:<id>",        // стабилен для всей цепочки переноса (см. §6)
  "business_date": "2026-05-20",  // день-колонка, в которой стоит карточка (МСК)
  "project_id": 12, "project_name": "Relisme",
  "video_title": "Одна вещь — два формата. Удобно?",
  "total_accounts": 10,           // N
  "done_count": 5,                // M, выложено к концу этого дня (нарастающим)
  "state": "partial",             // published|approved|pending|partial|echo|final
  "mode": "auto",                 // auto|manual (по завершениям этого дня)
  "carried_in_from": null,        // DATE|null — ↩ с DD.MM
  "carried_out_count": 5,         // K — сколько уехало на следующий день
  "carried_out_to": "2026-05-21", // DATE|null — ↗ K на DD.MM
  "closed_transfer_from": null    // DATE|null — ↩ закрыло перенос с DD.MM
}
```

Группировка/идентичность цепочки (`chain_id`): «исходный слот» = `(project_id, исходный слот)`, где слот резолвится через `unic_task.meta.slot_id` (как в #108 §8). Все аккаунт-намерения (`client_publish_id`) этого ролика входят в одну цепочку. Точный ключ (`slot_id` vs `unic_task_id`) — сверяется на этапе плана (см. §17).

## 6. Карточки и состояния

Состояния и палитра — из макета (стандарт CH; оранжевый = «в процессе, не закрыто»):

| state | Бордер | Бейдж | Условие |
|---|---|---|---|
| `published` | фиолетовый | `опубликовано N/N` | Обычная публикация: все аккаунты выложены в свой день, без переноса |
| `approved` | зелёный | `✅ Одобрено` | Будущий план: контент одобрен, ещё не выкладывался |
| `pending` | жёлтый | `⏳ Требует одобрения` | Контент ждёт модерации команды |
| `partial` | оранжевый | `⚠️ Частично M/N` + прогресс-бар | **День-источник:** часть выложена, остаток уехал → `↗ K на DD.MM` |
| `echo` | оранжевый | `🔄 Перенос M/N` + прогресс-бар | **День-приёмник, ещё не закрыт:** `↩ с DD.MM` + `↗ K на DD.MM` |
| `final` | фиолетовый | `опубликовано N/N` + прогресс 100% | **Цепочка закрыта в этот день:** `↩ закрыло перенос с DD.MM` |

- **Плашка режима** (низ карточки, всегда): `🤖 авто` или `👋 вручную`. `manual` — когда завершения этого дня прошли через ручную выкладку (`manual_handoff_at` ⇒ день 3). День-1/день-2 цепочки = `авто`.
- **Hover-highlight:** у каждой карточки `data-chain="<chain_id>"`. При наведении на любую карточку цепочки все карточки с другим `chain_id` приглушаются (`opacity .2`), эхо-карты цепочки остаются яркими. Логика — как в макете (mouseenter/mouseleave).
- **Прогресс-бар** (`progress-mini`): `done_count/total_accounts`, оранжевый для partial/echo, фиолетовый для published/final.

## 7. Вывод переносов из таймлайна (ядро Подхода 1)

Для каждой цепочки (исходный слот) с исходной бизнес-датой `D0` (МСК) и `N` аккаунт-намерениями:

1. **Реконструкция по аккаунтам:** для каждого `client_publish_id` находим бизнес-день **успеха** = МСК-дата первой `publish_tasks` со `status IN ('done','published')` (с пойманным `post_url`, либо `published_no_url` = успех без ссылки, #86). Если успеха нет — намерение ещё в процессе/исчерпано.
2. **Раскладка по дням:** успехи группируются по МСК-дню. `done_count` на день `Dk` = нарастающий итог успехов до конца `Dk` включительно.
3. **Карточки цепочки:** цепочка порождает карточку на **каждый бизнес-день с активностью** (попытки/успехи) в окне `[from,to]`, плюс `D0`:
   - На `D0`: `partial`, если к концу `D0` выложено `M<N` (остаток `K=N−M` уехал на ближайший следующий день активности → `carried_out_*`); иначе `published`.
   - На `Dk` (`k>0`): `echo`, если после `Dk` всё ещё не все `N`; `final`, если к концу `Dk` достигнуто `N`. `carried_in_from` = предыдущий день активности.
   - `mode` карточки `Dk` = `manual`, если завершения этого дня прошли через `manual_handoff` (день 3).
4. **Счётчик «попытка»** (для деталей и колонки очереди) = `COUNT(publish_tasks)` по `client_publish_id`, исключая `error_code='process_interrupted'` (PM2 deploy-kill — не баг).

> ⚠️ **Все вычисления «календарного дня» — в `Europe/Moscow`** (`(<ts> AT TIME ZONE 'Europe/Moscow')::date`), а не в TZ сессии БД. Зеркалит правило #108 §7; иначе у границы суток попытки/переносы лягут не в тот день. Логику day-rollover вынести в **общий хелпер** (один источник правды с #108, чтобы реконструкция совпадала с фактическим поведением движка).

**Будущие дни (нет строк `publish_queue`):** карточки `approved`/`pending` берутся из плана контента (расписание + статус модерации), без `N/N` (решено — показываем; точный источник плана сверяется на этапе плана, §17.1).

## 8. Новые колонки в таблице очереди

Добавляются в `up:queue` перед колонкой «Действия» (HTML-заголовки `~2410–2440`, рендер `upqRenderRow()` `~11129–11141`):

- **«попытка»** = агрегат `COUNT(publish_tasks WHERE client_publish_id = pq.client_publish_id AND error_code <> 'process_interrupted')`. В `GET /api/publish/queue` добавить коррелированный подзапрос / `LEFT JOIN LATERAL` по `client_publish_id` (текущий джойн берёт только одну связанную задачу — недостаточно). `0`/`—` если нет `client_publish_id`.
- **«перенесено»** (дата) = вывод: МСК-бизнес-дата **последней** попытки, если она позже исходной `scheduled_at`-даты; либо `date(manual_handoff_at)`, если ушло в ручную; иначе `—`. Считается тем же хелпером (§7), без хранения в схеме.

Колонки read-only, без сортировки/фильтра в первой итерации (можно добавить позже). За фича-флагом (§13), чтобы скрыть до прода #108.

- **Кнопка сайдбара** в группе publishing: `nav('publishing'); upSwitchTab('planner')`, id `nav-publishing-planner`, подпись «📅 Планировщик».

## 10. Интерактивность

- **Просмотр + навигация:** недельная навигация (prev/next), hover-подсветка цепочки, фильтр по проекту.
- **Клик по карточке → детали слота:** переход в под-таб `up:queue`, **предотфильтрованный по цепочке** (project + ролик + дата), чтобы показать подслоты по аккаунтам (строки очереди = подслоты, с их статусом/попытками/событиями через существующий «Show Events»). Минимум нового UI: переиспользуем таблицу очереди как «детали слота». Реализация: `upSwitchTab('queue')` + проставить фильтры (по `chain`/`project_id`+`unic_task_id`+дате).
- **Без действий:** запуск/отмена/перепланирование из планировщика — вне scope (см. §16).

## 11. Сортировка / раскладка карточек

Из описания: «чтобы карточки примерно рядом были, не получилось так что сегодня ролик вверху, а завтрашний перенос где-то 20-й внизу второго столбца».

- **Цель:** карточки одной цепочки переноса должны читаться **горизонтально** — стоять примерно на одной «полосе» (row) в соседних колонках-днях, чтобы hover-подсветка и взгляд легко прослеживали перенос.
- **Решение:** активным цепочкам переноса (оранжевые/закрытые) присваиваем стабильную «полосу» (lane) и поднимаем их к верху колонок; затем сортируем по `chain_id` (детерминированно) → одна цепочка занимает близкую вертикальную позицию во всех днях. Обычные (не-переносные) карточки идут ниже, сортировка по времени слота. Точная схема lane-assignment — деталь реализации (достаточно «сначала переносные цепочки, стабильный порядок по chain_id, потом остальные по времени»).

## 12. Edge cases

- **Цепочка через границу недели** (началась на прошлой неделе, закрывается на текущей): `carried_in_from` показываем даже если день-источник вне экрана; недельная навигация открывает источник.
- **Легаси без `client_publish_id`** (строки до бэкфилла #108): группируем по фолбэку (`unic_task_id`), переносы/попытки не выводим (нет линковки попыток) — карточка как обычная published/partial по статусам. Не падаем.
- **`process_interrupted`** (PM2 deploy-kill) — исключаем из счётчика попыток и из реконструкции (не баг).
- **`published_no_url`** — успех без ссылки (#86), считается выложенным (`done`), НЕ failed-попыткой.
- **Структурная ошибка (`banned`/`ui_changed`)** — #108 уводит в ручную сразу, без 2 дней авто. Карточка может стать `manual` раньше дня 3; режим/перенос отражают факт по `manual_handoff_at`.
- **Смешанные платформы в одной карточке** (IG+TT+YT): карточка агрегирует `N/N` по всем аккаунтам; разбивка по аккаунтам/платформам — в деталях слота (очередь).
- **`N` меняется** (аккаунт убрали/добавили): берём текущее число строк `publish_queue` цепочки.
- **День без активности у цепочки** в середине окна (например, лимит 3/сутки исчерпан, ждём завтра): карточки на этот день нет — цепочка «замирает» и появляется снова в день следующей попытки.

## 13. Kill-switches / флаги

| Флаг | Дефолт | Назначение |
|---|---|---|
| `PLANNER_ENABLED` | true | Под-таб планировщика + эндпоинт `/api/publish/planner` (жёсткий стоп / скрыть до готовности #108) |
| `QUEUE_TRANSFER_COLUMNS_ENABLED` | true | Колонки «перенесено»/«попытка» в очереди (откат отдельно от планировщика) |

Фича read-only, риск низкий; флаги нужны в основном чтобы скрыть UI, пока #108 не в проде (иначе колонки/цепочки показывают `—`).

## 14. Тестирование

- **Бэкенд `node --test` (mock-pool) — `publish_planner.js`:**

  - частичный + перенос на 2 дня → карточки `partial(D0)`/`echo(D1)`/`final(D2)` с корректными `M/N`, `carried_in/out`, `closed_transfer_from`;

- **Колонки очереди:** корректность подзапроса «попытка»; вывод «перенесено» (последняя попытка позже исходной даты / `manual_handoff_at` / `—`).

## 15. Зависимости и деплой

- **Read-only фича.** Полные переносы/попытки зависят от `client_publish_id`/`error_class`/`manual_handoff_at` из #108 (§4). До прода+бэкфилла #108 — деградация (карточки без цепочек, колонки `—`); за фича-флагом.
- **Порядок сборки гибкий** (контракт зафиксирован): #109 фронт+эндпоинт можно мёрджить независимо; полнота «загорается» с приходом #108. Реализатор обращается к полям #108 защищённо (`COALESCE`/проверка наличия колонки) либо гейтит чтение за `PLANNER_ENABLED` до мёрджа #108.
- **Общий day-rollover хелпер** с #108 (§7) — один источник правды по МСК-дню; если #108 ещё не выделил хелпер, выделяем его в #109 так, чтобы #108 переиспользовал.
- **Cross-repo grep перед деплоем** (общая БД `openclaw`): `client_publish_id`, `error_class`, `manual_handoff_at`, имена нового роута/модуля — нет ли коллизий в валидаторе/delivery.
- **Деплой:** фронт (`public/index.html`) + бэкенд (`publish_planner.js` + роут в `server.js`) в autowarm → `pm2 restart autowarm`. Прод-чекаут — с одобрения Данила; **без force-push**; учитываем auto-push hook прод-autowarm (любой коммит в прод-чекаут улетает в `GenGo2/delivery-contenthunter`).

## 16. Non-goals / YAGNI

- **Клиентская часть переносов** — «пока нет» (явно в задаче).
- **Действия из планировщика** (запуск/отмена/перепланирование выкладки) — только просмотр+навигация.
- **Drag-n-drop** перепланирование карточек.
- **Изменение модели данных #108** — переносы выводим, не храним (Подход 1).
- **Месячный вид / произвольные диапазоны** — недельный вид по макету; расширение позже.
- **Сортировка/фильтры по новым колонкам очереди** в первой итерации.

## 17. Открытые вопросы (решаются на этапе плана / spec-review)

1. **Источник плановых карточек (`approved`/`pending`) — РЕШЕНО (показываем из расписания).** Осталось grounding-задачей плана: сверить точные таблицы плана контента (`validator_schedule_slots` + статус модерации `unic_results`/контента) и джойн «контент по дню по проекту», чтобы корректно строить `approved`/`pending` карточки.
2. **Точный ключ цепочки** (`chain_id`): `slot_id` из `unic_task.meta.slot_id` vs `unic_task_id` vs `(project_id, source_video)` — сверить на этапе плана по фактической схеме.
3. **Семантика колонки «перенесено»** для строки, которая ещё падает в окне 2 дней: дата **последней** попытки (факт) vs дата **ожидаемого** следующего ретрая. Рекомендую факт (последняя попытка) + дата ручного дня при handoff.
4. **Режим карточки при смешанной цепочке** (ранние аккаунты — авто, день-3 — вручную): принято «режим по завершениям дня» (день-1/2 = авто, день-3 = вручную). Подтвердить, что это читается понятно.
