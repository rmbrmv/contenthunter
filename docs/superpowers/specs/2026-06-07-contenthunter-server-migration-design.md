## Схема деплоя (полный автомат через GitHub Actions)

Принцип: **на сервере код руками не трогаем; сервер всегда тянет то, что лежит в нужной ветке GitHub.** Серверные копии — deploy-only (только `git pull`, никаких ручных правок) — это устраняет прежнюю боль с гонками на общем checkout.

- В каждом репозитории две долгоживущие ветки: **`develop` → test-стенд**, **`main` → prod-стенд**.
- На каждый push в `develop`/`main` срабатывает **GitHub Actions**, который по SSH заходит на сервер, делает `git pull` нужной ветки в нужной папке, прогоняет миграции БД, перезапускает процесс, делает health-check. Если health-check провалился — деплой красный, старая версия продолжает работать (без даунтайма на проде).
- **Промоушен test → prod** = Pull Request `develop → main`. Само окно PR в GitHub — это момент живого review и финального одобрения. Мердж PR → автоматически уезжает на prod.
- Секреты (API-ключи, токены, SSH-ключ деплоя) — в **GitHub Secrets**, не в репозитории.

### Совместимость с worktree-разработкой
Worktree — локальный инструмент разработки (несколько параллельных сессий Claude Code, каждая в своём worktree на своей feature-ветке). Деплою важно только содержимое веток `develop`/`main` на GitHub. Поток:

```
Сессия A → feature/A ┐
Сессия B → feature/B ┼─→ merge в develop → test (авто)
Сессия C → feature/C ┘        ↓ после теста + review
                          PR develop → main → prod (авто)
```

`develop` — общая интеграционная ветка: несколько фич собираются на тесте вместе (норма). Изолированные preview-стенды на одну фичу сейчас НЕ закладываем (YAGNI).

## База данных

- Боевую `openclaw` дампим (`pg_dump`) и **восстанавливаем на новом сервере под именем `contenthunter`** (старое имя устарело). На этапе дампа сверяем, что в `openclaw` нет «чужих» таблиц соседних продуктов — берём только таблицы ContentHunter.
- В коде/`.env` мигрируемых сервисов меняем имя БД на `contenthunter`. В delivery имя БД сейчас захардкожено в `server.js` (строки ~74 и ~210-213) — правим там.
- `contenthunter_test` = **обезличенный слепок** прода: реальная структура и данные, но занулённые токены/пароли/перс.данные и **выключенная реальная публикация** (kill-switch), чтобы тест не постил в живые аккаунты. Изолирован от боевой БД.
- Старая БД `openclaw` на старом сервере остаётся нетронутой до вывода сервера из эксплуатации (горячий бэкап).

## Последовательность переезда (окно работ)

**Фаза 0 — подготовка (без простоя, заранее):**
1. Получить расширенный `sudo`-доступ (вариант А) на обоих серверах. Прочитать root-конфиги старого сервера (`.env` валидатора, `Caddyfile`).
2. На новом сервере поставить: Caddy, PostgreSQL 16, Node, Python, ADB-клиент, зависимости.
3. Завести в GitHub ветки `develop` в обоих репозиториях; настроить GitHub Actions (workflow деплоя) + GitHub Secrets (SSH-ключ, env).
4. Развернуть 4 стенда (папки, `.env`, процессы PM2/systemd, Caddy-сайты).
5. Создать `contenthunter_test` (обезличенный слепок), поднять **test-стенд**, прогнать смоук-тест.

**Фаза 1 — окно переезда (короткий простой):**
6. На старом сервере повесить плашку «Идут технические работы» (Caddy 503 для всех, кроме IP Данила/Claude) на `client` и `delivery`.
7. **Заморозка записи:** остановить на старом сервере процессы-писатели (PM2 id35/36/33/26/28/29) и root-cron.
8. **Финальный дамп** `openclaw` → восстановить в `contenthunter` на новом сервере.
9. Деплой кода на prod-стенды нового сервера (через ветку `main`), прогон миграций, запуск процессов.
10. **Смоук-тест prod** на новом сервере (вход, дашборд, очередь публикаций, доступ к устройствам ADB и к S3) — на адресах `prod-*`.

**Фаза 2 — переключение и завершение:**
11. Настроить **301-редиректы**: старые `client/delivery.contenthunter.ru` → новые `prod-client/prod-delivery.contenthunter.ru`.
12. Снять плашку, открыть доступ людям.
13. Старый сервер держать как горячий бэкап N дней, затем вывести из эксплуатации.

## Критерии успеха
- Оба интерфейса (prod-client, prod-delivery) работают на новом сервере: вход, ключевые функции, публикация в живые аккаунты через устройства, доступ к S3.
- Данные перенесены без потерь (сверка количества строк ключевых таблиц до/после).
- Тестовый стенд (test-client, test-delivery) работает на отдельной БД, реальная публикация выключена.
- Деплой полностью автоматический: push в `develop` → test, мердж PR в `main` → prod.
- Старые домены 301-редиректят на новые.
- Плашка снята, простой минимален.

## Открытые вопросы / риски
- **Состав БД `openclaw`:** подтвердить на этапе дампа, что нет «чужих» таблиц соседних продуктов (берём только ContentHunter).
- **Сетевой доступ к устройствам/внешнему уникализатору** с нового сервера (firewall/whitelist по IP) — проверить на смоук-тесте, возможно потребуется добавить новый IP в разрешённые на стороне Raspberry Pi / 91.98.180.103.
- **Telegram Login виджет** на client требует, чтобы домен бота в BotFather соответствовал сайту — при смене канонического домена на `prod-client.contenthunter.ru` проверить настройку бота.
- Точный список cron-задач старого сервера, пишущих в `openclaw` (прочитать root-crontab после выдачи доступа), чтобы заморозка была полной.
