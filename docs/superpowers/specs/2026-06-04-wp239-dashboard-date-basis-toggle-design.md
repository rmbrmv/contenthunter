## Проблема

На дашборде автовыкладки два набора метрик считаются от **разных дат**, поэтому не сходятся между собой:

- **Метрики автовыкладки** (плитки, тренд, success rate) — когорта по `pq.scheduled_at` (**дата задачи**: когда строка очереди исполнялась; плывёт от ретраев и переносов).
- **Воронка пайплайна** (WP#153) — когорта по `slot_date` (**запланированная дата**: редакторский план слота; стабильна).

`success_rate = done / (done + errors)` (доля успешных среди исполненных задач) и `sr_total воронки = (выложено авто + вручную + подтв.) / запланировано` (доля выложенного из плана) — это разные формулы, считаемые ещё и по разным датам. Видеть «% успешной выкладки именно из запланированного контента» нельзя, а сравнивать воронку с success rate невозможно.

## Цель

Один переключатель **типа даты** на весь дашборд автовыкладки. От него когортируются **оба** набора метрик — и воронка, и метрики автовыкладки. Формулы метрик **не меняются**; меняется только дата-ось когорты. Дефолт — запланированная дата.

## Решение

### Базис даты

Новый параметр `date_basis` с двумя значениями:

| Значение | Дата когорты | Смысл |
|----------|--------------|-------|
| `planned` (**дефолт**) | `COALESCE(s.slot_date, ut.slot_date)` | Запланированная дата слота |
| `task` | `pq.scheduled_at` (в МСК-границах) | Дата задачи (как сейчас) |

`planned` становится поведением по умолчанию для дашборда и нового блока в телеграме. Отдельного серверного kill-switch **нет** (решение по WP#239): аварийный откат к прежней семантике — это сам UI-переключатель в положение «Дата задачи».

### Backend — `/api/publish-queue/dashboard` (server.js)

1. Принять query-параметр `date_basis` (валидировать в `{planned, task}`, иначе `planned`).
2. Подключить к когортным запросам цепочку до слота. В дашбордовом FROM (`PUBLISH_QUEUE_FROM`) уже есть `LEFT JOIN unic_tasks ut`; добавить `LEFT JOIN validator_schedule_slots s ON s.id = NULLIF(ut.meta->>'slot_id','')::int` (как в воронке).
3. Выбор когорта-даты в `tilesSql` и `seriesSql`:
   - `planned`: фильтр `COALESCE(s.slot_date, ut.slot_date) >= $slotFrom::date AND < $slotTo::date` (границы из `slotDateBoundsFromRange(range)`, как воронка).
   - `task`: текущий фильтр `pq.scheduled_at >= $1 AND < $2`.
4. **Гранулярность тренда под `planned`**: `slot_date` дневной → серия принудительно по дням (`unit='day'`). Часовые бакеты допустимы только под `task`. `pickBucketUnit` вызывается только в режиме `task`; в `planned` юнит фиксируется `day`.
5. Воронка: пробросить `basis` в `computeFunnel` (см. ниже).
6. Вернуть `date_basis` в ответе (поле верхнего уровня) — UI отображает активный базис.

### Backend — воронка (pipeline_funnel.js)

`computeFunnel({ pool, slotDateFrom, slotDateToExcl, filters, basis })`. По умолчанию `basis='planned'` (текущее поведение Q1–Q4 без изменений).

При `basis='task'` окно каждой подзапросной когорты — по `scheduled_at`, а не по slot_date:

- **Q1, Q4** (`publish_queue`): `WHERE pq.scheduled_at >= $from AND < $to` (МСК-границы) вместо `COALESCE(s.slot_date, ut.slot_date)`.
- **Q2** (`validator_manual_publish_queue`): у ручной очереди нет `scheduled_at`. По выбору заказчика — **строки без `scheduled_at` исключаются** из воронки в режиме `task`. Практически: реактивная ручная привязана к строке publish_queue (через `unic_result_id`+account+platform), её можно оконить по `scheduled_at` соответствующей строки; проактивная-ручная без строки очереди в режим `task` **не попадает**.
- **Q3** (`validator_schedule_slots`, слепая зона «до уникализации»): слот без строки очереди не имеет `scheduled_at` → в режиме `task` исключается. Следствие: `slots_planned` под `task` = слоты, у которых есть строка очереди, оконенная по `scheduled_at`; слепая зона `before_uniq` стремится к 0.

Передавать в `computeFunnel` нужно и slot-границы (для `planned`), и UTC-границы диапазона (для `task`). Сигнатуру расширить: добавить `rangeFrom`/`rangeTo` (UTC Date) либо передавать весь `range`.

**Замечание о согласованности:** в режиме `task` числитель и знаменатель воронки берутся по одной дате (`scheduled_at`), поэтому воронка и success rate когортируются одинаково. Прямого тождества чисел между двумя формулами не возникает (разные определения), но обе считают одну и ту же когорту задач.

### Frontend — переключатель

Сегментированный переключатель рядом с выбором периода на дашборде автовыкладки:

```
Период: [Сегодня ▾]   Дата: ( ● Запланировано ) ( Дата задачи )
```

- Значения: «Запланировано» → `planned`, «Дата задачи» → `task`. Дефолт — «Запланировано».
- Переключение меняет `date_basis` и ре-фетчит дашборд (один запрос, ~доли секунды).
- Тултип-пояснение: «Запланировано — по дате слота из плана; Дата задачи — по дате исполнения публикации».

### Telegram — ежедневный отчёт (daily_publish_report.js)

**Оба расчёта рядом** (по выбору заказчика). Текущий отчёт считает per-platform SR по `scheduled_at`, а блок воронки — по slot_date. После изменения отчёт содержит обе версии, явно помеченные:

- Блок «по дате задачи»: per-platform SR + воронка, оконенные по `scheduled_at` (текущее поведение SR + воронка с `basis='task'`).
- Блок «по запланированной дате»: per-platform SR + воронка, оконенные по slot_date (`basis='planned'`).

Заголовки явно называют базис, чтобы числа не путались. SR per-platform под `planned` считается по той же цепочке слота, что и плитки дашборда.

## Тестирование (TDD)

- **pipeline_funnel:** воронка под `planned` (без регрессии к текущим числам) и под `task`; исключение строк без `scheduled_at` в `task`; границы окон.
- **server.js dashboard:** сборка SQL для `planned`/`task`; форс дневной гранулярности серии под `planned`; дефолт `planned` при отсутствии/некорректном `date_basis`; `date_basis` в ответе.
- **daily_publish_report:** формат сообщения с двумя блоками; независимый расчёт обоих базисов; per-platform SR под `planned`.

## Открытые риски

- **Производительность серии под `planned`:** добавочный джойн на `validator_schedule_slots` и группировка по `slot_date`. Ожидается приемлемо (LEFT JOIN по PK слота, без фан-аута), подтвердить на проде после раскатки.
- **Семантика `task`-воронки:** исключение проактивной-ручной и неочередённых слотов делает воронку в режиме `task` уже воронки в `planned`. Это осознанный выбор заказчика; в UI стоит сопроводить тултипом, что режим «Дата задачи» считает только исполнявшиеся задачи.
