# Дашборд выкладки: пояс отображения, «на сейчас» и факт-время часового ряда

Дата: 2026-06-05
Репозиторий кода: `delivery-contenthunter` (дашборд — `server.js`, фронт — `public/index.html`, помощники пояса — `tz_display.js`).
Статус: дизайн на согласовании.

## Проблема (как её увидел пользователь)

На дашборде выкладки график «Success rate в динамике» (режим **«Дата задачи»**, пресет **«Сегодня»**) выглядит так, будто данные отстают от настенных часов МСК примерно на час: в 12:55 МСК линия обрывается на ~11:00–12:00 и «проваливается» в 0%. Восприятие — «потеряли таймзону / дашборд отстал».

## Диагноз (подтверждён живыми данными на 2026-06-05 13:30 МСК)

Таймзонного бага **нет**. Проверено:

- `SELECT now() AT TIME ZONE 'Europe/Moscow'` → `2026-06-05 13:30` — совпадает с настенными часами; БД отдаёт МСК верно.
- Ось графика (`buildBucketAxis` → `hourLabelInTz`) и бакеты данных
  (`date_trunc('hour', pq.scheduled_at AT TIME ZONE 'Europe/Moscow')`) дают **одну и ту же** МСК-стену часа. Сдвига нет (был бы 3 часа, а не 1, если бы пояс «забыли»).

Почасовое распределение СЕГОДНЯ по `scheduled_at` (МСК):

| Час | total | done | errors | in_progress | SR |
|-----|------:|-----:|-------:|------------:|----|
| 08:00 | 156 | 61 | 11 | 0 | 85% |
| 09:00 | 75 | 40 | 7 | 0 | 85% |
| 10:00 | 28 | 18 | 8 | 0 | 69% |
| 11:00 | 23 | 13 | 4 | 4 | 76% |
| 12:00 | 11 | 3 | 4 | 1 | 43% |
| **13:00** | **60** | **0** | **0** | **58** | **— (gap)** |
| 14:00–21:00 | 3 | 0 | 0 | 3 | — (gap) |

Корень «отставания» — **структурный**, две причины:

1. **Группировка по плановому времени.** Ряд бакетится по `scheduled_at` (плановое время слота), а не по факту выкладки. При этом сам режим называется «Дата задачи / дата исполнения публикации» — внутренняя нестыковка.
2. **Текущий час всегда «недозрел».** В текущем часе публикации ещё `in_progress` → `done+errors=0` → `assembleSeries` ставит `null` → **разрыв**, точки нет. Линия замирает на последнем **завершённом** часе. На скрине 12:55 текущим был 12:00, где успехи на тот момент ещё не накопились → визуальный провал в 0%.
3. Плюс **нет подписи**, что данные по МСК и «на текущий момент» — поэтому это читается как сбой.

## Цель

Чтобы данные на графике совпадали с текущим временем МСК и было явно видно: «данные по Москве, по состоянию на сейчас». Покрыть все согласованные пункты A/B/C.

## Дизайн

Три независимых изменения. Когорта (basis planned/task) и дневной режим **не меняются** — затрагивается только почасовой ряд и оформление графика.

### A. Подпись пояса + «на сейчас»

Над графиком (и/или в шапке дашборда) показывать:

```
🌍 По Москве (UTC+3) · данные на 13:30
```

- Пояс берётся из настроек пользователя через `resolveDisplayTz(req)` (дефолт МСК) — **без хардкода**.
- API `GET /api/publish-queue/dashboard` добавляет в ответ блок:
  - `display_tz` — IANA-имя (например `Europe/Moscow`);
  - `display_tz_label` — человекочитаемое смещение (`UTC+3`), вычисляется из `tzOffsetMs` в `tz_display.js`;
  - `as_of` — серверное «сейчас» в поясе отображения (`HH:MM`), чтобы метка не зависела от часов браузера.
- Фронт рендерит метку из этих полей. Метка обновляется при автообновлении дашборда.

### B. Отметка текущего часа

На графике (Chart.js, canvas `#dash-chart`) в почасовом режиме:

- вертикальный маркер «сейчас» на текущем часе (через annotation-плагин, если он подключён; иначе — пунктирный последний сегмент + точка «полая»/иного стиля);
- сноска под графиком: `Текущий час (13:00–13:59) ещё заполняется`.

Цель — чтобы правый край (последний завершённый час) не читался как поломка.

### C. Часовой ряд по факту выкладки (режим «Дата задачи»)

В **почасовом** режиме (`basis=task`, `unit='hour'`) бакетить ряд по **фактическому времени выкладки** вместо планового:

- Текущее выражение бакета:
  `date_trunc('${unit}', pq.scheduled_at ${tzClause(dtz)})`
- Новое (под kill-switch):
  `date_trunc('${unit}', COALESCE(pq.updated_at, pq.scheduled_at) ${tzClause(dtz)})`

`pq.updated_at` — timestamptz (после WP#247 Фаза 2), момент перехода задачи в терминальный статус (`done`/`failed`/`cancelled`/…). Это то же поле, что `lifecycle.js` использует как прокси времени выкладки (`COALESCE(mq.published_at, pq.updated_at)`). `COALESCE(..., scheduled_at)` — страховка, хотя у `updated_at` есть `DEFAULT now()`.

Эффект: завершённые в текущем часе публикации попадают в текущий бакет → линия доходит до текущего часа и совпадает с часами. `in_progress` не считаются (правильно — ещё не выложены), поэтому текущий час остаётся частичным (см. пункт B).

**Kill-switch:** `DASHBOARD_SERIES_ACTUAL_TIME_ENABLED` (дефолт ON; code-default — старое поведение по `scheduled_at`). Откат = выключить флаг.

**Что НЕ меняется:**
- Когорта (`whereSql`/`baseParams`) остаётся по `scheduled_at` — плитки, воронка, окно не затрагиваются (минимальная, изолированная правка только выражения бакета ряда).
- Режим «Запланировано» (`basis=planned`, дневной по `slot_date`) — без изменений.

### Известные ограничения (приемлемы, follow-up при необходимости)

Когорта осталась по `scheduled_at`, а ось — по `updated_at`, поэтому на стыке суток возможны краевые случаи:
- задача, запланированная сегодня, но завершённая после полуночи, выпадет за правую границу оси (бакет вне axis → отбрасывается);
- задача, запланированная вчера и завершённая сегодня ночью, в «сегодня» не попадёт (нет в когорте).

Для внутридневного «сегодня» это пренебрежимо (слот и исполнение обычно в одни сутки). При желании — отдельный follow-up: когорта факт-режима по `updated_at`.

## Тестирование

Стиль проекта — TDD + kill-switch + субагент-driven (см. WP#247/#239/#221).

- **C (бэкенд):** юнит-тесты на выражение бакета — флаг ON → `COALESCE(updated_at, scheduled_at) AT TIME ZONE …`; флаг OFF → прежнее `scheduled_at`. Проверка, что когорта/плитки не изменились. Регрессия существующих dashboard/funnel/tz тестов зелёная.
- **A (бэкенд):** тест, что ответ содержит `display_tz`/`display_tz_label`/`as_of`, корректные для МСК и для не-МСК пояса (например `Asia/Yekaterinburg`).
- **B (фронт):** smoke-проверка рендера маркера/сноски в почасовом режиме; в дневном — отсутствует.
- Сверка часовой раскладки факт-режима с живым SQL (по `updated_at`) на проде после деплоя.

## Вне рамок

- Изменение когорты факт-режима (только ось).
- Отчёт `daily_publish_report.js`, воронка `pipeline_funnel.js`, farming-графики — не трогаем.
- Отдельный переключатель «План/Факт» — отклонён в пользу замены в режиме «Дата задачи».

## Файлы
