# WP#247 — Per-user часовой пояс отображения (Фаза 1)

**Тип:** Ошибка/улучшение (корневой фоллоу-ап WP#220/#221) · **Приоритет:** Обычный (отчётность, не hot-path) · **OpenProject:** #247

## Контекст и проблема

Сервер и хранение работают в **UTC**. Колонки публикационного пайплайна `publish_queue.scheduled_at` и `publish_tasks.created_at` — `timestamp without time zone` со значениями по Гринвичу (naive-UTC). Для отображения в МСК код применяет конвертацию **тремя разными способами**, что и есть корневой footgun:

1. SQL-константа `MSK = AT TIME ZONE 'Europe/Moscow'` — корректна только для timestamptz-колонок (`manual_handoff_at`, `published_at`).
2. SQL-константа `MSK_FROM_UTC = AT TIME ZONE 'UTC' AT TIME ZONE 'Europe/Moscow'` — для naive-UTC-колонок (введена в WP#221).
3. JS-хардкод `MSK_OFFSET_MS = 3 * 60 * 60 * 1000` (ручной «+3 часа») в `pipeline_funnel.js`, `daily_publish_report.js`, `server.js`.

Перепутать способы легко (ровно это породило WP#220 и WP#221), а пояс жёстко зашит как `'Europe/Moscow'` — нельзя показать оператору даты в его поясе.

## Цель

Привести отображение к единой модели **store-UTC / compare-naked / display-from-settings**:
- хранение остаётся каноническим UTC (значения уже UTC — не трогаем);
- логика сравнения инстантов (диспатч «пора публиковать», сортировки) часовых поясов не требует и не меняется;
- **отображение** дат/времён пересчитывается в часовой пояс, выбранный пользователем в настройках; по умолчанию — `Europe/Moscow` (текущее поведение).

### Решённые границы (брейншторм с Данилом)

- **Подход C, фазами.** Этот WP = Фаза 1: только слой отображения, **без ALTER колонок**. Миграция колонок в `timestamptz` (устранение footgun на уровне типа) — отдельный WP позже (Фаза 2), т.к. затрагивает горячий путь диспатча и аудит записей и фиче отображения не нужна.
- **Per-user, но только отображение.** Личный пояс меняет лишь *как показаны* даты/времена в дашбордах/логах/очереди. **Планирование публикаций остаётся в бизнес-поясе МСК** (когда ролик физически выкладывается — бизнес-решение, флот живёт по Москве). Горячий путь диспатча и запись `scheduled_at` НЕ трогаются.
- **Без kill-switch:** дефолтный пояс `Europe/Moscow` даёт поведение байт-в-байт как сейчас; фича ничего не меняет, пока пользователь сам не выберет не-МСК пояс.

## Дизайн

### 1. Модель данных — пояс пользователя

- Новая колонка `autowarm_users.timezone TEXT NOT NULL DEFAULT 'Europe/Moscow'`.
- Миграция аддитивная, на маленькой внутренней таблице, бэкфилл автоматом дефолтом → нулевой риск, не горячий путь.
- Валидация значения при сохранении: пояс обязан присутствовать в `pg_timezone_names` (набор, который знает сам Postgres). Неизвестный пояс отклоняется.

### 2. Резолв пояса на запрос

- `resolveDisplayTz(req) -> string`: возвращает `req.session.user.timezone`, иначе фоллбэк `'Europe/Moscow'`.
- Пояс кладётся в `req.session.user` при логине (рядом с `{id, username, role}`) и обновляется при смене в настройках — чтобы не ходить в БД на каждый запрос.
- **Неинтерактивные контексты** (cron `daily_publish_report.js`, telegram-рассылка) — `req` нет → дефолт `'Europe/Moscow'` (бизнес-пояс). Рассылка остаётся в МСК.

### 3. Единый источник истины конвертации (убираем три способа)

Новый модуль-хелпер (напр. `tz_display.js`), принимающий пояс параметром:

```js
// naive-UTC колонки (scheduled_at, created_at): пометить UTC, затем перевести в пояс
naiveDateInTz(colExpr, tz)  // -> (colExpr AT TIME ZONE 'UTC' AT TIME ZONE '<tz>')::date
// timestamptz колонки (manual_handoff_at, published_at): прямой перевод
tzDateInTz(colExpr, tz)     // -> (colExpr AT TIME ZONE '<tz>')::date
// JS-форматирование момента в пояс — через Intl/tz-aware, без ручного +3ч
formatInstantInTz(date, tz, fmt)
```

- **Безопасность интерполяции:** `tz` валидируется против кэшированного allowlist `pg_timezone_names` перед подстановкой в SQL. Инъекция невозможна — значение обязано точно совпасть с известным именем пояса. (Параметризация `$N` рассматривалась, но ломает нумерацию параметров в существующих запросах; валидированная интерполяция чище и совпадает со стилем текущего кода, где `MSK`/`MSK_FROM_UTC` уже интерполируются.)
- Старые константы `MSK` / `MSK_FROM_UTC` и хардкоды `MSK_OFFSET_MS` заменяются вызовами хелперов с резолвнутым поясом.

### 4. Проводка пояса во все читающие места

Каждый эндпоинт отчётности резолвит `tz` из `req` и передаёт в хелперы вместо хардкод-констант. Поверхность (по инвентарю кода):

| Файл | Места |
|---|---|
| `publish_planner.js` | `getPlannerCards` (chain_id, scheduled_date, business_date, WHERE-окна, JOIN `= s.slot_date`, created_at-попытки), `attachQueueTransferColumns` |
| `server.js` | business_date-фильтр (`pt.created_at`), лейблы часов дашборда (timestamptz `h.hour`), JS-конвертации `scheduled_at` (≈2317, 6742), `date_from`/`date_to`, **когортные окна дашборда WP#239** (`dashboardDateWindow`/`resolveDateBasis`/`DASHBOARD_QUEUE_FROM` — плитки/тренд/SR) |
| `pipeline_funnel.js` | окна воронки — границы выбранного пользователем диапазона вычисляются в его поясе (`task`-базис: range по `scheduled_at`; `planned`-базис по `slot_date` — чистая дата, поясонезависим) |
| `daily_publish_report.js` | cron-контекст → дефолт МСК |

Это самый объёмный раздел — отображаемых дат много; такова цена «полного per-user». **`slot_date`** — чистый `date` (целевой бизнес-день, поясонезависим), участвует в JOIN как есть.

### 5. Планирование остаётся в МСК

- Запись `scheduled_at` и горячий путь диспатча (`scheduled_at <= NOW() + INTERVAL …`) НЕ трогаются.
- UI-пикер расписания явно подписывается «МСК», чтобы оператор в другом поясе не путал: он *видит* времена в своём поясе, но *планирует* в московском бизнес-времени.

### 6. UI-настройка пояса

- Выпадающий список в настройках пользователя: курированный RU/СНГ-список (Москва, Калининград, Самара, Екатеринбург, Омск, Красноярск, Иркутск, Якутск, Владивосток, Магадан + пара СНГ) с переключателем «показать все» → полный IANA из `pg_timezone_names`.
- Сохранение `POST /api/me/timezone` → валидация → `UPDATE autowarm_users.timezone` + обновление `req.session.user.timezone`.

## Тестирование (TDD)

1. **Хелперы:** `naiveDateInTz`/`tzDateInTz` дают верную дату для МСК и второго пояса (напр. `Asia/Yekaterinburg`, +5) на граничном инстанте `2026-06-04 22:30:00` UTC (МСК → 05-е; Екб → 05-е; для значений у границы +5 vs +3 даты расходятся).
2. **Регрессия-эквивалентность:** `tz='Europe/Moscow'` даёт результат, идентичный текущим константам `MSK`/`MSK_FROM_UTC` (доказываем отсутствие изменения поведения для существующих пользователей).
3. **Per-user смок эндпоинта:** один и тот же набор строк, запрошенный пользователем с tz=МСК и tz=не-МСК, возвращает даты в соответствующем поясе.
4. **Валидация пояса:** невалидный пояс отклоняется при сохранении; резолв невалидного/пустого → фоллбэк МСК.

Аддитивная миграция (колонка `autowarm_users.timezone`). Прод `git pull` + `sudo pm2 restart 35`. Код-репозиторий = **delivery-contenthunter** (autowarm), правки в изолированном worktree. Доки — в rmbrmv/contenthunter отдельным PR.

## Критерий приёмки

- Все три способа конвертации (`MSK`, `MSK_FROM_UTC`, `MSK_OFFSET_MS`) сведены к одному хелперу с поясом-параметром.
- Пользователь выбирает пояс в настройках; даты/времена в дашбордах/логах/очереди/планировщике/воронке показываются в его поясе; дефолт МСК.
- Планирование и диспатч не изменились (регрессия-эквивалентность при tz=МСК зелёная).
- Тесты 1–4 зелёные.
- OP#247 → Тестирование, затем верификация в UI Данилом → Готово.

## Вне объёма (Фаза 2, отдельный WP)

- ALTER `publish_queue.scheduled_at` / `publish_tasks.created_at` → `timestamptz` (устранение footgun на уровне типа, схлопывание `naiveDateInTz`/`tzDateInTz` в один рецепт). Затрагивает горячий путь и аудит записей — делается отдельной тщательно верифицируемой правкой.
- Per-user пояс для *планирования* (если когда-нибудь понадобится) — сейчас сознательно нет.
